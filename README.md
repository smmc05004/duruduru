# DURUDURU (두루두루)

사용자가 목적지를 먼저 정하지 않아도 되는 국내 여행 추천 서비스의 PoC입니다. 출발지와 정확한 출발·복귀 시간, 이동수단, 관심사를 입력하면 **주어진 시간 안에 갈 수 있는 목적지부터** 추천하고, 선택한 지역의 간단한 일정 타임라인을 만듭니다.

> 기존 여행 플래너가 “경주에 가는데 무엇을 할까?”를 돕는다면, DURUDURU는 “이번 주말 이 시간에 어디를 다녀올 수 있을까?”를 먼저 해결합니다.

## 현재 상태

현재는 외부 API 없이 실행되는 화면 중심의 PoC입니다. 경주·공주·강릉의 목업 데이터를 사용하며, 추천과 일정 생성은 클라이언트에서 실행되는 규칙 기반 로직입니다.

- 실제 공공 API를 사용자 흐름에 연결하지 않았습니다.
- 데이터베이스, 로그인, 여행 저장 기능은 없습니다.
- 스탬프, 방문 인증, 친구, 컬렉션, 랭킹은 현재 범위에 포함되지 않습니다.
- 대중교통 선택 UI와 해당 목업 이동시간은 있지만, 초기 제품 방향에서 정식 지원 대상으로 확정된 것은 자차입니다.

## 주요 사용자 흐름

1. 출발지(서울·대전·부산), 출발·복귀 일시, 자차/대중교통, 관심사(역사·자연·문화·미식)를 입력합니다.
2. 입력한 전체 시간과 왕복 평균 이동시간을 바탕으로 목적지 후보를 점수순으로 보여 줍니다.
3. 관심사와 목적지 태그가 겹칠수록 점수가 높아지고, 왕복 이동시간을 뺀 뒤 7시간 이상을 확보할 수 있는지를 반영합니다.
4. 후보를 선택하면 관심사에 맞는 장소를 우선 배치한 간단한 일정과 복귀 이동 항목을 확인합니다.
5. 여행 기간이 목업 축제 기간과 겹치면 축제 제안을 일정에 표시합니다.

## 현재 PoC의 일정 생성 방식

`lib/planner.ts`의 `buildItinerary`가 선택 지역의 장소를 관심사 우선으로 정렬하고, 장소별 목업 운영시간·휴무 요일·권장 체류시간을 기준으로 순서대로 배치합니다. 장소 사이에는 고정 30분을 더하고, 마지막에는 입력한 복귀 시각에서 목적지별 평균 이동시간을 뺀 복귀 이동을 표시합니다.

이는 알고리즘과 사용자 흐름을 검증하기 위한 단순 구현입니다. 다음 항목은 아직 완전하게 제약 검증하지 않습니다.

- 장소 간 실제 거리 또는 도로 이동시간
- 식사 시간과 음식점의 시간·위치
- 모든 배치 항목이 복귀 출발시각 전인지의 엄격한 검증
- 운영시간/휴무 데이터 결측, 날짜별 예외 운영, 실제 교통 상황

따라서 화면의 시간과 이동시간은 목업 기반 예상치이며, 실제 여행에 바로 사용하면 안 됩니다.

## 기술 스택

- Next.js 15.4 (App Router)
- React 19, TypeScript
- ESLint 9 + `eslint-config-next`
- 별도 백엔드·DB·상태 관리 라이브러리 없음

```text
app/

scripts/
  probe-tourapi.mjs        # TourAPI 응답 품질을 확인하는 수동 점검 스크립트
```

## 로컬 실행

요구 사항: Node.js와 npm

```bash
npm install
npm run dev
```

브라우저에서 [http://localhost:3000](http://localhost:3000)을 엽니다.

## 환경변수와 TourAPI 점검

앱을 실행하는 데 API 키는 필요 없습니다. 다만 한국관광공사 TourAPI의 실제 응답을 조사하는 스크립트에는 서비스 키가 필요합니다.

1. 공공데이터포털에서 [한국관광공사 국문 관광정보 서비스_GW](https://www.data.go.kr/tcs/dss/selectApiDataDetailView.do?publicDataPk=15101578)를 활용 신청합니다.
2. `.env.local.example`을 `.env.local`로 복사합니다.
3. `TOUR_API_SERVICE_KEY`에 발급받은 서비스 키를 넣습니다. `.env.local`은 저장소에 커밋하지 않습니다.
4. 다음 명령으로 경주·공주·강릉의 관광지/문화시설과 축제 응답, 주소·좌표·운영정보 필드의 충족 여부를 확인합니다.

```bash
npm run check:tour-api
```

스크립트는 TourAPI v4.4의 법정동 코드(`lDongRegnCd`, `lDongSignguCd`)로 조회합니다. 서비스 키는 스크립트에서 URL 인코딩을 처리하므로 인코딩 키와 디코딩 키 모두 입력할 수 있습니다.

## 데이터 소스와 현재 사용 상태

| 데이터 | 현재 PoC | 실제 전환 후보 |
| --- | --- | --- |
| 목적지·관광지·운영시간·휴무·체류시간 | `lib/mock-data.ts` | 한국관광공사 TourAPI 및 필요한 보완 데이터 |
| 행사·축제 | 목업 기간 비교 | TourAPI 행사/축제 조회 |
| 지역 간 이동시간 | 지역별 고정 평균 시간 | 한국도로공사 평균/과거 통행 데이터 또는 필요 시 경로 서비스 |
| 관광지 간 이동시간 | 고정 30분 | 좌표 거리와 보정 모델, 필요 시 Routing API |
| 지역 대표음식·음식점 | 지역별 목업 문자열 | 지자체 공개데이터를 수집·정규화한 내부 데이터 |

권장하는 실제 데이터 구조는 사용자 요청마다 외부 API를 직접 호출하는 방식이 아니라, **공공 API → 주기적 수집 → 정규화 → 내부 데이터 레이어 → 서비스**입니다. 변경 빈도가 낮은 데이터는 일 단위 갱신하고, 장애 시 마지막 정상 데이터를 제공할 수 있어야 합니다. 초기에는 Next.js 서버 캐시 또는 DB 기반 갱신으로 시작하고 Redis는 필요해질 때 도입합니다.

## 현재 한계

- 지원 후보와 모든 세부 정보가 3개 지역의 목업에 한정됩니다.
- 출발지 선택은 서울·대전·부산 UI 옵션이지만, 목적지별 이동시간은 출발지별로 달라지지 않는 목업값입니다.
- 추천 점수와 7시간 최소 여유 기준은 PoC용 규칙이며, 사용자 검증을 거쳐 확정되지 않았습니다.
- 일정은 단순 순차 배치이며, 실제 도로 경로·식사·숙박·날짜별 예외 운영·데이터 품질을 최적화하지 않습니다.
- TourAPI 프로브는 데이터 품질을 조사할 뿐, 앱 데이터나 화면을 갱신하지 않습니다.

## 다음 개발 방향

1. TourAPI를 실제로 조사해 초기 지원 지역의 장소·운영시간·휴무·축제 데이터 품질을 확인합니다.
2. 외부 응답을 정규화하고 일 단위 캐시/갱신이 가능한 서버 측 데이터 계층을 만듭니다.
3. 최소 현지 체류시간, 데이터 결측 처리, 목적지 점수 기준을 제품 결정으로 확정합니다.
4. 평균 이동시간과 복귀 버퍼를 포함해 제약을 엄격히 검증하는 일정 생성 엔진으로 발전시킵니다.
5. 제한된 지역·자차 중심 MVP에서 목적지 선택률과 일정 생성 완료율로 핵심 가설을 검증합니다.

제품 배경, 조사 결과, 제약과 PM 계획 입력은 [docs/product/PROJECT_CONTEXT.md](docs/product/PROJECT_CONTEXT.md)를 참고하세요.
