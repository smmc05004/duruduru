# DURUDURU (두루두루)

사용자가 목적지를 먼저 정하지 않아도 되는 국내 여행 추천 서비스입니다. 출발지와 정확한 출발·복귀 시간, 이동수단, 관심사를 입력하면 **주어진 시간 안에 갈 수 있는 목적지부터** 추천하고, 선택한 지역의 일정을 만듭니다.

> 기존 여행 플래너가 “경주에 가는데 무엇을 할까?”를 돕는다면, DURUDURU는 “이번 주말 이 시간에 어디를 다녀올 수 있을까?”를 먼저 해결합니다.

## 현재 상태

화면 흐름 검증용 PoC는 첫 커밋으로 종료했고, 현재는 정식 서비스(MVP) 개발 단계입니다. 디자인 방향은 H(여행 수첩)로 확정됐습니다. 단계와 제품 결정의 기준은 [docs/product/DECISIONS.md](docs/product/DECISIONS.md)이며, 이 README는 코드의 세부 상태를 옮겨 적지 않습니다.

- 실제 공공 API를 사용자 흐름에 연결하지 않았습니다. 목적지·장소 데이터는 아직 목업입니다.
- 데이터베이스, 로그인, 여행 저장 기능은 없습니다.
- 스탬프, 방문 인증, 친구, 컬렉션, 랭킹은 현재 범위에 포함되지 않습니다.

### 승격하지 않는 PoC 값

PoC가 쓴 숫자와 목업 데이터는 검증되지 않은 임시값입니다. 다음은 정식 정책으로 승격하지 않습니다.

- 추천 통과 기준으로 쓰였던 `왕복 이동시간 + 7시간`
- 장소 사이의 고정 30분 이동시간과 목적지별 고정 평균 이동시간
- 목업 운영시간·휴무·권장 체류시간 값
- 대중교통 선택 UI와 그 목업 이동시간 — 초기 제품 방향에서 정식 지원 대상은 자차입니다

### 아직 결정되지 않은 정책

승인 전까지 코드에 상수로 굳히지 않습니다. 선택지는 [docs/product/DECISIONS.md](docs/product/DECISIONS.md) 2절에 있습니다.

- 최소 현지 체류시간과 복귀 버퍼 (`제안`)
- 운영시간·휴무·체류시간 결측 장소의 제외 또는 fallback (`제안`)
- 일정 재생성·장소 교체의 포함 범위 (`보류`)
- 식사 시간대·소요시간

## 주요 사용자 흐름

1. 출발지, 출발·복귀 일시, 이동수단, 관심사를 입력합니다.
2. 전체 가용시간에서 왕복 예상 이동시간과 복귀 버퍼를 뺀 시간으로 목적지 후보를 걸러 점수순으로 보여 줍니다.
3. 후보마다 추천 이유, 왕복 예상 이동시간, 현지 이용 가능 시간을 함께 표시합니다.
4. 후보를 선택하면 운영시간·휴무·체류시간·이동·식사와 복귀 조건을 반영한 일정을 확인합니다.
5. 여행 기간과 지역·관심사가 맞는 축제가 있으면 일정에 반영합니다.

이동시간은 실시간 정보가 아닌 평균·추정치이며, 결과에는 추정과 데이터 결측을 구분해 표시합니다.

## 기술 스택

- Next.js 16 (App Router), React 19, TypeScript 6
- TanStack Query, Axios, Zustand
- Tailwind CSS 4
- ESLint 9 + `eslint-config-next`
- Jest + React Testing Library, Playwright
- 별도 백엔드·DB 없음

## 프로젝트 구조

```text
app/                       # App Router 화면
lib/                       # 추천·일정 도메인 로직과 데이터
e2e/                       # Playwright 화면 점검
scripts/                   # 점검·작업 사이클 스크립트
docs/product/              # 제품 요구사항·결정·계획
docs/design/               # 디자인 방향과 토큰
docs/agent/                # 에이전트 공통 규칙

파일 단위 구성은 개발 중 바뀌므로 여기에 옮겨 적지 않습니다.

```

## 환경변수와 TourAPI 점검

앱을 실행하는 데 API 키는 필요 없습니다. 다만 한국관광공사 TourAPI의 실제 응답을 조사하는 스크립트에는 서비스 키가 필요합니다.

1. 공공데이터포털에서 [한국관광공사 국문 관광정보 서비스_GW](https://www.data.go.kr/tcs/dss/selectApiDataDetailView.do?publicDataPk=15101578)를 활용 신청합니다.
2. `.env.local.example`을 `.env.local`로 복사합니다.
3. `TOUR_API_SERVICE_KEY`에 발급받은 서비스 키를 넣습니다. `.env.local`은 저장소에 커밋하지 않습니다.
4. 다음 명령으로 경주·공주·강릉의 관광지/문화시설과 축제 응답, 주소·좌표·운영정보 필드의 충족 여부를 확인합니다.

```bash
npm run check:tour-api
```

스크립트는 TourAPI v4.4의 법정동 코드(`lDongRegnCd`, `lDongSignguCd`)로 조회합니다. 서비스 키는 스크립트에서 URL 인코딩을 처리하므로 인코딩 키와 디코딩 키 모두 입력할 수 있습니다.

## 데이터 소스와 전환 계획

| 데이터                               | 현재 (목업)           | 실제 전환 후보                                              |
| ------------------------------------ | --------------------- | ----------------------------------------------------------- |
| 목적지·관광지·운영시간·휴무·체류시간 | `lib/mock-data.ts`    | 한국관광공사 TourAPI 및 필요한 보완 데이터                  |
| 행사·축제                            | 목업 기간 비교        | TourAPI 행사/축제 조회                                      |
| 지역 간 이동시간                     | 지역별 고정 평균 시간 | 한국도로공사 평균/과거 통행 데이터 또는 필요 시 경로 서비스 |
| 관광지 간 이동시간                   | 고정 30분             | 좌표 거리와 보정 모델, 필요 시 Routing API                  |
| 지역 대표음식·음식점                 | 지역별 목업 문자열    | 지자체 공개데이터를 수집·정규화한 내부 데이터               |

권장하는 실제 데이터 구조는 사용자 요청마다 외부 API를 직접 호출하는 방식이 아니라, **공공 API → 주기적 수집 → 정규화 → 내부 데이터 레이어 → 서비스**입니다. 변경 빈도가 낮은 데이터는 일 단위 갱신하고, 장애 시 마지막 정상 데이터를 제공할 수 있어야 합니다. 초기에는 Next.js 서버 캐시 또는 DB 기반 갱신으로 시작하고 Redis는 필요해질 때 도입합니다.

## 현재 한계

- 지원 후보와 세부 정보가 소수 지역의 목업에 한정됩니다.
- 출발지별 실제 이동시간과 장소 간 실제 경로·이동시간을 계산하지 않습니다.
- 숙박, 날짜별 예외 운영, 실제 데이터 갱신은 아직 다루지 않습니다.
- TourAPI 프로브는 데이터 품질을 조사할 뿐, 앱 데이터나 화면을 갱신하지 않습니다.

## 다음 개발 방향

1. TourAPI를 실제로 조사해 초기 지원 지역의 장소·운영시간·휴무·축제 데이터 품질을 확인합니다.
2. 외부 응답을 정규화하고 일 단위 캐시/갱신이 가능한 서버 측 데이터 계층을 만듭니다.
3. 최소 현지 체류시간, 데이터 결측 처리, 목적지 점수 기준을 제품 결정으로 확정합니다.
4. 평균 이동시간과 복귀 버퍼를 포함해 제약을 엄격히 검증하는 일정 생성 엔진으로 발전시킵니다.
5. 제한된 지역·자차 중심 MVP에서 목적지 선택률과 일정 생성 완료율로 핵심 가설을 검증합니다.

제품 배경, 조사 결과, 제약과 PM 계획 입력은 [docs/product/PROJECT_CONTEXT.md](docs/product/PROJECT_CONTEXT.md)를 참고하세요.
