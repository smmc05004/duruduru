# 결과 화면 정보 위계 명세

> 상태: 구현 전 디자인 결정. 대상은 F-02·F-03·F-04·F-05의 추천 결과와 참고용 여행 계획 결과다.
>
> 목적: 계산에 사용한 데이터의 신뢰도는 숨기지 않되, 여행자가 목적지를 고르고 참고 계획을 읽는 흐름을 원본 수집 메타데이터가 방해하지 않게 한다. 제품의 참고 계획·추정값 고지 원칙은 `docs/product/PRD.md`와 `docs/product/FUNCTIONAL_SPEC.md`를 따른다.

## 1. 문제와 결정

현재 `components/CandidateCard.tsx`와 `app/page.tsx`는 TourAPI/OSRM의 원본 출처명, 수집 시각, 데이터·정책 버전, 재현 식별에 가까운 상태값을 결과 본문에 반복한다. 이 정보는 데이터 감사에는 필요하지만, 사용자가 답하려는 “갈 만한가 / 어떻게 둘러볼까”보다 먼저 읽히며 모바일에서 카드 길이를 크게 늘린다.

**결정:** 결과의 기본 레이어에는 선택 판단에 직접 필요한 시간·이유·불확실성만 보인다. 데이터의 제공자·수집·버전·원본 근거는 사용자가 여는 `데이터 기준 보기` 안에 묶는다. 원본 계약과 화면이 보존하는 provenance 필드는 삭제하지 않는다.

이것은 신뢰도 표시(F-05)를 줄이는 결정이 아니다. “일반 예상시간인지”, “확인되지 않은 운영 정보가 있는지”, “결측 때문에 결과를 만들 수 없는지”는 접기 전에도 명확하게 보인다. 기술적 이름과 감사 메타데이터만 기본 읽기 흐름에서 뺀다.

## 2. 정보 레이어

| 레이어 | 목적 | 기본 노출 내용 | 접힌 상세 내용 |
| --- | --- | --- | --- |
| 1. 여행 판단 | 후보를 고르고 계획을 읽는다 | 목적지/장소, 일반 예상 이동·방문 시간, 넓은 시간대, 관심사 일치, 선택 이유 | 없음 |
| 2. 주의·불확실성 | 확정 일정·실시간 정보로 오해하지 않는다 | 추정 상태, 기준일, 방문 전 운영·휴무·예약 확인 행동, 결측의 사용자 영향 | 없음 |
| 3. 데이터 기준 | 근거를 검토하거나 비교한다 | `데이터 기준 보기` 요약 버튼 | 제공자, 수집일, 데이터 상태, 데이터 기준일. 데이터/정책 버전과 재현 식별자는 필요 시 한 줄의 `수집 식별 정보`로만 표시 |

레이어 1과 2는 화면·보조기술 모두에서 레이어 3보다 먼저 읽힌다. `정상`은 별도 성공 메시지로 반복하지 않는다. `estimate`, `fallback`, `stale`, `missing`, `error`만 각각의 영향과 함께 알린다.

## 3. 추천 카드 명세

### 3.1 기본 노출 순서

1. 목적지명과 지역
2. 이동/체류 시간 막대와 `이동 2:55 · 머무는 시간 30시간 10분 · 이동 2:55`
3. 추천 이유: 기존 계산 결과 문장을 유지한다.
4. 관심사 태그
5. 계산 근거 두 줄: `시간 적합성 84% · 쓸 수 있는 시간 중 이동에 쓰이지 않은 비율`, `관심사 일치 1/1 · 고른 관심사 중 겹친 개수`
6. 이동시간 상태 고지 한 줄
7. `데이터 기준 보기` 접기
8. `강릉 일정 보기` 버튼

### 3.2 상태 고지의 정확한 문구

| 데이터 상태 | 기본 고지 문구 | 표현 |
| --- | --- | --- |
| `normal` | `이동시간은 도로 경로 데이터로 확인했어요. 기준일 YYYY.MM.DD` | 확인됨 아이콘 + `--olive-soft` |
| `estimate` | `이동시간은 도로 경로를 바탕으로 한 일반 예상치예요. 기준일 YYYY.MM.DD` | 추정 아이콘 + `--mustard-soft` |
| `fallback` | `이동시간은 대체 데이터예요. 출발 전 다시 확인해 주세요. 기준일 YYYY.MM.DD` | 시계 아이콘 + 점선 머스터드 |
| `stale` | `이동시간 기준일이 지났어요. 출발 전 다시 확인해 주세요. 기준일 YYYY.MM.DD` | 시계 아이콘 + 점선 머스터드 |
| `missing` | 후보를 표시하지 않는다. 기존 데이터 부족 결과에서 `이동시간 데이터를 준비하지 못해 추천할 수 없어요.`와 영향·다음 행동을 표시한다. | 결측 상태 화면 |

`정상`과 `estimate` 모두 실시간 교통·도착 보증이 아님을 결과 화면 상단의 한 번뿐인 공통 고지로 보완한다: **`일반 예상시간으로 만든 참고용 결과예요. 출발 전 최신 운영·휴무·예약 정보를 확인해 주세요.`** 이 문구를 각 카드에 반복하지 않는다.

### 3.3 데이터 기준 접기

`CandidateCard`에 `CandidateDataBasis`를 추가하고 네이티브 `<details>`/`<summary>`로 구현한다. 기본은 닫힘이다.

- 닫힌 요약: `데이터 기준 보기`
- 열린 제목: `이 추천에 사용한 데이터`
- 항목 표기(순서 고정):
  - `목적지 정보 · 한국관광공사 TourAPI · 수집일 YYYY.MM.DD · 확인됨`
  - `관심사 정보 · 한국관광공사 TourAPI · 수집일 YYYY.MM.DD · 확인됨`
  - `이동시간 · OpenStreetMap 도로 데이터 기반 일반 예상치 · 기준일 YYYY.MM.DD · 수집일 YYYY.MM.DD · 추정`
  - 필요한 경우에만 `수집 식별 정보 · 데이터 YYYY-MM-DD · 정책 YYYY-MM-DD`

`OSRM 공개 데모 서버`, 내부 메서드명, 원시 응답 경로, 좌표 provenance, 재현 ID는 사용자 기본 화면과 이 접기 안에도 직접 노출하지 않는다. 수집·감사 계약에는 그대로 유지하며, 운영자용 도구가 필요해질 때 별도 비사용자 화면에서 다룬다. 현재의 `source` 문자열이 기술 세부사항이면 위와 같은 사용자용 표현으로 매핑한다.

## 4. 참고용 여행 계획 명세

### 4.1 기본 노출 순서

1. 조건 요약 아래 공통 고지: `참고용 계획이에요. 일반 예상시간을 바탕으로 했으며, 방문 전 최신 운영·휴무·예약 정보를 확인해 주세요.`
2. 출발지 이동: `서울특별시에서 경주까지 일반 예상 4시간 10분`과 해당 상태 고지. `방식`, 제공자, 데이터/정책 버전은 노출하지 않는다.
3. 방문 순서별 카드: 순번·장소명·관심사 태그·`방문 약 N시간`·`넓은 시간대 YYYY.MM.DD HH:MM–HH:MM`·이전 장소에서의 `일반 예상 N분 이동`.
4. 운영 정보가 결측이면 장소별 원본 출처 대신 `운영 정보는 아직 확인하지 못했어요. 방문 전 확인해 주세요.`를 표시한다. 이는 오류가 아니라 참고 계획의 한계이므로 자적색을 쓰지 않는다.
5. 화면 하단의 단일 `계획 데이터 기준 보기` 접기. 각 장소에 동일한 원본 메타데이터를 반복하지 않는다.

방문시간이 `estimate`이면 `방문 약 N시간`을 유지하고, 바로 뒤에 `예상 시간` 배지를 붙인다. `missing`이면 해당 값을 만들어 내지 않고 `방문시간 정보 없음`을 표시한다. 장소 간 경로가 `missing`이면 `이동시간 정보 없음`과 함께 그 구간이 계획상 확정되지 않았음을 표시한다.

### 4.2 계획 데이터 기준 접기

`app/page.tsx`의 계획 결과 블록에서 `ItineraryDataBasis`를 분리한다.

- 닫힌 요약: `계획 데이터 기준 보기`
- 열린 제목: `이 계획에 사용한 데이터`
- 그룹 순서: `출발지 이동`, `방문 장소`, `장소 사이 이동`, `운영 정보`
- 각 그룹은 사람에게 읽히는 이름·상태·기준일·수집일만 표시한다. 예: `불국사 방문 정보 · 한국관광공사 TourAPI · 수집일 YYYY.MM.DD · 확인됨`.
- `관심사 증거` 원문은 사용자 기본 화면에 표시하지 않는다. 관심사 태그와 일치 개수만 표시하고, 원문 설명이 신뢰에 꼭 필요한 경우에만 이 접기에서 최대 한 줄로 보여 준다.

상단의 `itinerary.notices`는 기술 필드 목록으로 렌더링하지 않는다. 위 공통 고지와 상태별 문구로 중복을 제거한다. 엔진이 반환하는 각 notice는 사용자 문구로 매핑할 수 없으면 데이터 기준 접기로 보낸다.

## 5. 시각·접근성·모바일 규칙

- 기존 `docs/design/DESIGN_TOKENS.md`의 상태별 아이콘·색·테두리 규칙을 그대로 쓴다. 새 색 토큰은 만들지 않는다.
- 상태 고지는 카드 안에서 본문보다 작은 12px/600, 데이터 기준의 항목은 11px/500 `--ink-faint`로 쓴다. 기준일을 상태 고지에 함께 쓰므로 색만으로 상태를 전달하지 않는다.
- `<summary>`는 보조 버튼처럼 보이되, 최소 44px 터치 영역과 키보드 포커스 링을 가진다. `details[open]`은 아래꺾쇠 방향만 바꾸며 자동 스크롤·자동 열림을 하지 않는다.
- 스크린 리더에서 닫힌 요약은 `데이터 기준 보기, 접힘`으로 읽히고, 상태 고지는 아이콘과 독립된 텍스트를 갖는다. 동일한 수집일·상태가 목록에 반복되면 각 항목의 이름을 먼저 읽게 한다.
- 390px 폭에서 `기준일`은 상태 고지와 한 줄에 강제하지 않는다. 줄바꿈돼도 시간 막대·주요 CTA보다 아래에 두며, 긴 출처명은 단어 중간을 자르지 않는다.
- 데이터 기준을 열어도 CTA가 화면 밖으로 밀리지 않게, 카드 내부 접기 아래가 아니라 CTA 뒤 또는 카드 하단에 배치한다. 추천 카드의 첫 화면에는 항상 목적지·시간·이유·CTA가 함께 들어와야 한다.

## 6. 구현 범위와 수용 기준

### 변경 대상

- `components/CandidateCard.tsx`: 기존 `DataEvidence`의 본문 반복을 `CandidateDataBasis`와 상태 고지로 교체한다.
- `app/page.tsx`: 참고 계획의 원본 근거 문단을 사용자용 요약·`ItineraryDataBasis`로 교체한다.
- `app/globals.css`: 기존 토큰만 사용해 접기, 포커스, 상태 고지의 레이아웃을 추가한다.
- `components/__tests__/CandidateCard.test.tsx`, `app/__tests__/page.test.tsx`: 기본/열린 상태, 상태 문구, 원본 기술문구 비노출, 키보드 접근성을 검증한다.
- Playwright: 추천 결과와 참고 계획 결과에서 기본 화면에 핵심 정보·CTA가 보이고, `데이터 기준 보기`를 열어야 세부 출처가 나타나는 흐름을 검증한다.

### 수용 기준

1. 추천 카드의 첫 화면에서 목적지명, 왕복 이동/현지 체류 시간, 추천 이유, 관심사 근거, 이동시간의 추정 여부와 기준일, 일정 보기 CTA를 확인할 수 있다.
2. 기본 화면에는 `OSRM`, 데이터 버전, 정책 버전, 재현 식별자, 원시 관심사 증거가 보이지 않는다.
3. `데이터 기준 보기`를 열면 목적지·관심사·이동시간의 제공자, 수집일, 상태, 이동시간 기준일을 확인할 수 있다.
4. 참고 계획은 방문 순서·넓은 시간대·일반 예상 이동/방문 시간·운영 정보 결측의 사용자 행동을 기본으로 보이며, 기술 메타데이터는 단일 접기에만 있다.
5. `estimate`·`fallback`·`stale`·`missing`은 아이콘·테두리·텍스트를 함께 사용하고, 결측을 임의 시간으로 대체하지 않는다.
6. 접기는 마우스·터치·키보드로 동작하며 390px 폭에서도 터치 영역과 텍스트 대비를 지킨다.

## 7. 제외 범위

- 데이터 계약, 정적 경로 수집, 추천·일정 산식, 수집 제공자 변경
- 실시간 교통·주소 지오코딩·지도·예약·운영자용 데이터 감사 화면
- 결과 내용의 사실성 판정. 이번 변경은 이미 반환된 상태와 근거의 표시 위계만 바꾼다.
