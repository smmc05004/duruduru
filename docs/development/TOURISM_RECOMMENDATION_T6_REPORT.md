## 6. 미해소 항목 · 제품 규칙 변경 제안 (임의 튜닝하지 않음)

### 6.1 `interest` 역할이 원거리로 쏠린다 (수용 기준 5 "개선되지 않은 경우")

**현상**: `interest` 후보 왕복시간 중앙값이 62분 → 358분. 34/48셀이 편도 2시간 이상. 야간 출발 셀에서는 특히 나쁘다(예: 서울 → 경주 왕복 396분·현지자유 257분, 부산 → 정선 왕복 430분·현지자유 240분).

**원인**: D4 정렬 키가 `충족 관심사 수 → 목적 근거 점수 → 세부 분류 다양성 → 실제 관광 수 → 왕복시간` 순이다. 목적 점수가 왕복시간보다 우선이라, 단일 관심사 검색처럼 다수 지역이 관심사를 충족하면 목적 점수가 사실상 결정한다. 목적 점수는 초안에 배치된 6곳이 각각 낮은 hubRank(1~~10)에 연결되면 최대이므로, **중심 관광지 자료가 조밀한 지역**(대도시, 또는 관광 밀집 시·군)이 구조적으로 유리하다. 광역시 그룹은 소속 구 전체의 중심 관광지를 모아 초안이 낮은 hubRank 6곳을 고르므로 목적 점수 0.75~~0.83에 이르는 반면, 단일 시·군은 대개 0.3~0.5다. D4가 경계한 "하위 구 순위 1위의 무제한 합산"이 원천 합산이 아니라 **초안 선정 경로로** 재현된다.

**완화 요소**: 근거리 후보는 `easy`·`relaxed`로 항상 노출되어 사용자가 3장 중 고를 수 있다. "관심사를 깊게 즐기는 여행" 카드가 원거리라는 해석도 가능하다.

**제품 규칙 변경 후보(택1 또는 조합, PM 결정 필요)**:

1. **왕복시간 밴드 안에서만 목적 점수로 정렬**: 최소 가용 왕복시간의 일정 배수(예: 1.5배) 또는 절대 상한 안의 후보만 목적 점수로 비교하고, 밴드를 넘으면 감점.

### 6.7 3라운드 리뷰 후속 수정 (2026-09-10, 같은 PR)

수집 재개 기능의 결함 2건을 같은 브랜치에서 추가로 고쳤다. **추천 정책·가중치·역할 순서·목적 점수 공식은 불변이고, 변경 범위는 전부 `scripts/`(수집기)라 `lib/` 수정이 없다 → T6 48셀 비교 매트릭스는 구성상 영향 없음.**

- **결함 1 — 페이지 검증에 필수 식별자 유효성 포함.** 기존 페이지 완료 판정이 응답 배열 **길이만** 봐서, `totalCount=2`에 `[{contentId:"a"}, {}]`처럼 식별자가 빈 항목이 섞여도 `complete`로 저장됐다. 그 페이지가 체크포인트 `pages`에 남아 `--resume` 해도 재조회 없이 최종 `validateDocument` 실패가 무한 반복됐다. `scripts/lib/paged-collection.mjs`에 공유 함수 `hasRequiredId`/`pageItemsAllHaveId`를 두고, 페이지 완료 판정을 `isPageValidated`(항목 수 + 모든 항목의 필수 식별자)로 바꿨다. 필수 식별자는 프로필 = `contentId`, 중심 = `hubTatsCd`이며 두 수집기가 이미 넘기는 `idOf`를 그대로 쓴다(중복 로직 없음). 식별자 누락 페이지는 체크포인트에서 빠지고 스펙/지역 `done`도 false다. 오래된 체크포인트에 `complete`로 저장돼 있어도 seed 단계에서 배제해 재조회한다. `validateDocument`도 같은 함수로 항목 식별자 결측을 교체 차단 사유에 추가한다.
- **결함 2 — 검증된 페이지마다 체크포인트 영속 저장.** 체크포인트가 스펙/지역 종료·예외 시점에만 저장돼, 페이지 2 검증 후 프로세스가 죽으면 디스크에 아무것도 안 남았다. `collectPagedUnit`에 `onProgress` 훅을 두어 **정상 페이지 검증 직후**와 **일관성 붕괴로 단위를 재시작할 때(폐기 목록 `{}`)** 즉시 호출하고, 두 수집기 CLI가 이 훅에서 실제 체크포인트 파일(`data/region-profiles.checkpoint.json`, `data/central-attractions.checkpoint.json`)에 flush 한다. 뒤에 더 받을 페이지가 있을 때만 저장해 단일 페이지 수집(중심 API의 일반적 경우)의 쓰기 폭증을 피한다. 재시작 시 폐기는 재수집을 시작하기 **전에** 디스크에 반영된다.

## 8. T7-6 결과 — 세부 유형 중복 계산 결함 수정 (2026-09-11, 같은 PR)

> 사용자가 지정한 결함과 수정 규칙을 그대로 구현했다. T7 목적 적합성 지표 계산의 버그 수정이며, 추천 전략(근거리/원거리 우선순위) 변경은 이번 범위가 아니다.

### 8.1 결함

`lib/tourism-evidence.ts`의 `computePurposeEvidence`에서 관심사별 `facilities_i`(서로 다른 시설 수)는 `facilityGroups`(E2)로 중복 제거했지만, `types_i`(서로 다른 세부 유형 수)는 그 그룹화 전 `relevantPlaced` 전체 장소에서 계산했다. 그 결과 같은 시설의 세부 항목(예: 서로 다른 `lclsSystm3`를 가진 하위 장소)을 추가하는 것만으로 `facilities_i`는 그대로인데 `types_i`가 올라 `fit_i`와 `fitBand`가 부풀 수 있었다.

### 8.2 수정 규칙

- 요청 관심사별로 관련 장소를 기존 `facilityGroups` 기준으로 묶는다.
- **하나의 시설 그룹은 해당 관심사의 세부 유형에 최대 하나만 기여**한다.
- 그룹 내 **대표 유형**은 유효한 세부 분류(`detailClassificationStrict`, D1 새 분류 우선·구 분류 fallback)가 있는 장소 중 **안정적인 콘텐츠 ID 오름차순**으로 고른다.
- **유효 분류가 없는 그룹**은 시설 수에는 포함하되 유형 수에는 포함하지 않는다.
- 그룹별 대표 유형을 **다시 중복 제거**해 `types_i`를 만든다.
- 중심 연결 근거(`matchedFacilityCount`)의 시설 중복 제거는 그대로 유지한다(이 수정과 무관).

상수(`facilityCap=4`, `typeCap=3`, `bandBoundaries=[4.5, 6.5]`)와 정렬 순서(충족 관심사 → 적합성 구간 → 왕복시간 → 보조 근거 → 안정 ID)는 변경하지 않았다. 근거리 쏠림을 해결하기 위한 상수 조정, 거리 가점·하한, 추가 입력은 도입하지 않았다 — 이는 별도 제품 판단이 필요한 범위 밖 사안이다. 문서 반영: 제품 [D4-a](../product/TOURISM_RECOMMENDATION_UPGRADE.md#d4-a--확정-상수-t7-1-2026-09-10).

### 8.3 TDD — 결함 재현 실패 테스트 → 수정

`lib/__tests__/enhancement-tourism-evidence.test.ts`에 먼저 실패 테스트를 추가해 결함을 재현했다(같은 주소·좌표·공유 제목 토큰으로 하나의 시설 그룹을 만들고 서로 다른 `lclsSystm3`를 가진 두 장소를 배치): 수정 전 `{facilities: 1, types: 2, fit: 3}` → 수정 후 기대값 `{facilities: 1, types: 1, fit: 2}`. 수정 전 실행에서 두 신규 케이스가 실제로 실패함을 확인한 뒤 구현을 고쳐 통과시켰다.
