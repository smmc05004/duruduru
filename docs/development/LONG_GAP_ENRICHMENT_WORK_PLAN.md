# 긴 여유시간 보완 작업 계획

> 상태: LG-0~LG-8 구현 및 총괄 직접 기능 점검 완료 · 기준일: 2026-09-14 · 브랜치: `feat/long-gap-enrichment` · 커밋/PR 미생성
>
> 제품 기준은 [긴 여유시간 보완 기획](../product/LONG_GAP_ENRICHMENT.md)이다. 아래 계획에 따라 구현했고 실제 검증 결과는 마지막 절에 기록한다. 목적지 검색 정책은 R3 확정 역할(`nearby`/`overnight`/`interestRich`)과 검색 알고리즘 `e1-v4`, 초안 관광 선정 `e2-v3`를 유지한다.

## 1. 목표와 유지 범위

긴 여유시간 보완은 목적지를 선택한 뒤 만들어진 선택 계획에서 07:00~21:00 낮 구간의 연속 순수 `free`가 120분을 초과할 때만 적용한다. 같은 끼니·개인 일정·고정 시각·지역 간 이동·야간 휴식 경계 안에서 기존 관광 재배치를 먼저 시도하고, 그래도 개선이 남으면 선택 권역의 미사용 관광 후보 중 관심사·중복·좌표·5km 근접 조건을 만족하는 60분 관광을 추가한다.

다음은 유지한다.

- 검색 후보 초안, R3 목적지 역할, `overnight`/`interestRich`의 현지 자유시간 240분 조건, 검색 카드의 근거 수치.
- 검색 초안의 하루 관광 3곳·전체 6곳. 긴 여유 보완이 적용된 선택 계획만 하루 4곳·전체 8곳까지 허용한다.
- 음식점 최초 조회 최대 3지역·9회·동시성 2, 관광 자동 상세 최대 6개·원천 12회 예산.
- E4 일반 편집의 식사·개인 일정·고정 시각·저장 복원 보존 원칙.
- 새 API, 새 관광 목록 조회, 새 데이터 원천, 실시간 경로, 운영시간 자동 판정 없음.

보완의 성공은 자유시간을 숨기거나 이름만 바꾸는 것이 아니라 실제 관광 시각 조정 또는 새 관광 추가가 있어야 한다. 실패·무변경은 기존 계획, 식당, 저장 상태, 메모, 고정 상태를 그대로 반환한다.

## 3. 데이터·버전 계약

구현 시 `PlanSnapshot`에는 **실제 보완 성공 결과에만** 선택 계획 전용 보완 메타데이터를 추가한다. 필드명은 구현 중 타입에 맞춰 확정하되 아래 의미를 지켜야 한다. 무변경·실패·stale 결과는 `PlanSnapshot`에 version/status를 덧붙이지 않고 결과 객체와 UI 상태로만 전달한다.

| 계약                                      | 의미                                                                                                                                                                                      |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `longGapEnrichmentVersion: "long-gap-v1"` | 긴 여유 보완 규칙 버전. 검색 `algorithmVersion`이나 `itineraryAlgorithmVersion`을 대체하지 않는다.                                                                                        |
| `longGapEnrichmentSummary`                | 성공한 경우의 추가 관광 수, 재배치 여부, 처리한 대상 구간, 남은 긴 여유, before/after 지표를 저장 가능한 최소 구조로 보존. 실패 사유는 저장 plan이 아니라 실행 결과와 UI 상태로 전달한다. |
| 선택 계획 한도                            | `long-gap-v1`이 적용된 현재 계획은 하루 관광 4곳·전체 8곳까지 검증한다. 구 저장본과 검색 초안은 기존 3/6 한도를 유지한다.                                                                 |

기존 `Candidate.preview`와 검색 카드의 자유시간·관광 수는 검색 시점 초안으로 보존한다. 보완 후 화면에 표시하는 자유시간·관광 수는 `PlanSnapshot.metrics`와 보완 summary의 선택 계획 지표에서만 읽는다.

## 5. 보완 알고리즘 세부 계약

### 5.1 대상 구간과 검증

- 대상 free는 순수 `free` 블록만 본다. 현지 이동 travel, 미확정 이동 15분, 식사, 관광, 개인 일정, 운전, 휴식은 free가 아니다.
- 처리 시작 시 원래 대상 구간 `{day, startAt, endAt, duration}`을 보존한다.
- 보완 후 각 원래 대상 구간 안에는 연속 순수 free 60분 이상이 남아야 한다. 30분+30분은 실패다.
- 보완한 날의 최종 순수 free 합도 최소 60분이어야 한다. 대상이 없는 날은 기존 활동일 최소 30분 정책을 유지한다.
- 인접 free는 판정 전에 합친다. 표시상 쪼개기나 명칭 변경은 개선으로 세지 않는다.

### 5.2 기존 관광 재배치

재배치 탐색은 같은 날짜 안에서 끼니, 지역 간 이동, 휴식, 개인 일정, `fixedStartAt` 관광을 경계로 나눈 구간 단위로 수행한다. `fixed` 장소 유지 관광은 콘텐츠 선택 보존이며 시각 고정이 아니므로 같은 구간 안에서 움직일 수 있다. 개인 일정은 시각 고정 여부와 관계없이 ID·시각·내용을 모두 보존한다.

후보 선택 기준은 다음 순서다.

1. 그날의 `sum(max(0, freeBlockMinutes - 120))` 감소.
2. 동률이면 그날의 `maxFreeBlockMinutes` 감소.
3. 동률이면 시작 시각이 바뀐 기존 관광 수 최소.
4. 동률이면 시작 시각 변동 절대 분 합 최소.
5. 동률이면 최종 시작 시각 배열, 콘텐츠 ID 순.

두 지표가 모두 그대로면 성공으로 채택하지 않는다. 한 구간의 긴 여유를 다른 구간으로 옮겨 새 긴 여유를 만들고 성공 표시하지 않는다.

### 5.3 관광 추가

재배치 후에도 대상이 남으면 선택 권역의 `plan.destination.attractions`에서만 후보를 검토한다.

- 요청 관심사 중 하나 이상에 공식 분류로 해당해야 한다.
- 여행 전체 미사용 콘텐츠 ID여야 한다.
- 동일 콘텐츠, 강한 중복, 확인된 동일 시설, 시설 의심 묶음이 기존 방문과 겹치면 제외한다. 보완에서는 동일 시설 예외로 채우지 않는다.
- 새 관광 좌표가 있어야 하고, 삽입 바로 앞 또는 뒤의 같은 날 실제 관광·식당 중 유효 좌표가 있는 장소와 직선거리 5km 이내여야 한다.
- 앞→새 관광→뒤 연결을 `straight-line-v1`으로 다시 계산하고 기존 앞→뒤 연결은 제거한다. 비교 가능한 이웃이 없거나 좌표가 없으면 자동 추가 후보에서 제외한다.
- 추가 관광은 60분 고정이다.
- 후보 정렬은 추가되는 현지 이동 예약 분 오름차순 → 당일 미사용 세부 유형 있음 → 콘텐츠 ID 순이다. 변경 연결이 모두 추정 가능한 후보를 결측 후보보다 우선한다.
- 하루 4곳·전체 8곳 슬롯 안에서만 시도한다.

탐색은 날짜 오름차순, 해당 날짜 대상 구간은 길이 내림차순·시작 시각 오름차순으로 수행한다. 한 실행에서 같은 콘텐츠 ID와 같은 배치안을 반복하지 않는다. 구현 상한은 시간 후보 최대 96개, 관광 후보 최대 80개, 전체 평가 최대 2,000회, 반복 라운드 최대 8회로 시작한다. 상한에 닿으면 현재까지 검증된 최고 개선만 적용하거나 원본을 유지하고, 성능 측정값을 검증 로그에 남긴다.

## 6. 비동기·상태 전환

자동 보완은 최초 음식점 처리 종료 후 한 번만 실행한다.

1. `choose(candidate)`는 기존처럼 후보 preview로 계획을 즉시 표시하고 음식점 요청을 시작한다.
2. `choose`/최초 식당 요청 시작 시점에 `planId`와 edit generation을 캡처한 자동 보완 토큰을 만든다. 이 값이 기준 토큰이다.
3. 음식점 요청 성공·부분 성공·실패가 종료되면 기준 토큰을 현재 plan의 `id`와 edit generation에 대조한다.
4. 토큰이 그대로이면 식당 배정 결과와 자동 보완을 같은 최신 계획 흐름에 적용한다. 보완은 토큰이 확인된 계획 복사본에서 순수 함수로 계산한다.
5. 적용 직전에도 같은 토큰을 다시 확인하고 원자 적용한다.
6. 사용자가 편집, 저장, 복원, 다른 목적지 선택, 조건 변경을 했다면 토큰을 무효화하고 결과를 폐기해 화면을 덮어쓰지 않는다.

명시 버튼은 저장본 복원·편집 후 현재 계획에 사용자가 직접 실행할 때만 동작한다. 버튼 실행은 외부 관광/음식 API를 호출하지 않는다. 성공해도 사용자가 `이 기기에 저장`을 누르기 전에는 저장 원본을 바꾸지 않는다.

## 10. 성능과 bounded 탐색

- 보완 입력은 현재 선택 계획의 활동 수가 작다. 기본 관광 6곳, 보완 후 최대 8곳, 개인 일정 최대 4개, 후보 풀은 선택 권역 attractions 배열이다.
- 탐색은 날짜·대상 구간·후보 콘텐츠 ID·삽입 위치의 유한 조합만 본다. 같은 콘텐츠 ID와 같은 배치안은 한 실행에서 한 번만 평가한다.
- 기술 상한은 시간 후보 최대 96개, 관광 후보 최대 80개, 전체 후보 평가 최대 2,000회, 반복 라운드 최대 8회다. 구현 중 실제 측정으로 조정이 필요하면 제품 의미를 바꾸지 않는 선에서 이 문서를 갱신하고 근거를 남긴다.
- 재배치 후보는 같은 경계 구간 안 활동만 대상으로 하며 고정 경계를 넘어 전역 최적화하지 않는다.
- 모든 후보 평가는 복사본에서 수행하고 최종 시간·연결·한도·free 보존 검증을 통과한 결과만 적용한다.
- 정렬은 거리 분, 관심사/세부 유형, 콘텐츠 ID 등 결정적 키만 사용한다. 원천 배열 순서, 조회 시각, 무작위는 선택 근거로 쓰지 않는다.
- LG-8에서 `performance.now()` 또는 테스트 환경의 동등한 측정으로 합성 150분, 서울·역사 고양/문경/순창, 후보 상한 fixture의 실행 시간과 평가 횟수를 기록한다.
