# 정적 이동시간 수집 매니페스트

## 상태

2026-09-03 기준 계약과 수집 대상만 준비됐다. 실제 도로 경로 거리·일반 예상시간은 아직 한 건도 넣지 않았다. 이 문서는 런타임 경로 API나 실시간 교통을 도입하지 않고, 사전 수집값을 재현 가능하게 기록하는 절차다.

## 적용 범위

- F-02: 서울특별시·대전광역시·부산광역시에서 경주·공주·강릉까지 자차 일반 편도 이동시간 3×3
- F-04: 실제 수집·정규화된 동일 목적지의 장소↔장소, 장소↔대표음식 음식점 자차 경로

대표음식 확정, TourAPI 장소·음식점 수집, 운영시간 판정은 이 매니페스트의 선행 입력이며 이 문서에서 수행하지 않는다.

## 현재 수집 대상

| 출발지       | 목적지                       |
| ------------ | ---------------------------- |
| 서울특별시청 | 경주시청, 공주시청, 강릉시청 |
| 대전광역시청 | 경주시청, 공주시청, 강릉시청 |
| 부산광역시청 | 경주시청, 공주시청, 강릉시청 |

ID·기준점은 [support-conditions.ts](/Users/seokhwa/dev/duruduru/lib/support-conditions.ts)의 승인된 지원 조건을 단일 기준으로 사용한다. 장소 쌍은 실제 장소/음식점 ID와 좌표가 정규화된 뒤에 필요한 쌍만 추가한다.

## 레코드 입력 조건

`static-travel-time-data.ts`의 정적 레코드는 아래 모든 항목이 있을 때만 추가한다.

| 필드        | 요구사항                                                                                         |
| ----------- | ------------------------------------------------------------------------------------------------ |
| 거리·시간   | 도로 경로 거리(km)와 일반 예상시간(hours)을 함께 기록한다. 0·음수·임의 기본값은 허용하지 않는다. |
| 상태        | 실시간값이 아닌 `estimate`만 사용한다.                                                           |
| 출처        | 제공자/공개 데이터셋 또는 허가된 사전 수집 방법을 사람이 이해할 수 있게 적는다.                  |
| 기준일      | 조회·내보내기 기준일을 `YYYY-MM-DD`로 기록한다.                                                  |
| 정책 버전   | 수집 시점의 정적 이동시간 정책 버전을 기록한다.                                                  |
| 재현 식별자 | 서비스키 없이도 같은 수집 요청·내보내기·보관물을 추적할 수 있는 ID를 기록한다.                   |

수집 전에 확인할 항목은 제공자의 데이터 이용 조건, 사전 저장·표시 허용 범위, 도로 경로와 차량 모드 지정 가능 여부, 일반 예상시간 산출 기준, 좌표/경유지 및 조회일 보존 방법이다. 이 중 하나라도 확인되지 않으면 값을 쓰지 않는다.

## 금지와 결측 처리

- 서비스 런타임에서 경로 API·지도 UI·실시간 교통을 호출하지 않는다.
- 지도 UI를 자동화·스크래핑하거나 PoC의 고정 30분을 재사용하지 않는다.
- 소스·기준일·재현 식별자 없이 숫자만 입력하지 않는다.
- 수집되지 않은 3×3 또는 POI 쌍은 `null` 조회로 남긴다. 결측을 후보 0개나 임의 추정값으로 바꾸지 않는다.

## 다음 입력

실제 값을 수집하려면 아래 중 하나가 필요하다.

1. 사전 저장과 제품 표시가 허용되는 지도/경로 제공자 또는 공개 데이터셋의 선택과 이용 조건 근거
2. 선택한 제공자의 재현 가능한 수집 절차(출발·도착 기준점, 차량 모드, 일반시간 기준, 조회·내보내기 일자)
3. E6 장소·음식점 데이터 정규화 후 필요한 POI 쌍 목록

입력 확보 후에도 각 레코드는 코드 리뷰와 계약 검증을 거쳐야 하며, 정적 데이터가 준비됐다고 해서 실시간 정확성을 보장하지 않는다.
