# MVP 구현 계획

> 상태: 사용자 검토용 초안 / 기준일: 2026-09-05
>
> 이 문서는 현재 MVP 기능을 구현하기 위한 순서와 완료 조건을 정리한다. 코드리뷰, 작업 사이클, 자동 테스트·빌드·화면 점검 절차는 이 계획의 범위에서 제외한다.

## 1. 구현 목표와 고정 범위

완료 목표는 사용자가 고정된 서울특별시 출발, 자차·출발/복귀 일시·관심사를 입력해 `갈 수 있는 곳 찾기`를 누르면 전국 목적지 후보 중 최종 3곳을 받고, 하나를 선택해 1박 2일(1일차 08:00 출발, 2일차 20:00 복귀) 날짜별 계획을 보는 것이다. MVP는 1박 2일만 허용하며 당일치기·2박 이상은 요청 검증에서 거절한다. 경주·공주·강릉은 초기 예시·검증 지역이며 지원 목적지의 전부가 아니다.

고정 규칙은 다음과 같다.

- TourAPI 공식 분류 콘텐츠로 하루 1회 JSON 지역 프로필 인덱스를 만들고, 검색은 이 인덱스와 서울 중구 존 출발→전국 252존 시간 필터를 사용한다. 검색 단계에서는 음식점 API를 호출하지 않는다. 사용자가 목적지를 선택한 뒤 선택 지역 한 곳의 음식점 목록 기본 정보만 제한 동시성·페이지네이션으로 연결한다.
- 이동시간은 국가교통DB(KTDB) 2024 도로 네트워크에서 252존 중심 노드 간 승용차 기본 링크 비용으로 사전 산출한 일반 예상시간만 사용한다. 실시간·시간대별 혼잡·내비게이션 시간은 쓰지 않으며, 사용자 검색 중 경로 API를 호출하지 않는다.
- 관광지↔관광지와 관광지↔음식점의 이동시간은 계산·표시·선정·제약에 쓰지 않는다.
- 관광지와 음식점 체류시간은 각각 1시간이다.
- 매일 21:00~다음날 07:00은 휴식이며 관광·식사 배치를 금지한다.
- 점심(11:30~~13:30)과 저녁(17:30~~19:30)은 반드시 한 시간씩 배치한다. 음식점은 TourAPI 목록 기본 정보를 사용하며, 실제 운영시간·메뉴는 사용자가 상세를 열 때 확인한다.
- 엔진은 규칙 기반이고 LLM, 평점·리뷰·랭킹, 도로 경로 API, 실시간 교통, 내비게이션은 사용하지 않는다.

## 3. 현재 정적 구현의 교체·삭제 대상

다음은 새 MVP의 데이터 원천이나 계산 근거로 더 이상 사용하지 않는다.

- `lib/static-travel-time-data.ts`의 OSRM 청사 3×3 값과 관광지·음식점 내부 경로 매니페스트
- `lib/route-collection.ts` 및 OSRM/OSM 수동 수집 provenance
- `lib/reference-itinerary-data.ts`의 최소 장소 앵커와 장소 간 경로값
- `lib/recommendation-data-adapter.ts`가 정적 데이터만 읽어 후보를 만드는 경로
- `lib/support-conditions.ts`의 고정 3개 출발지·목적지 지원 목록과 이를 전제한 입력 UI·테스트 fixture. 서울 출발지는 하나의 고정 값으로 교체하고, 목적지만 전국 252존·TourAPI 법정동 매핑으로 확장한다.
- 기존 역사·자연·문화·미식 임의 태그와, 이를 임의 태그에 결합하던 어댑터 구현. 대표음식·지역N문화·모범음식점 원천 자체와 선택 후 식사 우선순위는 유지한다.
- `lib/reference-itinerary.ts`·`lib/planner.ts`의 장소 간 이동시간, 방문시간 결측 카드, 식사 직접 확인 fallback
- 결과 화면의 OSRM·정적 경로·내부 장소 이동 근거 표시

KTDB 지역 간 자동차 시간으로 서울 출발→전국 252개 지역권을 후보 판정한 뒤, OSRM 청사 3×3 값·내부 경로 정적 데이터와 수집 코드는 삭제한다. 현재 코드의 고정 3개 출발지·목적지 구현은 문서 기준선과 불일치하므로 서울 중구 존 고정 출발·전국 KTDB 목적지 존·TourAPI 법정동 매핑으로 교체한다. 향후 출발지 확장을 막지 않도록 데이터 계약의 출발/도착 지역 ID는 분리해 유지한다. PoC 고정 이동시간, 장소 간 고정 30분, 정적 음식점 fallback은 새 구현에 이관하지 않는다.

## 4. API와 환경변수 의존성

| ------------------------------------ | -------------------------------------------- | ------------------------------------------- | -------------------------------------------------------------------------- |
| TourAPI KorService2                  | 공식 분류 관광지 지역 프로필                 | 하루 1회 정기 수집 작업                     | `TOUR_API_SERVICE_KEY`; 서버 전용                                          |

TourAPI 키와 모범음식점 API 키는 현재 개발 환경에 존재한다. 지역N문화 원본은 2023년 12월 향토음식 문화 자료이므로 직접 식당 추천 원천이 아니라 보조 키워드로만 정규화한다. 모범음식점 API는 페이지 단위·제한 동시성으로 인증 캐시를 만들며, 두 원천의 수집 실패는 지역 프로필·목적지 후보 필터를 막지 않고 해당 가점만 생략한다.

## 5. 최종 완료 조건

다음이 모두 성립하면 MVP 핵심 흐름 구현을 완료로 판단한다.

1. 검색 클릭 한 번으로 고정된 서울 중구 존에서 전국 252개 지역권까지의 KTDB 시간 필터와 후보 검색 스냅샷 생성이 시작된다.
2. 출발지는 서울특별시로 고정 표시되며 선택·검색 입력이 없다. TourAPI 법정동 코드와 KTDB 존의 전국 **목적지** 매핑이 동작한다.
3. TourAPI 공식 분류 콘텐츠 수·ID·수집일의 하루 1회 지역 프로필 인덱스를 사용한다. 매핑 가능·선택 카테고리의 서로 다른 콘텐츠 ID가 3개 이상인 시간 적합 후보를 정렬해 음식점 정보 없이 최종 3곳을 보여 준다.
4. 1일차 08:00 출발·21:00 휴식 시작, 2일차 07:00 재개·20:00 복귀의 날짜별 시간표가 생성된다.
5. 관광지·음식점은 1시간씩만 배치되고, 내부 이동시간·도로 경로·실시간 교통 정보는 어디에도 쓰거나 표시하지 않는다.
6. 목적지 선택 뒤 선택 지역 한 곳의 음식점 목록만 조회해 점심·저녁을 구성한다. 목록을 불러오는 동안 진행 상태를 보이고, 목록 수집 실패는 목적지 후보를 소급 제외하지 않으며 식사 정보 재시도 상태로 보인다. 음식점 상세는 사용자가 클릭할 때만 서버에서 조회하며, 운영시간·메뉴·휴무 결측 또는 상세 실패는 일정 후보를 소급 제외하지 않고 해당 음식점의 확인 필요/재시도 상태로 보인다.
7. 데이터/API 부족은 정직한 재시도 또는 계획 생성 불가 상태로 보이며, 오래된 정적 값·PoC 값·임의 fallback으로 대체되지 않는다.

## 6. 로컬 준비 순서

로컬에서 새 MVP 검색 흐름을 확인하기 전에는 아래 준비를 한 번 수행한다. GitHub Actions 정기 실행은 로컬 확인에 필요하지 않다.

1. `npm run build:region-mapping`으로 KTDB 252존과 TourAPI 법정동 코드의 목적지 매핑 JSON을 생성하고, `review` 목록을 확인한다. 1:1 행정명 변경(강원·전북·전남광주통합특별시·세종)은 명시적 별칭으로 대조한다. 인천의 기존 중구·동구·서구처럼 경계가 분할되어 자동 대조가 모호하거나 일치하지 않는 지역은 프로필 수집·추천 대상에 넣지 않는다.
2. 검토를 통과한 매핑으로 `npm run build:region-profiles`를 실행해 TourAPI 공식 분류 관광지 지역 프로필 JSON을 생성한다. 이 수집은 지역별 반복 호출 대신 전국 카테고리 목록을 페이지 단위로 받은 뒤 법정동 코드로 매핑된 지역에 분류한다. 문화는 `A0206` 또는 콘텐츠유형 `14`, 레저는 `A03` 또는 콘텐츠유형 `28`을 모두 수집한다. 개발 계정의 일일 호출 한도를 넘기지 않도록 기본 900회 안전 한도를 적용하며, 한도를 넘길 것으로 판단되면 부분 JSON을 저장하지 않고 실패한다.

현재 생성본은 2026-09-07 KST 기준 249개 지역·11,764개 관광지이며, TourAPI 요청 19회로 생성됐다. 카테고리별 3개 이상 근거가 있는 지역은 자연 161개, 역사 195개, 휴양 140개, 문화 234개, 레저 217개다. 3. 확보한 지역N문화 원본에서 향토음식 문화 키워드만 정규화한다. 관련 음식점 필드는 버린다. 4. `EXCELLENT_RESTAURANT_API_SERVICE_KEY`로 모범음식점 정보를 수집해 인증 캐시를 생성한다.

1~~2는 목적지 추천의 필수 전제다. 3~~4는 식사 우선순위화의 보조 근거이며, 수집 실패 시에도 TourAPI 목록 기본 정보로 식사 블록을 구성할 수 있다.
