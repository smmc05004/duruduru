## 1. 사용하는 방법과 상태 규칙

작업을 시작할 때는 이 문서에서 `다음`인 에픽 한 개를 선택하고, 연결된 기능 ID·선행 조건·수용 기준을 읽는다. 상태의 뜻은 다음과 같다.

| 상태             | 뜻                                                                                                   |
| ---------------- | ---------------------------------------------------------------------------------------------------- |
| 완료             | 기능 명세의 현재 수용 기준을 실제 데이터 계약으로 충족했고, 코드·테스트 근거가 있다.                 |
| 부분 완료 (목업) | 화면 또는 규칙은 동작하지만 PoC/임시 데이터 또는 미확정 정책에 의존한다. **정식 MVP 완료가 아니다.** |
| 부분 완료 (조사) | 조사 결과나 작업 준비는 남았지만 구현 완료 조건을 만족하지 않는다.                                   |
| 다음             | 현재 선행 조건으로 바로 시작할 employee 작업이다.                                                    |
| 대기/차단        | 제품 결정 또는 앞 에픽 산출물이 없어 구현을 시작할 수 없다.                                          |
| 미착수           | 관련 구현·조사 근거가 없다.                                                                          |

`완료`와 `부분 완료 (목업)`을 혼동하지 않는다. 특히 `lib/mock-data.ts`의 값, PoC 화면, 고정 이동시간은 제품 정책이나 정식 데이터가 아니다.

## 4. 다음 employee 작업: E2 데이터 품질 조사·수집 경계

**목표:** E1 계약을 이용해 초기 지역 관광·축제·음식 데이터의 필드 충족률·결측·갱신 위험을 재현 가능한 조사 산출물로 남긴다. 실제 API/DB·지원 지역·이동수단 정책은 확정하지 않는다.

**범위:** `docs/product/FUNCTIONAL_SPEC.md` 7.1절과 `docs/product/FOOD_DATA_NEXT_STEPS.md`의 남은 조사 항목을 계약 레코드로 정규화할 수 있게 검증한다. 결과에는 레코드 수·필수 필드 충족/결측·출처·갱신 시각·제한을 남긴다. 고정 fixture는 `npm run check:data-quality`, 실제 TourAPI 키가 있을 때는 `npm run check:tour-api`로 각각 실행한다.

**완료 조건:**

- 조사 입력과 정규화 결과가 E1 계약의 안정 식별자·출처·수집/갱신 시각·데이터 상태를 보존한다.
- 관광지·축제·음식점·대표음식의 필수 필드 충족률과 결측이 근거·표본·한계와 함께 남는다.
- 미달 값은 근거 없는 기본값이 아니라 `missing` 상태 또는 기존 확정 제외 규칙으로 표현한다.
- 실제 API/DB 도입과 정식 지원 조건 값 확정 없이, 조사 스크립트/fixture가 재현 가능하다.
- 기능 구현이므로 `context → plan → implement → verify → review → handoff` 사이클을 전부 기록하고 독립 reviewer 검토를 받는다.

**범위 밖:** 초기 지원 지역·이동수단·출발지 단위의 값 확정, 실제 API/DB 도입, 음식명 목록 확정, 운영시간 파싱, 일정 알고리즘 구현. 이들은 결정 또는 후속 에픽의 일이다.

## 6. 매 작업 후 갱신 규칙

employee는 작업 완료 보고·커밋·PR 준비 전에 다음을 수행한다.

1. 관련 기능 ID와 에픽의 상태를 실제 수용 기준으로 다시 판정한다. 목업 또는 미확정 정책 의존이 남으면 `완료`로 올리지 않는다.
2. 이 문서에 커밋 해시, 코드 경로, 실행한 Jest/Playwright/`npm run verify` 결과를 완료 근거로 남긴다. 실행하지 못한 검증은 이유와 위험을 함께 남긴다.
3. 완료 조건이 남으면 구체 항목을 `선행 조건·차단 사유`에 유지한다. 제품 판단이 필요하면 값을 정하지 말고 PM이 `DECISIONS.md`에 기록하도록 요청한다.
4. 하나의 에픽이 완료되면 상태를 바꾸고, 의존성상 가장 앞선 미완료 에픽 하나만 `다음`으로 표시한다.
5. 문서 변경만이면 위험에 비례한 검증을 실행한다. 기능·화면 구현이면 `docs/agent/WORK_CYCLE.md`의 전체 사이클과 독립 리뷰를 반드시 적용한다.
