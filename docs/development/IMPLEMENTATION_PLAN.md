## 1. 사용하는 방법과 상태 규칙

작업을 시작할 때는 이 문서에서 `다음`인 에픽 한 개를 선택하고, 연결된 기능 ID·선행 조건·수용 기준을 읽는다. 상태의 뜻은 다음과 같다.

| 상태             | 뜻                                                                                                   |
| ---------------- | ---------------------------------------------------------------------------------------------------- |
| 완료             | 기능 명세의 현재 수용 기준을 실제 데이터 계약으로 충족했고, 코드·테스트 근거가 있다.                 |
| 부분 완료 (목업) | 화면 또는 규칙은 동작하지만 PoC/임시 데이터 또는 미확정 정책에 의존한다. **정식 MVP 완료가 아니다.** |
| 부분 완료 (조사) | 조사 결과나 작업 준비는 남았지만 구현 완료 조건을 만족하지 않는다.                                   |
| 다음             | 현재 선행 조건으로 바로 시작할 employee 작업이다.                                                    |
| 대기/차단        | 제품 결정 또는 앞 에픽 산출물이 없어 구현을 시작할 수 없다.                                          |
| 미착수           | 관련 구현·조사 근거가 없다.                                                                          |

`완료`와 `부분 완료 (목업)`을 혼동하지 않는다. 특히 `lib/mock-data.ts`의 값, PoC 화면, 고정 이동시간은 제품 정책이나 정식 데이터가 아니다.

## 4. 다음 employee 작업: E11 라이브 1박 2일 계획 MVP

**현재 상태:** E10의 정적 결과는 기본 화면을 표시하지만, 동일 관광 권역의 세부 지점만 나열하고 날짜별 시간표와 식사 계획을 만들지 못한다. 이는 완료된 여행 계획이 아니다.

**계획 먼저 작성:** employee는 구현 전에 `DECISIONS.md` 11절과 F-02/F-04/F-05를 대조해 API 호출 경계, 검색 스냅샷, 권역 정의, 일정 배치 입력, 오류·키 경계를 적은 계획을 작성한다.

**최소 구현 범위:**

- `갈 수 있는 곳 찾기` 클릭에서만 TourAPI를 서버로 호출하는 adapter와 요청별 스냅샷을 만든다. 클라이언트·로그·오류 화면에 키나 원시 응답을 노출하지 않는다.
- TourAPI 관광지·음식점·상세 응답을 장소, 관광 권역, 운영 정보, 대표음식 근거의 내부 계약으로 정규화한다. 같은 권역의 세부 지점 중복을 제거한다.
- 1일차 08:00 출발·2일차 20:00 복귀의 실패 테스트를 먼저 만들고, 날짜별 최소 두 권역·점심/저녁·체류시간·이동시간 제약을 만족하는 규칙 기반 시간표를 구현한다. 필요한 값이 부족하면 정상적인 계획 생성 불가로 반환한다.
- 허가된 이동시간 제공자 또는 거리→시간 정책이 확정되기 전에는 실제 이동시간 호출을 구현하지 않는다. provider interface·구성 오류·서버 mock은 만들 수 있지만, 정적 데이터·PoC 값·공개 OSRM 데모로 대체하지 않는다.
- Jest와 Playwright에서 검색 클릭→추천→목적지 선택→두 날짜 결과, 외부 API 실패, 데이터 부족, 키 비노출을 검증하고 독립 리뷰를 받는다.

**차단된 완료 조건:** 실제 자동차 도로 경로 제공자를 쓸지, 또는 좌표 거리 기반 일반 시간 추정 정책을 제품적으로 승인할지 사용자가 결정해야 한다. 주소→좌표 지오코딩만으로는 이 값을 만들 수 없다. 카카오 모빌리티 길찾기는 사용하지 않는다.

**E11 범위 밖:** 실시간 교통 보장, 지도 UI 스크래핑, 공개 OSRM 데모의 런타임 사용, 영업·예약·분 단위 복귀 보증, PoC 고정 30분·임의 fallback, 숙소 위치 데이터, LLM 일정 생성.

## 5. E1 이후의 고정 순서

1. E2의 실제 프로브와 음식 데이터 후속 조사는 정식 데이터 전환 전까지 병행 가능한 데이터 준비로 유지한다.
2. E6은 `DECISIONS.md` 9절의 최소 데이터·근사 정책을 따른다. E7은 E6 완료 뒤에 시작하며, 결과가 참고용이라는 사실과 최신 정보 확인 행동을 보여야 한다.
3. E11의 실제 검색·계획 흐름이 완료된 뒤 E9 관측·품질 게이트와 E8 P1 확장을 다시 우선순위화한다.

이 순서는 제품 우선순위가 아니라 의존성 순서다. 새 제품 결정이 이 순서를 바꾸면 먼저 `docs/product/DECISIONS.md`와 이 문서의 상태·차단 사유를 함께 갱신한다.

## 6. 매 작업 후 갱신 규칙

employee는 작업 완료 보고·커밋·PR 준비 전에 다음을 수행한다.

1. 관련 기능 ID와 에픽의 상태를 실제 수용 기준으로 다시 판정한다. 목업 또는 미확정 정책 의존이 남으면 `완료`로 올리지 않는다.
2. 이 문서에 커밋 해시, 코드 경로, 실행한 Jest/Playwright/`npm run verify` 결과를 완료 근거로 남긴다. 실행하지 못한 검증은 이유와 위험을 함께 남긴다.
3. 완료 조건이 남으면 구체 항목을 `선행 조건·차단 사유`에 유지한다. 제품 판단이 필요하면 값을 정하지 말고 PM이 `DECISIONS.md`에 기록하도록 요청한다.
4. 하나의 에픽이 완료되면 상태를 바꾸고, 의존성상 가장 앞선 미완료 에픽 하나만 `다음`으로 표시한다.
5. 문서 변경만이면 위험에 비례한 검증을 실행한다. 기능·화면 구현이면 `docs/agent/WORK_CYCLE.md`의 전체 사이클과 독립 리뷰를 반드시 적용한다.
