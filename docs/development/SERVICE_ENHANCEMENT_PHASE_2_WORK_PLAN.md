# 서비스 2차 고도화 작업 계획

> 상태: S2-L·S2-O 구현 및 작업자 검증 완료 · 총괄 직접 점검 대기 / 작성일: 2026-09-09
>
> 제품 기준은 [서비스 2차 고도화 계획](../product/SERVICE_ENHANCEMENT_PHASE_2_PLAN.md)이다. 이 문서는 구현 순서와 검증 기준을 정의하며 코드 구현·테스트 완료를 의미하지 않는다. 아래 미정 항목은 employee가 임의 확정하지 않는다. 기존 MVP 2단계 또는 1차 고도화 E1–E4와 구분하기 위해 기능 ID에 `S2` 접두사를 사용한다.

## 1. 목표와 유지 범위

1. 장소 간 직선거리 기반 예상 이동시간을 일정에 실제 반영하고, 장소·음식점·순서가 바뀌면 같은 규칙으로 다시 계산한다.
2. 표준 출발 지역 검색·선택을 제공하고 선택한 지역의 KTDB 시간으로 목적지 후보와 계획을 다시 계산한다.

자차·다음날 복귀하는 1박 2일·공식 관심사·최대 3개 목적지 비교를 유지한다. 출발/귀가 이동은 24시간 허용하고 관광·개인 활동은 현지 체류 범위와 07:00–21:00의 교집합 안에 둔다. 같은 편도 KTDB 값을 왕복에 각각 적용하는 기존 정책은 별도 변경 승인 없이는 유지한다.

새 유료 API, 경로 API, OSRM 서버, 주소 검색·지오코딩 API, 키, DB는 필요하지 않다. 관광 좌표는 기존 지역 프로필, 음식점 좌표는 지역 선택 후 기존 목록 응답을 사용한다. 관광 상세 실패나 휴무 원문 때문에 계획을 자동 재생성하지 않는다. 지역N문화·모범음식점 보조 근거, 서로 다른 식당 배정, 저장 복원 시 자동 외부 조회 금지와 기존 호출 예산은 유지한다.

## 2. 구현 전에 확정할 정책

### S2-00 결정 결과

2026-09-09 총괄 지시에 따라 D1–D8의 구현 기본 정책을 [제품 계획의 구현 기본 정책](../product/SERVICE_ENHANCEMENT_PHASE_2_PLAN.md)에 기록했다. D1은 30km/h·5분 올림·최소5분·동일좌표0분, D2는 연결 이동으로 기존15분 대체·순수자유30분 유지, D3는 미확정 연결15분 임시 확보, D4는 같은 날 연속 실제 장소만 연결하고 대표점·숙소 경로는 미확정 안내다. D5는 식당 후보 순차 검토·관광 자동삭제 금지·교체 실패 원본 유지, D6는 기존 저장본 읽기 보존·새 검색/편집 시 새 버전, D7은 검증된 구/시군 표준 항목·일반구 필수·세종 단일, D8은 명시적 새 검색·실패/취소 원본 보존이다.

아래 표는 결정 전 점검 목록을 추적하기 위한 것이며 현재 재승인을 요청하는 목록이 아니다. `straight-line-v1`은 관측 통계가 아닌 제품 추정 규칙이다.

다음은 누락을 임의 값으로 채우지 않기 위한 승인 게이트다. PM이 두 기능의 제품 문서에 상세 규칙과 사례를 정리하고 필요한 사용자 결정을 받은 후 기능 구현을 시작한다. 준비 조사·계약 초안 작성은 가능하지만 미정 정책을 코드 기본값으로 넣지 않는다. D1–D8 중 보류 항목이 있으면 계획 작성은 완료할 수 있어도 S2-00의 구현 착수 게이트는 통과한 것으로 표시하지 않는다.

**D1–D8은 사용자에게 같은 내용을 다시 승인받는 질문 목록이 아니다.** PM이 먼저 기존 합의를 바탕으로 구체안을 만들고, 모듈 분리·필드명·알고리즘 등 합의 범위 안의 기술 선택은 담당자가 결정해 근거를 남긴다. 제품 범위나 사용자 결과·선택 보존을 바꾸는 판단에만 필요한 결정을 요청한다. 상위 계획이 미정으로 남긴 환산 수치·결측 처리 등은 이 작업 계획에서 확정하지 않으며, 상세 정책이 정리됐는지와 사용자 추가 승인이 필요한지는 구분해 기록한다.

## 4. 데이터 계약과 예외

### 4.1 장소 간 이동

- 구간은 같은 날짜의 안정적 출발/도착 항목 ID, 계산 대상 범위, 원천 좌표, 직선거리, 예상 분, 상태, 결측 이유, 환산 정책 버전을 연결한다. 단위는 km/분으로 명시한다.
- 상태는 ‘계산된 추정’과 ‘미확정’을 구분한다. 좌표는 유한 수치·위경도 범위를 검사하고, 결측 거리/예상 분은 `null` 등 명시적 표현을 쓴다. 예약 분을 쓰기로 승인하면 계산된 예상 분과 별도 의미로 저장한다.
- 같은 좌표·아주 짧은 거리·매우 큰 거리·좌표 한쪽만 존재하는 경우는 D1/D3 규칙으로 처리한다. 지도상 직선이 바다·산을 가로지른다고 도로 연결을 확인한 것으로 표현하지 않는다.
- 자유/휴식 블록을 장소로 취급하지 않는다. 미선택 식사나 개인 장소를 건너뛰어 앞뒤 관광지만 연결한 값을 전체 이동인 것처럼 표시하지 않는다. 숙소 좌표가 없는데 전날 마지막 관광지와 다음날 첫 관광지를 숙소 경로처럼 연결하지 않는다.
- 지역 간 KTDB 운전과 현지 추정을 별도 합산한다. `freeMinutes`에서 이동을 제외하고 식사·관광·이동·여유·휴식이 여행 범위 안에서 중복 없이 일치해야 한다. 카드의 왕복 운전 지표에 현지 이동을 몰래 섞지 않는다.
- 음식점 전 초안과 배정 후 결과를 구분한다. 식당 배정으로 지표가 바뀌면 초안 수치를 확정 수치처럼 유지하지 않는다. 검색 단계에서 음식점 API를 새로 호출해 이 차이를 없애지 않는다.

### 4.2 표준 출발 지역

- 표준 항목은 안정적 지역 ID, 완전한 표시명, 시도/시군구 계층, 검색 별칭, 대응 KTDB 존, 동일 지역 제외용 그룹, 매핑 버전, 지원 상태와 사유를 가진다. 자유 입력 문자열은 검색어일 뿐 선택 ID가 아니다.
- `강남`, `수원`, `해운대` 검색어를 표준 목록에서 찾고 동명이명은 상위 지역까지 표시한다. 시도 선택 → 필요한 하위 지역 선택도 제공한다. 세종에 없는 하위 구를 강제하지 않는다.
- 기존 `seoul`은 `ktdb-zone-2`, `busan`은 `ktdb-zone-26`의 의미를 보존한다. 복원 시 임의의 다른 구나 새 기본 출발지로 치환하지 않는다.
- 원천 KTDB 존, TourAPI 법정동, 표시 행정구역을 같은 코드라고 가정하지 않는다. 목적지에 필요한 관광 프로필 조건과 출발지의 KTDB 조회 조건도 분리해 점검한다. 출발 지역에 관광 콘텐츠가 부족하다는 이유만으로 출발 기능을 자동 제외하지 않는다.
- KTDB 값의 `null`, 0 이하, 비유한 값, 행/존 누락은 해당 경로의 미지원/데이터 오류로 구분한다. 울릉·제주 등 도로 미연결 쌍을 항공·선박·임의 평균으로 채우지 않는다. 입력 자체 미지원과 유효 출발지에서 가능한 목적지가 없는 상태를 구별한다.
- 출발 변경 시 같은 목적지 그룹의 대표 존도 다시 선택한다. 구별 입력 정밀도가 높아져도 목적지 결과를 다시 구 단위로 쪼개지 않는다.

### S2-L5 안내 노출의 명시적 수용 기준

- **L5-AC1:** 현지 이동 추정을 사용하는 계획의 상단 또는 하단 기본 영역에 아래 문구를 표시한다. 둘 중 한 위치면 충족하며 양쪽 중복 노출은 필수가 아니다. 데이터 근거·상세·도움말을 펼쳐야만 보이는 구현은 실패다.
- **L5-AC2:** 최초 계획, 음식점 배정 후, 관광/음식점 편집 후, 새 이동 규칙을 적용한 저장본 복원에서도 안내가 유지된다. 기존 이동 미반영 저장본은 D6의 기준선 안내를 적용해 이미 이동을 계산한 계획처럼 표시하지 않는다.
- **L5-AC3:** 문구가 현지 장소 간 추정임을 식별할 수 있고 KTDB 지역 간 시간의 원천을 직선거리라고 바꾸지 않는다. 모바일·데스크톱에서 문구가 잘리거나 숨겨지지 않으며 스크린리더가 읽을 수 있다.

> 장소 간 이동시간은 직선거리를 기준으로 추정했어요. 실제 도로의 우회, 교통 상황, 주차 등에 따라 달라질 수 있어요.

H · 여행 수첩 디자인의 시간 열·세로 레일을 유지한다. 출발 검색·선택·편집 오류는 키보드와 스크린리더로 확인할 수 있게 한다. React 구현 시 Vercel 스킬과 설치된 Next.js 문서를 확인한다.

### 공통 구현 주의점

- 기존 `placeActivities`는 고정 간격 배치다. 장소별 이동 비용은 식사라는 고정 경계의 앞뒤에도 걸리므로 단순히 15를 이동 분으로 치환해서 끝내지 않는다. 순서와 식당이 정해진 상태에서 각 연결 비용을 계산하고 배치 가능한 시작 구간을 구한 뒤 결정적 탐색을 적용한다.
- 관광 슬롯과 지리 선정이 서로 영향을 준다. 슬롯 확정 후 다른 관광지를 붙이거나 시간 초과 시 이동을 삭제하는 방식은 금지한다. 승인된 초기 선택/관광 수 축소 순서와 최대 관광 수 범위에서 유한하게 재평가한다.
- 편집 배치의 기존 목표(대상 외 시작 시각 보존 수 최대 → 기존 시작 시각 이동량 최소 → 시작 시각 배열 순)는 유지한다. 작은 사례의 독립 완전 탐색과 비교해 최적성과 불가 판정을 확인한다.
- 선택한 음식점 적용과 재계산은 하나의 결과 객체로 만든다. 시간표 적용 뒤 나중에 검증하거나 식당만 먼저 화면에 확정하지 않는다.
- 음식점 응답은 검색/계획 ID뿐 아니라 편집 세대를 확인한다. 응답 대기 중 관광·출발이 바뀌면 낡은 구간 계산을 적용하지 않는다. 실패가 자동 무한 조회나 전체 계획 초기화로 이어지지 않게 한다.
- 일정 재계산 성공은 방문정보 전체 자동 재조회를 뜻하지 않는다. 유지된 항목 정보는 보존하고 날짜 경고만 재계산한다. 저장 규칙 검증은 엔진과 같은 정책 버전을 사용한다.

기존 `lib/__tests__/mvp-phase-two-*.test.ts`, `enhancement-*.test.ts`, `activity-placement` 검증과 관련 컴포넌트·API 테스트를 유지/확장한다. 실제 운전 블록을 제거하거나 저장 검증을 우회한 fixture로 성공을 만들지 않는다. 관련 Jest부터 전체 회귀, 타입 검사·lint·포맷·빌드, 핵심 Playwright 순으로 검증한다. 실패는 변경으로 생긴 문제와 기존 실패를 구분하되 기존 실패를 숨겨 전체 통과라고 기록하지 않는다.

새 외부 API가 없으므로 결정적 mock 검증이 기본이다. 기존 목록 API 실연결 확인이 필요하면 소량으로 별도 수행하고 mock 통과와 구별해 기록한다. 전국 모든 음식점의 좌표/영업 또는 도로 이동 가능성을 보장하는 테스트라고 표현하지 않는다.

## 8. 위험·인계 조건

- 직선거리 시간은 도로 우회·산·바다·주차·교통을 반영하지 못한다. 기본 안내를 유지하며 이 작업을 실제 길찾기 정확도 개선이라고 부르지 않는다.
- 좌표 결측과 식당 선택 전 정보 부족은 없앨 수 없는 데이터 상태다. D3/D5가 확정되지 않으면 화면에 시간이 보이더라도 구현 완료로 보지 않는다.
- 이동이 추가되면 기존 최대 관광 수를 못 채우는 후보가 생길 수 있다. 승인된 최소·축소 정책을 적용하고 기존 개수를 맞추기 위해 이동/식사를 생략하지 않는다.
- 표준 출발 목록은 전국 행정명과 KTDB 2024 존의 시간 차이를 가진다. 원천 근거 없는 신규/분할 구 매핑을 만들지 않고 지원 범위를 자료로 남긴다.
- 저장 이관과 비동기 음식점 반영은 기존 사용자 선택을 손상할 위험이 크다. 엔진 단위 성공만으로 종료하지 않고 저장 왕복·실패 rollback·지연 응답까지 완료 기준에 포함한다.
