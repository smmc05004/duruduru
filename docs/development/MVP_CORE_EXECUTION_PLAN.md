# MVP 핵심 기능 실행 계획

> 기준 브랜치: `main` / 기준 데이터: 2026-09-07 KST 생성본
>
> 범위: 디자인 변경 없이 검색·선택·식사·시간표·오류 흐름을 제품 문서 계약으로 교체한다.

## 완료 목표

사용자는 서울특별시 출발 자차 1박 2일의 출발·복귀 일시와 관심사를 입력한다. 검색은 서울 중구 KTDB 존에서 출발해, KTDB 시간과 정기 수집 TourAPI 지역 프로필을 함께 적용하여 최종 목적지 **3개**를 보여 준다. 목적지를 고르면 그 지역 한 곳에 대해서만 최신 TourAPI 음식점 목록을 조회하고, 지역N문화·모범음식점 보조 근거를 반영해 점심·저녁을 정한 뒤 1일차·2일차 참고 시간표를 만든다.

이 작업은 디자인 개선, 실시간 교통·길찾기, 음식점 목록 단계의 `detailIntro2`, 평점·리뷰·랭킹, 내부 장소 이동시간을 포함하지 않는다.

## 현재 기준선과 교체 지점

| 항목          | 현재 기준선                                                                  | 구현 후 기준                                                                      |
| ------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 출발지·목적지 | 6개 고정 지역 설정과 출발지 선택                                             | 서울 중구 존 고정, 249개 매핑 가능 지역 프로필을 목적지 모수로 사용               |
| 후보 검색     | `app/api/trip-search/route.ts`가 요청마다 3개 지역 관광지·음식점·상세를 호출 | 검색은 로컬 `region-profiles.json`과 KTDB 테이블만 읽고 최종 3개를 반환           |
| 음식점        | 후보 검색 중 여러 지역의 목록·`detailIntro2`를 호출                          | 선택한 지역 한 곳의 목록 기본 정보만 호출; 상세는 식당 클릭 때 별도 호출          |

| 오류          | 후보·식사 실패가 섞여 있음                                                   | 입력 오류, 검색 데이터 오류, 결과 없음, 음식점 목록 오류, 음식점 상세 오류를 분리 |

| ------------------------------------------------ | -------------------------- | --------------------------------------------------------------------- | --------------------------------------- |
| `data/ktdb/interregional-travel-times-2024.json` | 252존·63,504쌍             | 서울 중구 존에서 목적지 존까지 편도/왕복 일반 예상시간 조회           | 시간 없음 지역 제외                     |
| `data/region-mapping.json`                       | 249개 매핑, 3개 검토 대상  | TourAPI 지역 코드와 KTDB 지역 ID 연결                                 | 검토 대상·매핑 없음 지역 제외           |
| `data/region-profiles.json`                      | 249개 지역·11,764개 관광지 | 공식 분류별 서로 다른 콘텐츠 ID 3개 이상 판정 및 일정 관광지 선택     | 해당 관심사 후보 제외                   |
| `data/food-culture-keywords.json`                | 36개 지역 키워드           | 음식점 우선순위의 약한 보조 근거                                      | 가점 생략                               |

| TourAPI `areaBasedList2`                         | 서버 키 필요               | 목적지 선택 뒤 선택 지역 한 곳 음식점 목록 기본 정보                  | 식사 목록 오류·재시도, 후보는 유지      |
| TourAPI `detailIntro2`                           | 서버 키 필요               | 사용자가 음식점 행을 열 때만 상세                                     | 해당 행의 상세 오류·재시도, 시간표 유지 |

## 작업 순서와 파일 범위

### 1. 도메인 계약과 입력 검증

- `lib/trip-conditions.ts`, `lib/support-conditions.ts`, 새 `lib/mvp-search-contract.ts`
- `app/page.tsx`의 출발지 선택을 서울특별시 고정 표기로 교체한다.
- 자차만 표시하고, 출발·복귀가 KST 기준 서로 다른 이틀을 걸치는 1박 2일인지 검증한다. 당일치기와 2박 이상은 검색 요청을 보내지 않는다.
- UI 관심사는 `nature`, `history`, `rest`, `culture`, `leisure`의 공식 분류 계약으로 매핑한다. 휴양·레저를 하나의 표시 그룹으로 묶어도 원천 ID는 보존한다.

### 2. 전국 후보 검색 Route Handler와 스냅샷

- 기존 `app/api/trip-search/route.ts`를 `app/api/search/route.ts`로 교체하고, 새 `lib/mvp-search-service.ts`, `lib/search-snapshot.ts`, `lib/interregional-travel-time.ts`를 추가한다.
- KTDB 서울 중구 존에서 편도·왕복 시간이 있고, 입력 시간에서 왕복과 최소 체류시간을 뺀 값이 유효한 249개 프로필 지역을 먼저 걸러낸다.
- 선택 관심사별로 서로 다른 TourAPI 콘텐츠 ID가 3개 이상인 지역만 남긴다.
- 시간 적합성, 공식 관심사 근거 수, 더 짧은 왕복시간, 안정적인 지역 ID 순으로 정렬해 정확히 최대 3개를 반환한다. 음식점 API는 이 단계에서 호출하지 않는다.
- 후보와 선택에 필요한 관광지, 이동시간 근거, 프로필 생성 시각을 검색 스냅샷으로 직렬화해 클라이언트가 보관한다.

### 3. 선택 지역 음식점 목록과 우선순위화

- 새 `app/api/destinations/[regionId]/restaurants/route.ts`, `lib/tour-api-client.ts`, `lib/restaurant-selection.ts`, `lib/restaurant-match.ts`
- Route Handler는 스냅샷에 있는 후보 지역 ID만 허용하고, 선택 지역의 법정동 코드로 `areaBasedList2` 음식점 목록을 페이지네이션·제한 동시성으로 조회한다.
- 목록의 콘텐츠 ID·이름·주소·전화번호를 정규화해 스냅샷에 저장한다. `detailIntro2`, 운영시간, 메뉴를 이 시점에 호출·필터링하지 않는다.
- 우선순위는 (1) 지역N문화 키워드와 TourAPI 음식점명·분류의 근거, (2) 모범음식점의 안전한 일치와 음식 종류, (3) TourAPI 기본 정보 충족, (4) 콘텐츠 ID 순이다. 지역N문화의 관련 음식점 필드는 사용하지 않는다.
- 음식점 목록 실패는 선택 후보를 지우지 않고 재시도 가능한 식사 데이터 오류를 반환한다.

### 4. 1박 2일 시간표 엔진

- 새 `lib/itinerary-scheduler.ts`와 `lib/itinerary-contract.ts`; 기존 `lib/mvp-trip-planner.ts`, `lib/planner.ts`, `lib/reference-itinerary.ts`의 정적/내부 이동 의존을 제거하거나 호출 경계에서 분리한다.
- 출발→목적지와 목적지→서울의 KTDB 편도시간만 배치한다.
- 21:00~~07:00 휴식, 각 날짜 점심 11:30~~12:30·저녁 17:30~18:30, 관광지·식당 각각 1시간을 고정한다.
- 동일 콘텐츠 ID와 같은 장소의 하위 명소를 중복 배치하지 않고, 선택 관심사 근거가 있는 서로 다른 관광지를 남은 블록에 배치한다. 내부 장소 이동시간은 계산·표시하지 않는다.
- 식당 근거가 약하거나 상세 정보가 아직 없더라도 목록 기본 정보로 식사 블록을 만든다. 상세 조회는 시간표를 재계산하지 않는다.

### 5. UI 상태 연결

- `app/page.tsx`, `components/CandidateCard.tsx` 및 필요한 결과 컴포넌트만 수정한다. `app/globals.css`, 토큰, 공통 디자인 컴포넌트는 디자인 변경 없이 기존 표현을 재사용한다.
- 상태 전환: 입력 → 후보 검색 로딩 → 최종 3개 후보 → 선택 지역 음식점 로딩 → 시간표 → 음식점 상세 열기/재시도.
- 일반 예상 이동시간·프로필 수집 시각·참고용 계획 안내를 표시한다. 내부 이동시간, OSRM, 정적 PoC 근거, 실시간 교통 표현은 제거한다.
- 오류 문구는 입력 오류, 검색 API/프로필 오류, 정상 결과 없음, 음식점 목록 오류, 음식점 상세 오류를 구분하고 각각 안전한 재시도 경로를 제공한다.

### 6. 정적 PoC 경로 제거와 계약 정리

- `lib/poc-data-adapter.ts`, `lib/mock-data.ts`, `lib/static-travel-time-data.ts`, `lib/route-collection.ts`, `lib/reference-itinerary-data.ts`와 이를 전제한 테스트·호환 주입 경계를 검색·일정 실행 경로에서 제거한다.
- 실제로 사용되지 않는 구형 `app/api/trip-search/route.ts`, `lib/region-config.ts`, `lib/trip-planner-contract.ts`는 새 계약 전환 뒤 삭제한다.
- 데이터 수집 스크립트와 생성 JSON은 유지하며, 원본 API 키·원시 응답은 저장소에 추가하지 않는다.

## E2E 수용 기준

통합 후 **E2E만** 실행한다. Jest·빌드·수동 화면 점검·독립 코드리뷰는 실행하지 않는다.

1. 서울 고정·자차·1박 2일·관심사 입력으로 검색하면 최종 후보가 3개 이하이고, 각 후보에 왕복 일반 예상 이동시간과 공식 관심사 근거가 보인다.
2. 당일치기, 2박 이상, 복귀가 출발 이전인 입력은 검색 요청 없이 명확히 거절된다.
3. 후보 검색 중 음식점 Route Handler가 호출되지 않고, 후보 선택 뒤 선택 지역 한 곳의 음식점 목록 Route Handler만 호출된다.
4. 선택 뒤 1일차·2일차 일정에는 출발·복귀, 점심·저녁, 서로 다른 관광지들이 보이며, 21:00~07:00 또는 장소 내부 이동시간 항목이 없다.
5. 음식점 상세는 클릭할 때만 호출하고, 상세 호출 실패가 기존 시간표·후보를 지우지 않으며 해당 식당 재시도만 제공한다.
6. 검색 오류·음식점 목록 오류·정상 결과 없음은 서로 다른 안내와 재시도 동작을 보인다.

## 구현 전제와 남은 위험

- 현재 프로필은 249개 지역만 포함하므로 3개 검토 대상과 KTDB 도로 결측 도서 지역은 추천하지 않는다.
- 지역N문화 키워드는 36개 지역만 있고 약한 보조 근거다. 없다고 해서 식사 블록을 만들지 못하는 것은 아니다.
- 모범음식점 인증 캐시는 수집 시점 기준이며, 전화번호 또는 정규화 상호·주소가 모두 일치하지 않으면 가점을 주지 않는다.
- TourAPI 목록의 결측은 목록 오류와 구분해, 정직하게 식사 후보 부족 상태로 처리한다.
