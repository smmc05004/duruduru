# DURUDURU 브랜치 작업 하네스

이 문서는 1인 개발과 에이전트 협업에서 `main`을 안정적인 기준선으로 유지하기 위한 작업 규칙이다. 모든 구현·수정 작업은 이 절차를 기본값으로 사용한다.

## 원칙

- `main`은 검증된 변경만 담는다. 직접 작업·직접 push·force push를 하지 않는다.
- 하나의 작업 브랜치는 하나의 기능, 버그 또는 문서 목적만 다룬다.
- 기능 브랜치는 짧게 유지한다. 병합 후 원격·로컬 브랜치를 삭제한다.
- 커밋 메시지와 PR 제목·설명은 한글로 작성한다.
- 제품 범위, 우선순위, 데이터 신뢰도, 사용자 흐름에 영향을 주는 변경은 먼저 `AGENTS.md`에 지정된 PM 문서를 확인한다.

## 브랜치 이름

| 접두사   | 사용처                  | 예시                         |
| -------- | ----------------------- | ---------------------------- |
| `feat/`  | 사용자 가치가 있는 기능 | `feat/recommendation-engine` |
| `fix/`   | 버그 수정               | `fix/return-time-validation` |
| `docs/`  | 문서만 변경             | `docs/data-contract-update`  |
| `chore/` | 도구, 의존성, CI, 정리  | `chore/add-ci`               |

이름은 목적을 드러내야 하며, 여러 에픽을 하나의 브랜치에 섞지 않는다.

브랜치 이름은 영문 소문자 케밥 표기로 적는다. 커밋 메시지와 PR 제목·설명은 한글로 쓰지만, 브랜치 이름은 셸 명령·CI 로그·URL에서 인코딩되는 자리라 영문으로 통일한다.

## 표준 작업 흐름

```bash
git switch main
git pull --ff-only
git switch -c feat/work-purpose

# 구현 및 한글 커밋
git push -u origin feat/work-purpose
```

1. 기능 명세서의 작업 단위 또는 명확한 버그·문서 목적을 하나 선택한다.
2. `main`을 최신화한 뒤 작업 브랜치를 만든다.
3. 변경을 논리 단위로 나누어 한글 메시지로 커밋한다.
4. 기능형 MVP 구현 기간에는 `npm run cycle`, 자동 테스트, lint, 타입 검사, 빌드, Playwright 검증을 모두 생략한다. 구현 완료 후 사용자가 직접 화면을 확인한다.
5. 기능형 MVP 구현 기간에는 reviewer agent의 독립 검토도 생략한다.
6. PR을 열고 템플릿의 범위와 제품 문서 확인 항목을 채운다.
7. PR의 **체크 결과와 병합 가능 상태를 함께 확인한다.** 아래 기준을 따른다.
8. 병합 방식은 아래 기준을 따른다. 병합된 원격 브랜치는 자동 삭제를 사용하고, 로컬 브랜치도 정리한다.

```bash
git switch main
git pull --ff-only
git branch -d feat/work-purpose
```

## PR 확인

병합 전에 **체크 결과와 병합 가능 상태를 함께 본다.** 둘 중 하나만 보면 통과를 잘못 읽는다.

```bash
gh pr checks <번호>
gh pr view <번호> --json mergeable,mergeStateStatus
```

체크가 하나도 없는 것은 통과가 아니다. 병합 충돌이 있으면 GitHub은 PR 워크플로를 실행하지 않으므로, 체크가 "실패"가 아니라 **"없음"으로 나타난다.** 실제로 이 저장소에서 충돌 상태의 PR이 체크 없이 조용히 머물러 있던 적이 있다.

| 상태                | 의미                       | 할 일                                                 |
| ------------------- | -------------------------- | ----------------------------------------------------- |
| 체크 없음 + `DIRTY` | 충돌 때문에 CI가 돌지 않음 | 최신 `main`으로 rebase하고 충돌을 해결한 뒤 다시 push |
| 체크 없음 + `CLEAN` | 워크플로가 트리거되지 않음 | 워크플로 조건과 실행 이력을 확인한다                  |
| `pending`           | 아직 실행 중               | 끝날 때까지 기다린다                                  |
| `pass` + `CLEAN`    | 병합 가능                  | 병합 규칙을 따른다                                    |

작업 브랜치를 최신화할 때는 rebase를 쓴다. 원격에 이미 push한 브랜치라면 `git ls-remote`로 원격 상태를 확인한 뒤 `--force-with-lease`로 push한다. `main`에는 force push하지 않는다.

## 병합 규칙

- 작업 브랜치의 커밋 각각이 의미 있고 이력을 유지할 가치가 있으면 **rebase merge**를 사용한다.
- 실험·중간 커밋이 많고 결과만 하나의 변경으로 남기는 편이 명확하면 **squash merge**를 사용한다. squash 커밋 메시지는 한글로 작성한다.
- merge commit은 특별히 병합 구조를 남겨야 할 이유가 없는 한 사용하지 않는다.
- `main`의 공개 이력은 재작성하지 않는다. 잘못된 변경은 새 커밋으로 되돌린다.

## 에이전트 작업 경계

- 에이전트 하나는 하나의 브랜치와 하나의 명확한 파일/기능 범위를 맡는다.
- 서로 다른 에이전트가 같은 파일을 수정해야 하면 선행 작업을 먼저 병합하거나, 담당 범위를 다시 나눈다.
- 에이전트는 구현 전에 `docs/product/FUNCTIONAL_SPEC.md`의 관련 에픽·의존성·보류 항목을 확인한다.
- 보류 제품 결정이 구현을 막으면 상수를 임의로 정하지 않고 `DECISIONS.md`에 제안할 내용을 보고한다.
- reviewer agent는 구현 agent와 별도 세션·컨텍스트에서 실행하며, 구현 코드 수정이나 자기 검토를 맡기지 않는다.

## GitHub 설정 권장값

저장소 설정에서 `main`에 다음 규칙을 설정한다.

- Pull request를 통한 병합 요구
- `CI / 검증` 상태 검사 통과 요구
- 선형 이력 요구
- force push와 브랜치 삭제 금지
- 병합 후 head branch 자동 삭제 활성화

혼자 개발하더라도 PR은 동료 승인 절차가 아니라 변경 범위·검증 결과·결정 근거를 남기는 품질 관문으로 사용한다.
