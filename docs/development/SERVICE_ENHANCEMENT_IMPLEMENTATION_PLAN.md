## 수정 작업 계획 — 기획 요구사항과 구현·검증 연결

### 목적과 범위

사용자가 만든 최초 계획뿐 아니라 편집한 계획도 시간 제약을 만족하고 저장·복원할 수 있게 한다. 기획서를 변경하거나 실패하는 동작을 새 정책으로 인정하지 않는다. 기존 KTDB·TourAPI·지역 프로필과 H 여행 수첩 디자인을 사용하며, 새 API·키·DB·데이터 준비는 필요하지 않다.

수정 대상은 E4 일정 편집·저장 정합성, E3 상세 요청 예산, 이들을 검증하는 테스트와 CI다. E1 목적지 추천·E2 최초 관광 구성·기존 음식점 선택은 보존할 회귀 검증 대상이다. R 번호는 새 제품 기능이 아닌 보정 작업 ID다. 아래 단계는 순서대로 진행하며, 구체적인 구현·커밋·PR은 후속 구현 작업에서 수행한다.

### 공통 완료 불변조건

아래 조건은 최초 생성, 각 성공 편집, 저장 직전, 복원 결과에서 확인한다. 저장 시각 등 생성 시점에 없는 필드를 요구하는 저장 형식 검증과, 계획 자체의 의미 검증은 구분한다.

- 전체 블록은 입력 출발부터 복귀 완료까지 시간순으로 연결되고 중복·누락·범위 밖 구간이 없다. 관광·개인 일정·현지 자유시간은 실제 현지 도착~~귀가 출발과 해당 날짜 07:00~~21:00의 교집합에만 둔다.
- 출발·귀가 운전은 24시간 허용한다. 편집은 기존 운전·식사 시작 시각/현지·이동 구분·휴식 구간과 선택 식당을 유지한다. 동일 편도 KTDB 운전 분을 왕복에 각각 적용하며 지역 내부 이동시간을 만들지 않는다.
- 같은 가용 구간의 연속 관광·개인 활동 사이 최소 15분, 활동하는 날 자유시간 총합 최소 30분을 확보한다. 15분 여유는 30분 합에 포함하고 식사·휴식 경계에는 중복 추가하지 않는다.
- 관광은 여행 최대 6개·하루 최대 3개, 개인 일정은 전체 최대 4개이며 안정적 ID와 관광 콘텐츠 ID가 중복되지 않는다. 삭제 후 관광 최소 3개 예외는 유지한다. 개인 일정은 관광 수·관심사·공간 점수에 포함하지 않는다.
- 날짜·시각·체류 분·개인 일정 필드가 서로 일치한다. 시각 고정된 항목의 날짜/시각은 명시적으로 허용된 변경 외에는 유지된다. 숙소 메모는 야간 시간을 추가 차감하지 않는다.
- 편집 대상 외 선택·날짜·상대 순서·체류 분을 보존한다. 성공 결과만 한 번에 적용하고, 실패 시 메모리 원본·식당·고정·저장본·변경 표시가 모두 유지된다.
- 편집·저장 복원 자체는 관광/음식 API를 자동 호출하지 않는다. 완료된 방문 정보는 유지하고 방문일 휴무 안내를 현재 날짜로 다시 계산한다. 추가/교체 관광지는 명시적 클릭에서만 조회한다.

### R0 — 실패 재현과 검증 계약 먼저 확정

- [ ] 위 R1~R5를 실패하는 회귀 테스트로 작성하고 현재 코드에서 실제로 실패함을 기록한다. 정상 계획의 저장 가능 여부부터 확인해 잘못된 fixture 때문에 실패하지 않도록 한다.
- [ ] 테스트 fixture는 실제 검색 또는 공통 생성 엔진의 결과를 사용한다. 제어된 경계 사례도 유효한 운전·식사·휴식·시간 연결을 유지한다. 원하는 테스트를 통과시키기 위해 운전 블록을 제거하거나 결과 계획을 mock하지 않는다.
- [ ] 기획서의 각 수용 기준에 테스트 이름·파일·실행 명령을 연결한다. 직접 재현한 실패와 추가로 검증할 경계 사례를 구분한다.
- [ ] 총괄은 구현 전에 테스트와 단계별 완료 기준을 검토한다. 테스트가 `ok === true`나 화면 문구 존재만 확인하는 경우 계획·저장 결과 검증을 추가한다.

### R1 — 공통 시간 제약과 원자적 편집

- [ ] 실제 현지 체류 구간과 낮 활동 구간의 교집합을 구하는 공통 계산을 도출한다. 최초 생성·편집·저장이 같은 의미 규칙을 따르게 하고, 서로 독립적인 07~21시 상수를 기준으로 재구현하지 않는다. 순수 공통 모듈을 둘 경우 저장/엔진 간 순환 의존을 만들지 않는다.
- [ ] 장소 유지 토글처럼 시간 변경이 필요 없는 명령은 시간표와 지표를 그대로 보존한다. 시간 재배치 명령은 위 불변조건 검사 후에만 성공 결과를 반환한다.
- [ ] 08:00→다음날 20:00 기준 30후보의 성공 편집→저장→복원 회귀를 재현한다. 07/21시 경계, 늦은 출발·이른 복귀·22시 야간 이동에서도 범위 밖 활동/자유시간이 없어야 한다.
- [ ] 실패하는 명령 전후 원본의 깊은 동등성과 기존 저장소 내용을 비교한다. 테스트 입력 동결로 내부 참조를 통한 원본 변경도 검출한다.

### R2 — 개인 일정과 저장 데이터 정합성

- [ ] 날짜·체류시간의 기준 필드를 정하고 UI/블록/개인 일정 표현을 한 경로로 갱신한다. 현재 저장 필드가 중복돼 있어도 서로 어긋난 성공 결과를 만들지 않는다. 저장 형식을 바꾸면 기존 유효 v3도 읽을 수 있게 한다.
- [ ] 개인 일정 30→90분 변경, 1→2일차 이동, 순서 변경, 시각 고정/해제, 삭제를 각각 실행한 뒤 저장·복원한다. 이름·주소·종류·안정적 ID·식당·숙소가 보존돼야 한다.
- [ ] v2 읽기 이관은 원래 날짜/시각/순서를 보존하고 장소 고정만 매핑한다. 개인 일정·숙소·시각 고정을 새로 꾸미지 않는다. v3 저장 확인 전 원본 v2를 제거하지 않는다.
- [ ] 빈 v3에서 삭제 계획 부활 금지, 손상/미지원 v3에서 묵시적 v2 재수입 금지, 저장소 차단·용량 오류·잘못된 개별 항목 처리 시 유효 원본 보존을 검증한다. 저장 후 검증 실패를 저장 성공으로 표시하지 않는다.

### R3 — 장소 유지와 시각 고정의 명령별 검증

- [ ] 관광지의 `장소 유지`와 관광/개인의 `시각 고정`을 구분해 엔진에서 검사한다. UI 버튼 비활성화만으로 제약을 보장하지 않는다.
- [ ] 시각 고정 상태에서 날짜·순서 이동과 삭제·교체 충돌을 거절한다. 장소 유지 관광지의 직접 삭제·교체도 해제 전 거절한다. 명시적 고정 시각 수정은 새 구간 검증 후 원자 적용한다.
- [ ] 14:00 고정 후 다른 활동의 체류시간을 변경해도 14:00이 유지돼야 한다. 식사·운전·휴식·21시 초과 충돌은 원본 보존과 구체적 오류를 확인한다. 해제 후에는 유효한 이동/삭제/교체가 가능해야 한다.

### R4 — 재배치 최적성 및 E2·음식 근거 보존

- [ ] 입력 계획의 원래 시각과 명령 대상을 분리 보관한다. 기획서의 우선순위인 편집 대상 외 기존 항목의 시작 시각 보존 개수 최대 → 기존 시각 대비 이동 절대 분 합 최소 → 최종 시작 시각 배열 사전순을 명시적 비교 함수로 구현한다. 추가 항목의 임시 07:00을 원래 사용자 시각처럼 점수화하지 않는다.
- [ ] 고정 활동 앞 사슬뿐 아니라 일반 활동의 기존 시각·식사/현지 체류 구간 끝을 포함해 모든 유효 배치에서 목적함수가 보장되는 유한 알고리즘을 선택한다. 분 단위 입력을 임의 15분 격자로 반올림하지 않는다. 후보 몇 개를 추가해 특정 예시만 해결하는 방식으로 최적성을 주장하지 않는다.
- [ ] 소규모 독립 전수 탐색을 테스트 기준으로 두고 배치 성공/실패와 목적함수 값을 비교한다. 기준 탐색은 실제 구현의 후보 생성·비교 함수를 재사용하지 않는다. 일반/고정 활동 사슬, 식사 경계, 하루 3관광+최대 4개인, 분 단위 고정·동점 사례와 실행시간을 기록한다.
- [ ] A 09:00~~10:00/B 10:15~~11:15에서 A를 90분으로 바꾼 경우, 유효한 08:30 배치를 놓쳐 07:15까지 앞당기지 않음을 검증한다. 기존 A/B/C 연쇄 고정 회귀도 유지한다.
- [ ] 이동·추가·교체 후 날짜/반일/시설 근거가 현재 장소와 맞는지 확인한다. 시설 의심 추가는 기획대로 안내 후 명시적 허용하며, 기존 식당은 보존하고 필요한 식사에 위치 확인 안내를 남긴다. 새 목록 조회는 명시적 동작에만 연결한다.

## E4 — 내 계획 편집

### 목표

선택한 관광·식사 스냅샷을 외부 조회 없이 유지하면서 관광 날짜·순서·추가와 개인 일정, 숙소 메모, 시작 시각 고정을 안전하게 편집한다. 모든 편집은 운전·식사·야간 휴식 경계를 보존한 공통 재배치 엔진의 성공 결과만 원자 적용하며, 기존 v2 저장본은 자동 재검색 없이 v3로 읽기 이관한다.

### 수용 기준

- 관광 날짜/순서 이동, 같은 선택 그룹·선택 관심사의 미사용 관광 후보 추가(30/60/90/120분), 개인 일정(전체 최대 4개), 계획당 숙소 메모 1개를 지원한다. 개인 일정은 관광·관심사·상세/API 대상이 아니다.
- 관광·개인 일정의 시각 고정은 해당 날짜·분 단위 구간을 함께 고정한다. 07:00~21:00, 식사·운전·야간 휴식, 하루 관광 3개, 연속 활동 15분 여유와 활동일 30분 자유시간을 만족하지 못하면 이전 계획을 그대로 보존하고 구체적인 실패 사유를 낸다.
- 재배치는 무관한 항목의 ID·선택·날짜·상대 순서·고정 상태를 보존하고, 가능한 배치 중 기존 시작시각 보존 최대 → 이동 분 합 최소 → 시작 시각 배열 순으로 결정한다. 식당은 자동 교체하지 않으며 관광 변경 때 위치 확인 안내만 추가한다.
- 저장 컨테이너와 스냅샷을 `schemaVersion: 3`으로 검증·정규화한다. v2는 메모리에서만 이관하고, v3 확인 쓰기 전 v2를 지우지 않으며, 빈 v3·손상 v3은 v2 재수입으로 삭제 계획을 부활시키지 않는다.
- 저장 복원·편집은 관광/음식 API를 호출하지 않는다. 기존 E1~E3 추천 근거·음식 흐름·H 여행 수첩 레일을 유지한다.

### 파일 범위와 구현 순서

1. `lib/mvp-phase-two-types.ts`, `lib/mvp-phase-two-planner.ts`에 v3 활동·숙소 계약과 결정적 재배치/명령 검증을 추가한다.
2. `lib/mvp-phase-two-storage.ts`를 v3 컨테이너와 v2 읽기 이관, 엄격한 길이·형식 검사, 원자 저장/삭제로 확장한다.
3. `components/mvp-phase-two/TripPlanner.tsx`와 최소 CSS에 기존 수첩 레일의 키보드 가능한 날짜·순서·추가·고정·개인 일정·숙소 편집 동작을 추가한다.
4. 먼저 실패하는 Jest로 재배치 제약/rollback/고정/개인 일정/후보 검증과 v2→v3 이관·손상·저장소 실패를 작성하고, 기존 실제 검색→계획→음식 목록 통합 흐름에 E4 편집·복원을 연결한다.
5. 변경 관련 Jest·통합 Jest·Playwright, `npm run verify`, 전체 Jest, `npm run test:e2e`, `npm run cycle`을 각각 기록하고 PR/CI 상태를 확인한다.

### 의존성·위험·제외

- 의존성: E1~E3 공통 시간 엔진, 기존 localStorage, 이미 선택한 목적지/음식점 스냅샷만 사용한다.

- 제외: 새 API·키·DB·LLM, 지오코딩·내부 이동시간·숙소 추천, 음식점 알고리즘/자동 재조회, 관광 상세 자동 재요청, 공유·출력이다.

- 도메인 Jest: 날짜/순서/추가·개인 일정·고정의 성공과 모든 제약 실패 rollback, 15분·30분 여유, 관광 3개·개인 4개 한도, 후보/중복/입력 경계, 식당 보존을 검증한다.

## E3 — 추천 근거와 방문 판단 정보

### 목표

선택한 계획의 실제 관광지에만 TourAPI 기존 상세 원천을 제한적으로 보강한다. 일정과 기존 음식점 흐름은 즉시 유지하고, 제공된 소개·Type1 확인 사진·휴무 원문·안전한 주소 도구를 항목별로 덧붙인다. 검색에는 관광 상세 호출을 추가하지 않는다.

### 수용 기준

- 자동 보강은 실제 계획의 서로 다른 관광지 최대 6개에만 하고, 항목별 `detailCommon2`/`detailIntro2` 최대 2회, 전체 최대 12회·원천 동시성 2·항목 12초·작업 28초를 지킨다. 항목은 순차 처리하고 내부 두 요청만 병렬 처리한다.
- 진행 요청은 `contentId + contentTypeId` 단위로 자동·클릭이 공유한다. 정상 캐시는 30분, 부분 캐시는 5분이며, 자동 재시도는 없고 명시적 재시도는 항목당 최대 2회 및 실패 뒤 30초 쿨다운을 적용한다.
- 검색/목적지/계획 세대가 바뀌면 이전 자동 결과를 취소 또는 무시한다. 저장본 복원은 자동 상세 호출 0회이고 명시적 `방문정보 확인`만 같은 예산으로 요청한다.
- 항목별 `loading / ready / partial / unavailable / not-requested`와 부분 성공을 보존한다. 느림·오류·시간 초과는 관광·식사 계획을 막거나 바꾸지 않는다.
- 소개는 HTML을 실행하지 않는 안전한 첫 160자 요약과 펼치기로, 사진은 `cpyrhtDivCd === Type1` 및 허용 관광공사 이미지 호스트일 때만 출처·조건·조회일과 함께 표시한다. 그 외 이미지·원시 HTML·원시 외부 URL은 쓰지 않는다.
- 휴무 원문을 보이고, 전체가 단일 `매주 {요일}` 또는 `매주 {요일} 휴무` 형식일 때만 KST 방문일과 비교해 경고한다. 공휴일 예외·복수 조건·부분 일치·결측은 자동 판정하지 않는다.
- 주소가 있으면 복사와 승인한 HTTPS 지도 검색 링크를 제공하고, 없으면 이름 검색임을 알리며 복사 버튼을 숨긴다. 링크는 URL 인코딩·`noopener noreferrer`를 사용하고 복사 실패는 주소 선택 안내로 처리한다.

## E2 — 하루 관광 구성과 여유

### 목표

E1이 검색과 선택에 함께 쓰는 공통 일정 엔진에 보수적 시설 의심 묶음, 반일별 근접 관광 선택, 활동 사이 15분 여유를 넣는다. 좌표 거리로 내부 이동시간을 만들지 않으며, 15분 여유는 관광일 최소 30분 자유시간 안에 포함한다. 후보 초안·선택 결과·기존 편집 재계산은 같은 엔진·규칙 버전을 사용한다.

### 수용 기준

E2의 시설 묶음·반일 여유, E3 상세/사진/휴무, E4 편집·저장 이관, 내부 이동시간 환산, 새 외부 API·키·DB·LLM·실시간 교통, 음식점 알고리즘 변경은 구현하지 않는다.

### 검증 계획

- Jest: 역할별 정렬·순차 중복 제거·동점·거리 결측·1~2개 결과 및 계획 동일성을 검증한다.
- Playwright: 서울/부산에서 검색, 세 역할 카드 확인, 하나 선택 후 기존 음식 목록 요청과 계획 표시를 검증한다. 검색/음식 API만 제한적으로 mock하고 엔진·역할 선택은 실제 코드로 실행한다.
- `npm run verify`, 관련 Jest, `npm run test:e2e`를 실행하고 실제 Playwright 브라우저 화면을 점검한다.
