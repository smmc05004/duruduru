# 목적지 추천 품질 재작업 기준

> 2026-09-14. PR #76의 근거리 쏠림을 진단한 R1/R2 정정·총괄 검토를 완료했다. 사용자는 아래 세 역할과 이동시간 기반 후보 구성을 승인하고 **같은 브랜치에서 R3~R5 구현·검증 후 PR 생성**을 지시했다. 총괄은 실제 비교 결과로 세부 정책을 확정하고 작업자를 감독한다. 최종 사용자 품질 수용은 PR 결과 확인과 별개로 남기되 구현·PR 진행을 위해 같은 승인을 다시 요청하지 않는다.

## 승인된 추천 구성 (2026-09-14)

| 역할             | 제공할 선택                                                                        |
| ---------------- | ---------------------------------------------------------------------------------- |
| 가까운 여행      | 이동 부담이 적은 목적지 1곳                                                        |
| 1박 2일 여행     | 가까운 나들이와 구별되는 목적지 1곳                                                |
| 관심사 중심 여행 | 이동 부담을 더 감수할 수 있으면서 관심사에 맞는 실제 방문 내용이 풍부한 목적지 1곳 |

이동시간 범위를 후보 구성에 명시적으로 활용하고 기존 interest/easy/relaxed 역할을 교체한다. 추가 입력 없이 최대 3개 서로 다른 지역을 제시한다. 역할에 맞는 후보가 부족하면 억지로 세 장을 채우지 않는다. 가장 먼 목적지 선택이나 도시 이름 가점은 승인되지 않았다. 시간 범위·활동 조건·역할별 동점 처리의 구체 수치는 R3 실측과 총괄 검토로 확정했다. R4~R5는 이 확정 정책을 구현·검증한다.

지역 내 `hubRank` 숫자를 지역 간 매력 점수로 쓰지 않는다. 실제 배치된 관심사 시설·유형·시간을 여행 내용의 근거로 쓰며 전국 인기나 역사적 가치를 보증하지 않는다. 목적지 선택 전 음식점 호출을 추가하지 않는다. 구 역할의 저장본은 당시 의미대로 복원하고 새 역할을 소급 덮어쓰지 않는다.

## R3 확정 정책 (2026-09-14)

아래 수치는 기존 로컬 데이터와 기존 일정 생성 결과만으로 좁게 비교한 뒤 총괄이 승인한 확정안이다. 과거 R1/R2 보고 숫자는 당시 배포 정책의 진단값으로 보존하고, 새 정책 결과로 덮어쓰지 않는다.

### 후보 공통 조건

선택 후 [긴 여유시간 보완](LONG_GAP_ENRICHMENT.md)은 아래 검색 후보 자격·역할·정렬을 변경하지 않는다. `overnight`/`interestRich`의 자유시간 240분은 검색 초안에 적용하는 조건이다. 선택 후 관광 추가로 자유시간이 줄어도 역할을 소급 변경하지 않으며, 검색 근거와 현재 선택 계획 지표를 구분한다.

- 후보는 기존 `scheduleTrip`을 통과한 실제 1박 2일 일정만 사용한다. 새 API 호출·재수집·지역명 가점·최장거리 우선은 없다.
- 출발 권역 제외, KTDB 일반 이동시간, 야간 휴식, 식사·음식점 호출 경계, 최대 3개 후보, 서로 다른 `groupId` 조건을 유지한다.
- 요청 관심사는 실제 배치된 관광지의 분류로 모두 충족해야 한다. 목적 적합성 설명에는 `fitAverage`/`fitBand`, 배치된 관심사 시설 그룹 수, 세부 유형 수, 방문 시각, 현지 자유시간을 함께 사용한다.
- `hubRank`는 지역 안 순위이므로 지역 간 정렬 키로 쓰지 않는다. 연결 있음/없음은 설명 보조 근거로만 남기고, 중심 결측은 매력 없음으로 처리하지 않는다.

### 역할별 후보 구간과 정렬

| 새 역할          | 1차 후보 구간    | 추가 활동 조건                                                                                                                                                                               | 동점 정렬 순서                                                                                                                                                                             |
| ---------------- | ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 가까운 여행      | 편도 `<= 60분`   | 실제 관광 시설 그룹 3곳 이상, 요청 관심사 모두 충족                                                                                                                                          | 편도시간 짧음 → capped `fitAverage` 높음 → 관심사별 최소 시설 그룹 수 capped 4 많음 → 관심사별 최소 세부 유형 수 capped 3 많음 → `groupId`                                                 |

역할은 위 순서로 1장씩 뽑고 이미 선택된 `groupId`는 다음 역할에서 제외한다. 어떤 역할의 조건을 만족하는 후보가 없으면 다른 역할의 후보로 억지 보충하지 않고 1~2장만 반환한다. 이 방식은 근거리 세 장 채우기와 최장거리 세 장 채우기를 모두 피하려는 제안이며, 특정 도시를 직접 가점하지 않는다. 1박 2일 여행의 120분 목표와 관심사 중심 여행의 180분 목표는 목적지 매력 점수가 아니라 세 카드가 서로 다른 이동 부담을 갖도록 하는 구성 선호다.

### 저장·버전 호환

- 새 검색 버전은 R4에서 `e1-v4` 계열로 올린다. 시간 엔진 자체를 바꾸지 않으면 planner/itinerary 버전은 `e2-v3`을 유지한다. 새 역할 값은 `nearby`·`overnight`·`interestRich` 같은 내부 enum으로 분리하되, 화면 문구는 위 한국어 역할명을 사용한다.
- 저장된 구 버전 후보의 `interest`·`easy`·`relaxed`는 당시 의미대로 복원한다. 저장본을 새 역할로 재해석하거나 소급 덮어쓰지 않는다.
- R4 검증 하네스는 두 갈래로 분리한다. R1/R2 과거 알고리즘 비교는 test-support에 명시적으로 보존하고, 새 정책 검증은 별도 현행 정책 테스트로 둔다. production export 변화 때문에 과거 보고가 새 정책 숫자로 바뀌거나 CI가 깨지지 않게 한다.

## 해결해야 할 사용자 문제

목적지를 정하지 않은 사용자가 1박 2일의 가용시간과 관심사를 입력했을 때, 가까운 곳에서 시간을 채우는 결과를 넘어 여행 목적에 맞는 목적지를 발견해야 한다. 사용자는 역사 여행의 예로 공주·익산·경주를 들었다. 해당 도시를 무조건 추천하라는 요구가 아니라, 방문할 가치가 있는 후보를 근거리와 비교할 수 있어야 한다는 요구다.

배포 후 사용자 관찰은 남양주·하남·과천 추천이다. 이 관찰의 정확한 관심사·날짜·시간·출발 ID는 아직 보존하지 못했으므로 임의로 재현 성공이라고 쓰지 않는다. 별도로 서울 빠른 선택, 역사, 연속 이틀 08:00→다음날20:00을 고정 진단 입력으로 사용한다. 테스트 날짜와 모든 입력을 기록한다.

## 실패 원인과 기존 작업의 가치

- T1~T4의 새 TourAPI 분류 대응·관광지 수집·중심 관광지 연결 및 시설 중복 수정은 보존한다. 수집부터 다시 시작할 이유는 확인되지 않았다.
- T6의 지역 내 중심 순위 합산은 전국 목적지 비교 근거로 부적절했고 원거리 쏠림이 발생했다.
- T7은 시설 수 4·유형 수 3의 상한과 세 등급으로 차이를 압축했다. 같은 등급에서는 왕복시간을 중심 근거보다 먼저 비교해 근거리가 이긴다. easy는 이동시간, relaxed는 현지 여유를 우선하므로 세 카드 모두 근거리로 모일 수 있다.
- 기존 48개 사례에서 interest가 모두 편도 40분 이내였다([검증 보고서 §7](../development/TOURISM_RECOMMENDATION_T6_REPORT.md#72-48개-입력-재실행-t6와-같은-매트릭스)). 이를 품질 미달로 처리하지 않고 회귀 검사 통과를 완료로 판단한 것이 검토 실패다.
- 시설 수와 유형 수는 일정을 구성할 수 있는 정도다. 그 자체로 역사적 중요성·지역 대표성·1박 2일 여행의 매력을 측정했다고 표현하지 않는다. 중심 관광지 API의 지역 내 연계 방문 순위도 전국 가치 점수가 아니다.

## 재설계 원칙

1. 왕복·관광·식사·휴식·현지 이동의 시간 적합성은 필수 조건으로 유지한다. 가능 후보 중 여행 목적에 맞는 곳을 비교하는 기준은 별도로 평가한다.
2. 기존 데이터로 실제 어떤 목적 적합성 차이를 설명할 수 있는지 먼저 확인한다. 공주·익산·경주와 근거리 후보의 실제 장소·공식 세부 분류·시설 묶음·중심 연결·미연결을 비교한다. 자료가 없거나 연결에 실패한 것을 매력 없음으로 간주하지 않는다.
3. 새 전략은 관심사 카드 한 장뿐 아니라 최종 세 장을 함께 평가한다. easy/relaxed 고정을 재작업의 제약으로 삼지 않는다. 역할 재정의·후보 조합 변경은 비교안으로 검토하고, 확정된 의미와 선정 순서를 구현 전에 이 문서에 기록한다.
4. 이동시간 범위를 이용한 후보 구성은 위 사용자 승인에 따라 R3에서 구체화한다. 특정 도시 가점·무조건 최장거리 우선·추가 사용자 입력은 도입하지 않는다. 시간상 가능한 후보에서 서로 다른 여행 선택지를 제공하고, 원거리 쏠림으로 근거리 쏠림을 덮지 않는다.
5. 무료 공공데이터·규칙 기반 엔진을 유지한다. 우선 기존 데이터로 진단하며 새 API·전국 재수집·유료 서비스·LLM·실시간 경로 호출을 해결의 선행조건으로 추가하지 않는다. 추가 원천이 꼭 필요하면 필요한 필드와 기존 데이터의 한계를 먼저 설명한다.
6. 새 수식·상한·시간 구간은 R3 실측 비교 후 총괄이 확정한다. 역할의 제품 의미는 위 승인 내용이 기준이다. 기존 D4/D4-a는 과거 배포 코드 설명으로 보존하되 재작업의 목표 명세로 사용하지 않는다.

## 품질 판정과 중단 조건

- 고정 진단 입력에서 근거리 후보와 공주·익산·경주의 포함/탈락 경로를 모두 설명한다. 매핑·분류·시간 탈락과 점수·정렬 탈락을 구분하고, 실제 초안에 쓰인 장소까지 보여 준다. 특정 도시의 강제 상위 노출은 통과 조건이 아니다.
- 비교 결과에는 변경 전후 최종 세 지역, 역할, 실제 관광 장소, 왕복/현지 활동/여유시간, 목적 적합성 근거, 각 주요 탈락 후보의 이유를 함께 남긴다. 새 기준에 맞춘 합성 테스트만으로 효과를 주장하지 않는다.
- 동일한 진단 입력에서 다시 근거리 세 곳만 나왔을 때, 코드가 명세를 따랐다는 이유로 해결 완료로 처리하지 않는다. 시간상 가능한 더 먼 후보와 비교해 결과가 타당한지 설명하고 사용자에게 실제 결과를 제시한다. 근거리만 가능하거나 목적 근거가 부족한 입력에서는 근거리 결과를 허용하지만 원인을 남긴다.
- 기존 48개 입력을 고정 회귀 묶음으로 사용한다. 서울 역사 단일 사례뿐 아니라 부산·다른 출발지, 다른 관심사, 야간 출발에서 반대 방향의 쏠림·시간 회귀를 확인한다. 왕복시간 중앙값만으로 품질을 판정하지 않는다.
- 기존 데이터로 목적지 매력의 차이를 구별할 수 없다면 그 사실이 진단 결과다. 근거 없는 점수를 만들지 말고 어느 정보 또는 제품 결정이 필요한지 구체적으로 보고한다.
- 최종 완료는 기능 검증 통과와 추천 결과의 제품 목표 충족을 각각 확인해야 한다. CI 성공·PR 병합·배포 성공을 품질 개선 완료로 대체하지 않는다. 최종 비교 결과를 사용자에게 제시하고 수용 여부를 확인하기 전에는 추천 문제를 해결 완료로 표시하지 않는다.

## 유지할 기능

목적지 선추천 흐름, 최대 3개 후보, 1박 2일, 표준 출발 지역, 출발 권역 제외, KTDB 일반시간, 현지 직선거리 추정, 야간 관광 휴식, 식사·음식점 조회 경계, 상세·편집·저장 호환을 유지한다. 디자인 개편과 무관한 기능 확대는 포함하지 않는다.
