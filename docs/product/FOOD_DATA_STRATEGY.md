# DURUDURU 음식 데이터 전략

> 대상: 음식·음식점 데이터의 수집·정규화·선정 방향을 판단해야 하는 PM·개발·리뷰 에이전트
>
> 이 문서의 위치와 성격: 여기에 적힌 것은 **제품 결정과 조사 사실**이다. 결정의 상태(`확정`·`제안`·`보류`)는 `docs/product/DECISIONS.md`가 단일 출처이며, 이 문서는 그 결정의 근거·전제·데이터 사실을 보존한다. 기능 수용 기준과 데이터 계약은 `docs/product/FUNCTIONAL_SPEC.md`에 있다. 문서가 충돌하면 PRD와 확정된 결정, 기능 명세 순으로 확인한다.
>
> **기술 구현 방식은 이 문서에서 확정하지 않는다.** 타입 정의, adapter 구조, 저장소 스키마, 정규화 알고리즘은 `.agents/employee/AGENT.md`의 개발 에이전트가 제안한다. 이 문서가 정하는 것은 "무엇을 보존해야 하는가"라는 요구사항까지다. 경계는 10절에 명시했다.

## 0. 검증 상태 표기 규칙

이 문서의 모든 사실 주장에는 다음 세 표기 중 하나가 붙는다. 표기 없는 서술은 제품 결정이다.

| 표기                        | 뜻                                                                                                        | 어떻게 다뤄야 하는가                                                              |
| --------------------------- | --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| **[실측]**                  | 우리가 실제 API 응답·파일을 받아 확인했다. 확인일과 표본 수를 함께 적는다                                 | 구현 전제로 쓸 수 있다. 표본이 작은 항목은 그 사실이 함께 적혀 있다               |
| **[외부주장·미검증]**       | 외부 참고 문서(2026-08-31 사용자가 제공한 ChatGPT 조사 문서)의 주장이며 **우리 조사에서 확인하지 않았다** | 구현 전제로 쓰지 않는다. 해당 지역·데이터를 실제로 쓰기 전에 확인 작업이 선행된다 |

**외부 참고 문서의 출처와 그 함의.** 이 문서의 골격(소스 유형·신뢰도 모델, 3단계 선정 전략, 스크래핑 정책, 수집·정규화·서비스 분리)은 2026-08-31 사용자가 제공한 외부 전략 문서에서 왔다. 그 문서는 **ChatGPT가 조사해 작성한 것**이며 저장소 밖에 있다(수정·복사 대상이 아니다). 따라서 그 문서의 **설계 원칙은 채택할 만하지만 사실 주장은 우리가 검증한 것이 아니다.** 특히 지역별 데이터 존재 주장은 전부 [외부주장·미검증]으로 분류했다. 원문을 그대로 옮기지 않고 저장소의 기록 방식으로 다시 썼다.

## 1. 왜 음식을 별도로 다루는가

음식은 일정의 빈 시간을 채우는 요소가 아니라 관광 항목과 동등한 일정 요소다. 이 방향은 2026-08-31 사용자 결정으로 확정됐다(`docs/product/DECISIONS.md` 6.2절 — 음식점을 일정에 포함하고, 관심사에서 미식을 고르지 않아도 끼니를 거르지 않는다).

DURUDURU는 "이 지역 최고의 맛집"을 단정하지 않는다. 대신 두 문제를 분리한다.

1. **이 지역에서 무엇을 먹을 것인가** — 지역 대표음식·향토음식의 선정
2. **그 음식을 일정 동선의 어디에서 먹을 것인가** — 대표음식을 취급하는 음식점 후보의 비교

이 분리가 중요한 이유는 두 문제의 데이터 출처와 신뢰도가 완전히 다르다는 데 있다. 1은 지자체 지정·문화 데이터에서 오고 갱신이 드물다. 2는 관광·위생 데이터에서 오고 폐업·운영시간 변경이 잦다. 하나의 소스로 둘을 동시에 해결하려 하면 둘 다 부정확해진다.

## 2. 소스 유형·신뢰도 모델 (제품 결정으로 채택)

대표음식의 근거는 소스마다 성격이 다르다. **어떤 종류의 근거로 이 음식이 대표음식이 됐는지를 데이터에 보존한다.** 그래야 나중에 더 좋은 데이터가 나왔을 때 기존 값을 교체할지 판단할 수 있고, 사용자에게 보여줄 근거 문구의 강도도 달라진다.

| 소스 유형                 | 뜻                                                            | 기본 신뢰도               |
| ------------------------- | ------------------------------------------------------------- | ------------------------- |
| `OFFICIAL_REPRESENTATIVE` | 지자체가 공식적으로 대표음식·○○미 등으로 **지정**한 데이터    | `HIGH`                    |
| `LOCAL_SPECIALTY`         | 공식 향토음식 또는 향토음식점 데이터                          | `HIGH`                    |
| `RESTAURANT_MENU`         | 관광·공공 음식점 데이터의 대표메뉴·주메뉴에서 **도출**한 후보 | `MEDIUM`                  |
| `CURATED`                 | 공공데이터로 채울 수 없는 지역의 최소 수동 보완               | `LOW` 또는 별도 검증 상태 |

신뢰도 값은 `HIGH` · `MEDIUM` · `LOW` · `UNVERIFIED` 네 단계다. `UNVERIFIED`는 소스에 존재하지만 우리가 확인하지 못한 상태를 가리키며, 이 문서 0절의 [외부주장·미검증]에 해당하는 데이터가 여기 들어온다.

**운용 원칙.**

- `RESTAURANT_MENU`는 "이 음식이 대표음식이다"를 직접 지정한 데이터가 **아니다.** 공식 대표음식과 같은 근거로 취급하지 않는다. 이유는 3절의 실측 결과가 구체적으로 보여 준다 — 메뉴 빈도 집계는 지역에 따라 통념과 어긋난다.
- 같은 음식이 여러 소스에 등장하면 출처를 잃지 않는다. 하나의 값으로 덮어쓰지 않고 근거를 함께 보존한다.
- `CURATED`는 범위를 최소화하고, 검토자·근거·검토일을 남길 수 있어야 한다.
- 신뢰도는 사용자 화면의 근거 문구 강도와 연결된다. `RESTAURANT_MENU` 근거로 "이 지역의 공식 대표음식"이라고 표시하지 않는다.

**대표음식 근거의 등급과 F-05 표시의 관계는 아직 맞물리지 않았다.** `docs/product/FUNCTIONAL_SPEC.md` F-05는 값 종류를 "공식/평균·추정/fallback/결측"으로 적는다. 위 4×4 모델을 그 표시에 어떻게 사상할지는 `docs/product/DECISIONS.md` 3.2절이 지적한 "출처 등급 집합 미정"과 같은 미해결 항목이다. 구현이 임의로 새 등급 이름을 만들지 않는다.

**카테고리로 음식 종류를 나눌 수 없다.** `cat3`는 한식/서양식/일식/중식/이색음식점/카페/클럽 7단계이고 빈 값이 경주 49% · 공주 41% · 강릉 14%다. 신규 체계 `lclsSystm`은 관광식당·모범음식점 같은 **지정 유형**이라 음식 종류가 아니다. 따라서 "대표음식을 파는가"의 판정을 카테고리로 할 수 없고 메뉴 텍스트에 의존한다.

**조회 함정.** `areaBasedList2`는 성남·청주처럼 **구가 있는 시를 시 단위 코드로 조회하면 0건**을 반환한다[실측]. 초기 3지역에는 해당하지 않지만 지역 확장 시 조용한 0건의 원인이 된다.

**호출 한도.** API 일일 요청 한도가 있다(`returnReasonCode 22`)[실측]. 전수 수집 시 고려 대상이다.

### 3.4 TourAPI 메뉴 텍스트의 상대빈도(lift) 집계 — 파생 신호 [실측]

전수 또는 부분 수집 후 타 2개 지역을 기준선으로 상대빈도를 계산한 결과다.

- **단순 빈도는 무용하다.** 원값 1위가 경주 `아메리카노 5`, 강릉 `아메리카노 6`. 토큰 집계도 `갈비`·`정식`·`비빔` 같은 전국 공통어에 묻힌다.
- **상대빈도는 경주·강릉에서 통념과 붙는다.** 경주 `쌈밥 ×8.1` · `갈비찜 ×9.8` · `떡갈비 ×5.7`, 강릉 `초당 ×8.5` · `옹심이 ×8.5` · `막국수 ×6.6` · `장칼국수 ×4.3`.
- **공주(76건)에서는 무너진다.** 상위가 `탕수 ×5.9` · `백숙 ×5.2`로 중식 메뉴다. 표본 크기가 원인으로 추정되지만 확정하지 못했다.
- **제과·특산물은 구조적으로 못 잡는다.** 황남빵 1업소, 알밤 5업소. 음식점 카테고리에 거의 없다.
- 카페 오염은 `cat3` 코드(`A05020900`)로 기계적으로 분리 가능하다. **단 강릉 커피는 실제 대표음식이므로 카페를 살릴지는 지역별 판단이 필요하다.**
- **한계.** 기준선이 타 2개 지역뿐이라 lift 절대값의 신뢰 구간이 넓다. 전국 베이스라인은 구성하지 않았다.

이 신호는 `RESTAURANT_MENU` 등급이며 **단독으로 대표음식을 확정하는 근거가 아니다.** 쓸 자리는 8절의 검증 단계다.

## 5. 대표음식 선정 전략 — 3단계 (제품 결정)

1. **지역 대표음식 선정** — 지역별로 무엇이 대표음식인지 정한다. 소스는 2절의 유형별 우선순위를 따르고, 근거·신뢰도를 보존한다. 3지역 MVP의 확정 절차는 8절.
2. **취급 음식점 후보 확보** — 대표음식을 파는 음식점을 찾는다. 음식명과 **별칭**을 함께 사용해 누락을 줄인다(3.6절이 별칭 필요성의 실측 근거다).
3. **일정 맥락을 반영한 후보 비교** — 동선 거리·예상 이동시간, 식사 시간대의 영업 가능성, 공식 지정 여부, 대표메뉴 일치 여부, 신뢰 가능한 소스 등장 여부.

**단계별 우선순위 (전체 데이터 수집).** 공공 API → 공공데이터의 공식 CSV·JSON 파일 → 무료 공식 API(후보 존재 확인·보강 용도) → 이용조건이 허용되는 공공기관 웹페이지의 제한적 수집 → **상용 지도·리뷰 플랫폼 스크래핑은 제외**(7절).

**무료 공식 API에 대한 유보.** 외부 문서는 네이버 지역검색을 후보 보조·존재 확인 수단으로 검토하라고 제안한다. 이는 [외부주장·미검증]이며 호출 한도·저장·표시 조건을 확인하지 않았다. 카카오 계열 API도 무료 쿼터·정책이 변할 수 있어 핵심 의존성으로 만들기 전에 구현 시점의 공식 정책 확인이 필요하다. **현재 확정된 것은 없다.**

## 6. 평점·리뷰를 쓰지 않는 이유와 대체 신호 (제품 결정)

`docs/product/PRD.md` MVP 비목표에 "맛집 평점·랭킹"이 있고 `docs/product/FUNCTIONAL_SPEC.md` 1.3절도 같다. 2026-08-31 음식점을 일정에 포함하기로 결정했지만 **이 비목표는 유지된다**(`docs/product/DECISIONS.md` 6.2절).

**왜 평점을 쓰지 않는가.** 세 층의 이유가 있고 층이 다르므로 하나가 해소돼도 나머지가 남는다.

1. **데이터가 없다.** TourAPI와 일반 공공데이터에는 구조화된 사용자 평점·리뷰 수가 보편적으로 제공되지 않는다[실측 — 3.1절의 필드 목록에 없다]. Google Places에는 해당 필드가 있으나 유료라 범위 밖이다.
2. **제품 포지션이 아니다.** DURUDURU의 핵심은 사용 가능한 시간으로 목적지부터 추천하는 경험이다(`docs/product/PRD.md`). 평점 순위 서비스와 정면으로 경쟁하는 것은 그 핵심과 무관하다.
3. **얻는 방법이 정책 위험을 만든다.** 평점을 확보하려면 상용 플랫폼 스크래핑으로 가게 되고, 그것은 7절에서 금지한다.

**대체 신호.** 평점이 없어도 공공·무료 데이터가 실제로 보장하는 것들을 조합한다.

| 신호                                         | 어떤 데이터로                                                                                            | 상태          |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ------------- |
| 대표음식과 메뉴의 일치도                     | TourAPI `firstmenu`·`treatmenu` (충족률 실측, 3.1절)                                                     | 데이터 확인됨 |
| 공식성 (향토음식점·관광식당·모범음식점 지정) | TourAPI `lclsSystm`, 모범음식점표준데이터                                                                | 데이터 확인됨 |
| 동선 (거리 또는 예상 이동시간)               | 좌표는 100% 실측. **다만 장소 간 이동시간 산출 방식이 미정**이다(`docs/product/DECISIONS.md` 1절 `제안`) | 값 차단       |
| 식사 시간대의 영업 가능성                    | 운영시간 100% · 휴무 93% 실측. **단 자유 서식 파싱이 선행**된다(3.1절)                                   | 파싱 차단     |
| 사용자 음식 취향                             | 향후 개인화 신호. 현재 범위 밖                                                                           | 범위 밖       |

**점수 설계에 대해 이 문서가 정하는 것과 정하지 않는 것.** 정하는 것은 "평점·리뷰 수·순위를 선정·정렬 기준으로 쓰지 않는다"와 "근거를 사용자에게 보여줄 수 있어야 한다"까지다. **구체적인 가중치 숫자는 이 문서에서 확정하지 않는다.** 층 ①·② 점수 정책은 이미 확정됐고(`docs/product/DECISIONS.md` 6.1절), 음식점 선정은 P0에서 별도 가중치를 도입하지 않는다 — 운영 가능 여부로 걸러진 뒤 층 ②의 동점 규칙으로 결정론적으로 하나를 고른다(같은 문서 6.2절). 음식점 전용 점수 항이 필요해지는 것은 P1(동선 최적화 선정)부터이며, 그때 필요한 값은 별도 결정으로 올린다.

**UX 원칙.** 평점 데이터가 없는데 "맛집 1위"·"최고의 맛집" 같은 표현을 쓰지 않는다. 표시하는 근거는 데이터가 실제로 보장하는 것에 한정한다 — 대표음식 근거, 일정 동선에서의 소요, 공식 지정 등록 여부. 아래 두 문구는 형식 예시이며 실제 값은 아니다: "이 지역의 대표음식 ○○을 다루는 음식점", "공식 향토음식/관광 음식점 데이터 등록".

## 7. 스크래핑 정책 (새 제품 결정 — `docs/product/DECISIONS.md`에 항목으로 올렸다)

**기술적으로 가능한 것과 제품이 의존할 만한 것은 다르다.** 상용 플랫폼 스크래핑은 HTML 변경, 봇 차단, CAPTCHA, 서비스 약관, 데이터 이용조건, 콘텐츠 권리 문제로 장기 운영 안정성이 낮다.

**금지.**

- 스크래핑을 음식점·대표음식 데이터의 **핵심 수집 방식으로 쓰지 않는다.**
- 상용 지도·리뷰 플랫폼(네이버지도·카카오맵 등)에서 **평점·리뷰 수·리뷰 본문을 수집하지 않는다.**
- 사용자 요청마다 외부 페이지를 긁는 **런타임 스크래핑 구조를 쓰지 않는다.** 이는 8절의 수집·서비스 분리 원칙과 같은 결론이다.
- 리뷰 본문의 저장·가공·재노출은 저작권·이용권 문제가 추가되므로 제외한다.

**제한적 예외.** 공공기관·지자체 홈페이지에 대표음식 목록이 공식 API나 다운로드 파일 **없이** 공개 HTML로만 제공되는 경우에 한해 보조 수집을 검토할 수 있다. 다음 조건을 **모두** 확인한 경우에만 해당한다.

1. 해당 사이트의 이용조건
2. robots.txt 등 자동 수집 정책
3. 공공누리 또는 별도 데이터 라이선스
4. 수집 가능한 필드와 재사용·표시 범위
5. 요청 빈도가 사이트 운영에 부담을 주지 않는지

예외로 수집할 때도 **초기 데이터 구축 또는 매우 낮은 빈도의 동기화로 제한**하고, 수집한 데이터에는 제공기관·원문 URL·수집일·적용 라이선스를 기록한다.

**공공기관이라는 이유만으로 허용되지 않는다.** 자동 수집과 재사용이 항상 허용되는 것은 아니며 소스별로 개별 확인해야 한다. 3.3절이 실제 사례다 — 값을 확인한 경로가 문서화되지 않은 내부 API이고 페이지 저작권 표기가 All Rights Reserved였으므로, 실사용을 CSV 경로로 옮기고 그 API는 개발·검증용으로 한정했다.

## 8. 수집·정규화·서비스 분리와 캐싱 (기존 결정의 구체화)

`docs/product/DECISIONS.md` 1절의 확정 항목 **"초기 데이터 전략 — 공공 API를 주기 수집·정규화하여 내부 데이터 계층에서 제공"**과 `docs/product/FUNCTIONAL_SPEC.md` 5장 서두("매 사용자 요청의 외부 API 직접 호출을 전제로 하지 않는다")가 이미 이 방향을 정해 두었다. 이 절은 그것을 음식 데이터에 적용하며 **바꾸지 않는다.** 새로 추가하는 것은 아래 두 가지다.

**추가 1 — 소스별 갱신주기.** 과거의 "하루 한 번 수집" 전제는 음식 데이터에 맞지 않는다. 지역N문화는 **비주기 갱신이고 최종 업데이트가 2023-12-21**이다[실측]. 하루에 한 번 받아도 2년 넘게 같은 값이 온다. 반면 TourAPI 음식점은 폐업·운영시간 변경이 잦다. 따라서 원칙은 **"소스별 실제 갱신주기에 맞춘다"**이며, 하루 단위가 기본값인 것이 아니다. 구체적 주기(예: 7·30일)는 소스별로 정하고 source inventory에 남긴다.

**추가 2 — 실패 시 동작.** 외부 API 장애 시 마지막 정상 데이터(last known good)를 계속 제공한다. **동기화 실패가 기존 정상 데이터를 삭제하거나 빈 결과로 덮어쓰지 않는다.** 이는 F-05의 "마지막 정상 데이터 사용 여부와 갱신 시각을 보존한다"와 같은 요구다.

**호출량.** 3.1절의 일일 요청 한도[실측]가 있으므로 전수 수집은 한도 안에서 분할해야 한다. 대표음식 데이터 쪽은 갱신이 드물어 호출량이 문제가 아니다.

**미확인 항목.** 소스별 조건부 요청·증분 동기화 지원 여부, 원천 데이터 버전 확인 가능 여부, 폐업·지정 취소를 반영하는 정책은 확인하지 않았다.

## 9. 데이터 품질과 매칭에서 지켜야 할 것

- 지역명과 행정구역 코드를 **별도로** 보존하고 코드 체계를 명시한다. 지역 코드는 선행 0이 손실되지 않게 다룬다.
- 행정구역 개편과 공급자별 코드 차이를 고려한다. 3.1절의 "구가 있는 시를 시 단위 코드로 조회하면 0건"이 그 실측 사례다.
- 음식명 정규화에서 공백·괄호·접두어·방언·메뉴 변형을 처리하되 **원문 이름을 보존한다.**
- **별칭의 부분 문자열 일치만으로 메뉴 일치를 확정하지 않는다.** 지역, 대표메뉴 필드, 카테고리 등 주변 맥락을 함께 쓴다. 3.4절이 그 근거다 — 전국 공통어(`갈비`·`정식`·`비빔`)가 단순 일치에서 상위로 올라온다.
- 영업시간이 없다는 이유만으로 폐업·영업 불가로 판정하지 않는다. 결측은 결측으로 다룬다(운영시간·휴무 결측은 후보 제외라는 별도 확정 규칙이 있다).
- 좌표계와 위·경도 순서를 확인한 뒤 거리를 계산한다.
- 응답의 누락·중복·문자 인코딩·잘못된 좌표를 **수집 단계에서 기록하고 격리**할 수 있어야 한다. 3.2절의 CP949 인코딩과 3.1절의 `"10:00~21::30"` 오타가 실제 사례다.
- 원천별 이용약관·라이선스·출처 표시 의무·저장 가능 기간을 source inventory에 기록한다. 무료 API 정책과 쿼터는 변할 수 있으므로 구현 시점의 공식 문서를 다시 확인한다.

## 10. 기술 설계의 경계 — 무엇을 개발 에이전트에게 남기는가

`.agents/pm/AGENT.md`는 "기술 구현 방식은 개발 에이전트가 제안한다"고 정한다. 외부 참고 문서에는 `LocalFood` TypeScript 인터페이스와 adapter 설계가 구체적인 코드로 들어 있으나 **이 문서는 그것을 확정으로 채택하지 않는다.**

| 이 문서가 정하는 것 (제품 요구사항)                                                             | 개발 에이전트가 정하는 것 (구현 결정)                         |
| ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| 대표음식 레코드는 **출처**(제공기관·데이터셋·소스 유형·원문 URL)를 보존해야 한다                | 그것을 어떤 타입·필드명·테이블로 표현할지                     |
| **신뢰도**를 보존해야 한다. 더 좋은 데이터가 나왔을 때 교체·우선순위 조정이 가능해야 한다       | 신뢰도의 저장 형태, 병합·교체 알고리즘                        |
| **별칭**을 보존해야 한다. 원문 이름도 함께 남는다                                               | 별칭 정규화 규칙의 구현, 검색 토큰 설계                       |
| **동기화 시각**을 보존해야 한다. 마지막 정상 데이터와 그 시점을 구분할 수 있어야 한다           | 캐시 계층, TTL 구현, 증분 동기화 방식                         |
| 하나의 음식에 **여러 근거**를 연결할 수 있어야 한다                                             | 단일 필드 확장 / 배열 / 별도 evidence 테이블 중 무엇으로 할지 |
| 수집·정규화·서비스가 **분리**되어야 한다. 추천 서비스가 개별 지자체 API 형식을 직접 알지 않는다 | adapter 인터페이스, 오류 처리, 격리 저장 구조                 |
| 수집 단계에서 이상 데이터를 **기록·격리**할 수 있어야 한다                                      | 검증 파이프라인의 구현                                        |

즉 이 문서가 인터페이스 코드를 박아 두면 개발 에이전트의 제안 권한을 침범하고, 동시에 제품 문서가 구현 변경마다 갱신돼야 하는 상태가 된다. 그래서 위 왼쪽 열까지만 정하고 **구체적인 타입·스키마·adapter는 employee agent가 구현 계획에서 제안한다.**
