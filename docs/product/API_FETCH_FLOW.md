# MVP 데이터 조회 흐름

## 목적

MVP는 모든 지원 지역의 모든 데이터를 한 번에 조회하지 않는다. 먼저 이동시간과 관광지로 1차 후보를 좁힌 뒤, 그 후보 지역에만 음식점 **목록 기본 정보**를 연결한다. 사용자가 후보를 선택할 때는 이미 관광지·식당 기본 정보가 연결돼 있어야 하며, 음식점 상세는 사용자가 해당 음식점을 열 때만 조회한다.

TourAPI는 서버가 `TOUR_API_SERVICE_KEY`로 호출한다. 브라우저에는 서비스 키나 원시 응답을 전달하지 않는다.

## 1단계: 관광지 기반 1차 후보 검색

사용자가 `갈 수 있는 곳 찾기`를 누르면 서버가 다음만 조회·계산한다.

1. 입력한 출발 지역과 지원 여행 지역의 KTDB 자동차 일반 예상 이동시간
2. 지원 여행지별 최신 관광지 데이터와 관심사 분류
3. 왕복 이동시간, 휴식 시간, 관광지 1시간 체류 규칙으로 만들 수 있는 관광 계획의 수

왕복 후 남는 시간에 관심사 관광지를 여러 곳 배치할 수 있는 지역만 **1차 후보**로 남긴다. 이 단계에서는 음식점·대표음식 정보를 아직 조회하지 않는다.

1차 후보의 관광지 데이터와 KTDB 지역 간 일반 예상 이동시간은 검색 스냅샷에 보존한다.

## 2단계: 1차 후보의 음식점 연결

같은 검색 요청 안에서 서버는 **1차 후보 지역에 대해서만** 다음 최신 데이터를 조회한다.

1. TourAPI 음식점 목록의 기본 정보(식별자, 이름, 주소·좌표, 분류, 대표 이미지 등)
2. 지역 대표음식 근거와 공식 지정 여부를 확인하는 공공데이터

서버는 대표음식 근거가 있는 음식점 기본 정보를 식사 블록에 연결한다. 검색 단계에서는 메뉴·운영시간·휴무·상세 정보를 조회하거나 식사 시간 적합성을 판정하지 않는다. 후보가 여럿이면 공식 지정 여부와 안정적인 장소 ID 순으로 하나를 고른다. 원천별 역할과 연결 규칙은 [대표음식·음식점 데이터 정책](FOOD_DATA_POLICY.md)을 따른다.

점심·저녁 블록에 연결할 기본 음식점 정보와 대표음식 안내가 있는 지역만 최종 추천 후보로 남긴다. 최종 후보에는 관광지·음식점 기본 정보와 선정 근거가 연결돼 있으며, 이를 검색 스냅샷에 함께 보존한다.

## 3단계: 목적지 선택과 계획 생성

사용자가 최종 후보 중 한 지역을 선택하면 새 외부 API를 호출하지 않는다. 연결된 검색 스냅샷으로 점심·저녁과 관광지를 포함한 1박 2일 참고 계획을 만든다. 관광지·음식점은 각각 1시간이며, 여행지 내부 이동시간은 계산하지 않는다.

## 4단계: 음식점 상세 조회

사용자가 일정의 음식점을 클릭하면 서버 Route Handler가 해당 TourAPI 콘텐츠 ID로 `detailIntro2`를 호출한다. 이 요청에서만 메뉴·운영시간·휴무 등 상세 정보를 정규화해 보여 준다. 상세 조회 결과는 음식점의 현재 정보 확인용이며, 이미 만든 검색 스냅샷의 후보 순서·식사 배치·일정 시간표를 변경하지 않는다.

## 실패 처리

- 1단계 관광지 조회 또는 KTDB 지역 간 일반 예상시간이 없으면 해당 지역을 1차 후보에서 제외한다.
- 2단계에서 점심 또는 저녁에 연결할 기본 음식점 또는 대표음식 안내를 찾지 못하면 해당 지역을 최종 추천 후보에서 제외한다.
- 4단계 상세 조회 실패는 음식점 상세 화면의 재시도 상태이며, 여행 계획 전체를 실패로 바꾸지 않는다.
- API 장애와 정상 응답이지만 조건을 충족하는 데이터가 없는 경우를 구분한다.
- 정적 PoC 데이터, 임의 이동시간, 빈 음식점 fallback으로 대체하지 않는다.
