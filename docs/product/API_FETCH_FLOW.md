# MVP 데이터 조회 흐름

## 원칙

전국 TourAPI 분류 지역 프로필 JSON과 KTDB 2024 시간표를 검색에 재사용한다. 사용자 검색 중 전국 관광·식당을 조회하지 않는다. 정기 프로필 수집은 하루 1회를 목표로 별도 수행하며 서버 시작마다 전체 수집하지 않는다. 실제 생성일을 표시하고 자동 갱신되지 않은 파일을 당일 정보라고 표현하지 않는다.

TourAPI는 서버 전용 `TOUR_API_SERVICE_KEY`로 호출한다. 키·원시 응답은 브라우저·계획 저장본에 포함하지 않는다. 완료된 기준선은 [2단계 기획서](MVP_PHASE_2.md)이며 다음 구현의 상세 보강·편집 조회 계약은 [서비스 고도화 기획서](SERVICE_ENHANCEMENT_SPEC.md) E3~E4가 단일 기준이다. 이는 승인된 구현 방향이며 구현 완료를 의미하지 않는다.

## 1. 검색

다음 구현의 사전 수집은 [관광 데이터·목적 적합성 기획서](TOURISM_RECOMMENDATION_UPGRADE.md) D1~D3를 따른다. 공식 분류/지역 코드 확인 → 새 분류별 전국 관광지 목록 조회 → 지역별 정규화 → 동일 기준월의 지역별 중심 관광지 API 조회 → 원천 연결/중복 정리 → 정상 JSON 묶음 검증/배포 순서다. 기존 목록은 `TOUR_API_SERVICE_KEY`, 중심 목록은 `CENTRAL_ATTRACTION_API_SERVICE_KEY`를 서버 전용으로 사용한다. 분류 코드와 조회/저장/검색 소비를 함께 교체한다.

관광지 프로필과 중심 자료 모두 사전 준비이며 서버 시작·빌드·사용자 검색에서 재수집하지 않는다. 중심 자료는 기준월 성공분을 재사용하며 상세 일괄 호출은 하지 않는다. 정상본 보존·원천 오류 구분·예산·재시도/체크포인트는 D2의 계약이 단일 기준이다. 예약 자동 수집·신규 영속 DB는 이번 구현의 필수 범위가 아니다.

입력을 서버 검증하고 KTDB·법정동 매핑·선택 관심사 프로필로 권역을 합친다. 출발 권역은 제외한다. 각 지역의 관광·식사·휴식 초안을 공통 시간 엔진으로 계산해 최대 3곳을 제시한다. 관광 목록·중심 관광지·음식점·관광 상세 외부 API는 모두 호출하지 않는다. 신규 목적 적합성 근거도 사전 JSON에서 읽는다.

스냅샷에는 입력, 그룹·대표존·포함 매핑, 시간표 기준, 프로필 생성일, 실제 초안·후보 근거를 보존한다. 순위는 실제 초안 품질에 기반하고 원천 관광지 총개수에 기반하지 않는다.

## 2. 목적지 선택·음식점

실제 관광지가 있는 매핑 하위 지역을 우선해 최대 3지역만 조회한다. 지역당 100개씩 최대 3페이지, 동시성 최대 2, 전체 최대 9호출이다. 일부 페이지만 조회했다면 전체 목록인 것처럼 표시하지 않는다. 관광지역이 없으면 선택 그룹 매핑에서 동일 상한으로 조회한다.

콘텐츠 ID·상호·주소·좌표·분류·이미지·수집일을 정규화하고 로컬 지역N문화·모범음식점 보조 캐시를 연결한다. 현지 식사에 근접성·중복 방지·보조 근거 순으로 식당과 대체 후보를 배정한다. 이동 중 자유 식사는 배정 대상이 아니다. 상세·메뉴·운영시간을 목록별로 호출하지 않는다.

부분 실패 시 성공 목록을 유지하고 조회 실패 범위를 안내한다. 전체 실패해도 관광·식사 시간 블록은 유지하며 목록만 재시도한다. 이전 검색/목적지 응답은 현재 상태를 덮어쓰지 않는다.

## 3. 선택 계획 보강·클릭 상세

- 음식점 클릭: 콘텐츠 ID로 기존 `detailIntro2`를 요청해 메뉴·운영·휴무를 정규화한다.
- 관광지는 선택 계획에 실제 배치된 소수 항목만 E3 자동 보강 예산으로 공통·소개 상세를 요청한다. 검색 후보 전체·전국 상세는 조회하지 않는다. 사진·소개·주소·제공 운영정보를 표시하고 별도 이미지 목록 일괄 수집은 하지 않는다.
- 클릭 상세는 진행 중인 자동 요청과 캐시를 공유하며 같은 항목을 중복 조회하지 않는다. 자동/명시적 재시도·동시성·시간 초과·조회 상한은 E3의 계약을 따른다. 새 키나 영속 저장소를 요구하지 않는다.
- 상세 캐시/상태는 콘텐츠 ID·유형으로 분리한다. A 닫기 후 B 열기에서 A의 늦은 응답은 무시한다. 실패·결측은 해당 상세에만 표시하며 후보·계획을 재생성하지 않는다.

## 4. 편집·저장

관광 편집·식당 배정/교체는 기존 후보·좌표와 공통 시간 엔진으로 현지 이동까지 재계산한다. 개인 장소는 직접 입력이며 지오코딩/외부 장소 검색을 호출하지 않는다. 식당 교체는 이미 받은 대체 후보를 재사용한다. 새 조회가 필요하면 식사 영역만 명시적으로 재시도하며 선택 식당을 덮어쓰지 않는다. 식당 응답의 계획 ID와 편집 시점을 대조해 늦은 응답이 최신 편집을 덮어쓰지 않게 한다. 저장본 복원은 자동 검색·자동 외부 조회를 유발하지 않으며 클릭 상세 또는 명시적 방문정보 확인으로만 새로 조회할 수 있다. 관광 교체·추가마다 자동 상세 전체 작업을 다시 시작하지 않는다.

## 실패와 상한

요청 오류, 시간 조건 불가, 원천 결측, 외부 API 장애를 구분한다. 제한·부분 수집은 사실대로 알린다. 취소·시간 초과·늦은 응답 격리를 적용한다. 키 없는 환경에서 가짜 음식점·PoC 시간으로 성공을 만들지 않는다. 무료 API 한도 때문에 전국 상세 호출·유료 인프라를 필수 의존성으로 도입하지 않는다.
