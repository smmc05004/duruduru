# MVP 데이터 조회 흐름

## 목적

MVP는 서울특별시(현재 KTDB 서울 중구 존)에서 전국 252개 지역권을 목적지 후보로 쓰되, 252개 지역의 관광지·음식점을 한 번에 조회하지 않는다. TourAPI 공식 분류 콘텐츠로 하루 1회 만든 JSON 지역 프로필 인덱스를 먼저 쓰고, 서울 출발 지역권의 왕복 일반 예상시간으로 시간 적합 후보를 좁힌다. 매핑 가능·선택 관심사 근거 수 충족 후보에만 음식점 **목록 기본 정보**를 제한 동시성·페이지네이션으로 연결한다.

TourAPI는 서버가 `TOUR_API_SERVICE_KEY`로 호출한다. 브라우저에는 서비스 키나 원시 응답을 전달하지 않는다.

## 1단계: 전국 시간 적합 후보 필터

사용자가 `갈 수 있는 곳 찾기`를 누르면 서버가 다음만 조회·계산한다.

1. 고정된 서울 출발 지역권과 전국 252개 여행 지역권의 KTDB 자동차 일반 예상 이동시간
2. 왕복 이동시간으로 시간 적합한 지역권 목록
3. 매핑 가능·선택 TourAPI 관심사 근거 수 충족 지역 프로필 목록

왕복 후 남는 시간 기준을 통과하고, TourAPI 법정동 매핑과 선택 카테고리 최소 근거 수를 충족한 지역만 **시간 적합 후보**로 남긴다. 이 단계에서는 관광지·음식점 API를 조회하지 않는다.

KTDB 지역 간 일반 예상 이동시간과 시간 적합 후보 목록은 검색 스냅샷에 보존한다.

## 2단계: 시간 적합 후보의 관광지·음식점 연결

같은 검색 요청 안에서 서버는 **시간 적합 후보 지역에 대해서만** 다음 최신 데이터를 조회한다. 요청은 제공자 한도에 맞춘 제한 동시성과 페이지네이션을 사용하며, 252개 지역권을 동시에 조회하지 않는다.

1. TourAPI 음식점 목록의 기본 정보(식별자, 이름, 주소·좌표, 분류, 대표 이미지 등)

서버는 음식점 목록 기본 정보를 검색 스냅샷에 연결한다. 목적지 선택 뒤 일정 식사 블록에서는 일일 인덱스 또는 준비된 정적 공식 원천의 지역N문화 대표음식, 모범음식점 공식 지정·음식 종류, TourAPI 목록 기본 정보, 안정적인 콘텐츠 ID 순으로 고른다. 이 근거는 목적지 후보 제외 조건이 아니다. 검색 단계에서는 메뉴·운영시간·휴무·상세 정보를 조회하거나 식사 시간 적합성을 판정하지 않는다. 원천별 역할과 연결 규칙은 [MVP 음식점 데이터 정책](FOOD_DATA_POLICY.md)을 따른다.

지역 프로필 관광지·점심·저녁 블록에 연결할 기본 음식점 정보가 있는 지역을 평가해 최종 추천 **3곳**을 선정한다. 최종 후보에는 지역 프로필 근거·음식점 기본 정보·TourAPI 법정동 코드·KTDB 존 매핑을 검색 스냅샷에 함께 보존한다.

## 3단계: 목적지 선택과 계획 생성

사용자가 최종 후보 중 한 지역을 선택하면 새 외부 API를 호출하지 않는다. 연결된 검색 스냅샷으로 점심·저녁과 관광지를 포함한 1박 2일 참고 계획을 만든다. 관광지·음식점은 각각 1시간이며, 여행지 내부 이동시간은 계산하지 않는다.

## 4단계: 음식점 상세 조회

사용자가 일정의 음식점을 클릭하면 서버 Route Handler가 해당 TourAPI 콘텐츠 ID로 `detailIntro2`를 호출한다. 이 요청에서만 메뉴·운영시간·휴무 등 상세 정보를 정규화해 보여 준다. 상세 조회 결과는 음식점의 현재 정보 확인용이며, 이미 만든 검색 스냅샷의 후보 순서·식사 배치·일정 시간표를 변경하지 않는다.

## 실패 처리

- 1단계 KTDB 지역 간 일반 예상시간이 없으면 해당 지역을 시간 적합 후보에서 제외한다.
- 프로필 인덱스에 TourAPI 법정동 매핑 또는 선택 카테고리 최소 근거 수가 없으면 해당 지역을 추천에서 제외한다.
- 2단계에서 점심 또는 저녁에 연결할 기본 음식점 정보를 찾지 못하면 해당 지역을 최종 추천 후보에서 제외한다.
- 4단계 상세 조회 실패는 음식점 상세 화면의 재시도 상태이며, 여행 계획 전체를 실패로 바꾸지 않는다.
- API 장애와 정상 응답이지만 조건을 충족하는 데이터가 없는 경우를 구분한다.
- 정적 PoC 데이터, 임의 이동시간, 빈 음식점 fallback으로 대체하지 않는다.
