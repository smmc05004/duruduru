# MVP 데이터 조회 흐름

## 목적

MVP는 서울특별시(KTDB 서울 중구 존) 또는 부산광역시(KTDB 부산 중구 존)에서 전국 252개 지역권을 목적지 후보로 쓰되, 252개 지역의 관광지·음식점을 사용자 검색 중 한 번에 조회하지 않는다. TourAPI 공식 분류 콘텐츠로 하루 1회 만든 JSON 지역 프로필 인덱스를 먼저 쓰고, 선택 출발 지역권의 왕복 일반 예상시간으로 시간 적합 후보를 좁힌다. 후보 표시는 광역시의 시도 단위 또는 도 지역의 시·군 단위로 묶는다. 음식점 **목록 기본 정보**는 사용자가 최종 목적지 한 곳을 선택했을 때에만 조회한다.

TourAPI는 서버가 `TOUR_API_SERVICE_KEY`로 호출한다. 브라우저에는 서비스 키나 원시 응답을 전달하지 않는다.

## 1단계: 전국 시간 적합 후보 필터

사용자가 `갈 수 있는 곳 찾기`를 누르면 서버가 다음만 조회·계산한다.

1. 선택한 서울 또는 부산 출발 지역권과 전국 252개 여행 지역권의 KTDB 자동차 일반 예상 이동시간
2. 왕복 이동시간으로 시간 적합한 지역권 목록
3. 매핑 가능·선택 TourAPI 관심사의 서로 다른 관광지 콘텐츠 ID가 3개 이상인 지역 프로필 목록

왕복 후 남는 시간 기준을 통과하고, TourAPI 법정동 매핑과 선택 카테고리의 서로 다른 관광지 콘텐츠 ID 3개 이상 조건을 충족한 지역만 **시간 적합 후보**로 남긴다. 이 단계에서는 관광지·음식점 API를 조회하지 않는다.

KTDB 지역 간 일반 예상 이동시간과 시간 적합 후보 목록은 검색 스냅샷에 보존한다.

## 2단계: 목적지 추천

서버는 1단계의 시간 적합 후보를 지역 프로필의 공식 관심사 근거와 시간 적합성으로 정렬해 최종 추천 **3곳**을 선정한다. 특별시·광역시·특별자치시는 내부 구를 합쳐 한 후보만 만들고, 도 지역은 시·군 단위를 유지한다. 이 단계에서는 TourAPI 음식점 목록·상세 API를 호출하지 않는다.

최종 후보에는 지역 프로필 근거, TourAPI 법정동 코드, KTDB 존 매핑과 일반 예상 이동시간을 검색 스냅샷에 보존한다.

## 3단계: 목적지 선택 후 음식점 연결·계획 생성

사용자가 최종 후보 중 한 지역을 선택하면 서버는 그 **선택 지역 한 곳**의 TourAPI 음식점 목록 기본 정보(식별자, 이름, 주소·좌표, 분류, 대표 이미지 등)만 조회한다. 목록 조회는 제공자 한도에 맞춘 제한 동시성과 페이지네이션을 적용하되, 목록의 음식점 상세를 병렬로 조회하지 않는다.

클라이언트는 식당 목록을 불러오는 진행 상태를 보인다. 서버가 목록을 받으면 지역 프로필 관광지와 목록 기본 정보를 연결해 점심·저녁과 관광지를 포함한 1박 2일 참고 계획을 생성한다. 이때 서버는 정기 수집한 지역N문화 음식 키워드와 모범음식점 인증 캐시를 로컬에서 조회한다. 지역N문화 관련 음식점 필드를 직접 식당으로 추천하거나 매칭하지 않는다. TourAPI 목록과 인증 캐시는 전화번호 또는 정규화한 상호·주소가 모두 일치할 때만 결합한다.

식사 블록의 음식점은 대표음식 문화 키워드 일치, 모범음식점 공식 지정·음식 종류, TourAPI 목록 기본 정보, 안정적인 콘텐츠 ID 순으로 고른다. 네 식사 칸에는 서로 다른 콘텐츠 ID를 우선 배정하며, 음식점이 부족한 칸에는 임의·중복 식당을 넣지 않고 `추천할 식당을 더 찾지 못했어요`를 표시한다. 이 근거는 목적지 후보 제외 조건이 아니다. 메뉴·운영시간·휴무·상세는 이 단계에서 조회하거나 식사 시간 적합성에 사용하지 않는다. 원천별 역할과 연결 규칙은 [MVP 음식점 데이터 정책](FOOD_DATA_POLICY.md)을 따른다.

관광지·음식점은 각각 1시간이며, 여행지 내부 이동시간은 계산하지 않는다. 선택 지역의 음식점 목록을 얻지 못하면 관광 계획을 대체 식당으로 채우지 않는다. 식사 정보 수집 실패를 별도로 안내하고 재시도할 수 있게 한다.

## 4단계: 음식점 상세 조회

사용자가 일정의 음식점을 클릭하면 서버 Route Handler가 해당 TourAPI 콘텐츠 ID로 `detailIntro2`를 호출한다. 이 요청에서만 메뉴·운영시간·휴무 등 상세 정보를 정규화해 보여 준다. 상세 조회 결과는 음식점의 현재 정보 확인용이며, 이미 만든 검색 스냅샷의 후보 순서·식사 배치·일정 시간표를 변경하지 않는다.

## 실패 처리

- 1단계 KTDB 지역 간 일반 예상시간이 없으면 해당 지역을 시간 적합 후보에서 제외한다.
- 프로필 인덱스에 TourAPI 법정동 매핑이 없거나 선택 카테고리의 서로 다른 관광지 콘텐츠 ID가 3개 미만이면 해당 지역을 추천에서 제외한다.
- 3단계에서 선택 지역의 음식점 목록을 가져오지 못하면 목적지 추천 결과는 유지하고, 식사 정보를 불러오지 못한 상태와 재시도를 표시한다. 임의 음식점으로 대체하지 않는다.
- 4단계 상세 조회 실패는 음식점 상세 화면의 재시도 상태이며, 여행 계획 전체를 실패로 바꾸지 않는다.
- API 장애와 정상 응답이지만 조건을 충족하는 데이터가 없는 경우를 구분한다.
- 정적 PoC 데이터, 임의 이동시간, 빈 음식점 fallback으로 대체하지 않는다.
