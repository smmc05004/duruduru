# 서비스 고도화 1~4 기능 기획서

> 상태: PM 작성·총괄 기획 리뷰 완료 / 기준일: 2026-09-08. E1~E4 순차 구현 승인, 코드 구현·검증·병합은 아직 미완료.
> 승인 범위: 사용자가 승인한 고도화 제안의 **1. 비교할 가치가 있는 목적지 3안, 2. 하루 관광 구성, 3. 방문 판단 정보, 4. 내 계획 편집**이다. 로드맵의 운영 보강 등을 네 번째 기능으로 해석하지 않는다.
> 전체 방향은 [고도화 계획](SERVICE_ENHANCEMENT_PLAN.md), 구현 기준선은 [완료된 MVP 2단계](MVP_PHASE_2.md)다. 이 문서는 아래에서 명시한 교체 정책의 단일 기준이며, 나머지 MVP 규칙은 유지한다. 기능 명세 작성은 구현 완료를 의미하지 않는다.

## 1. 목적·경계·진행 순서

목적지를 모르는 사용자가 같은 입력으로 서로 비교할 만한 여행을 발견하고, 하루 구성을 이해한 뒤 자기 여행에 맞게 수정하도록 한다. 필수 입력은 늘리지 않는다. 검색 → 최대 3개 목적지 → 한 지역 선택 → 관광·식사 계획 흐름은 유지한다.

| 단계 | 기능 ID | 결과                                           | 선행 조건                    |
| ---- | ------- | ---------------------------------------------- | ---------------------------- |
| 1    | E1      | 의미가 다른 목적지 3안과 계산 근거             | 기존 지역 프로필·KTDB 시간표 |
| 2    | E2      | 시설 중복 억제·오전/오후 근접 묶음·명시적 여유 | E1 병합                      |
| 3    | E3      | 설명·허용 사진·휴무 원문·주소 및 지도 연결     | E2 병합, 기존 TourAPI 키     |
| 4    | E4      | 날짜·순서·추가·개인 장소·시각 고정 편집        | E3 병합                      |

각 단계는 독립 작업 계획 → 구현·검증 → 한글 PR → CI 확인·병합 순으로 진행한다. 이후 단계의 코드를 먼저 섞어 완료로 표시하지 않는다. MVP의 검증 생략은 종료된 MVP 범위에 한하며, 이번 고도화의 수용 기준은 실제 검증해야 한다. 기존 검색만 흉내 낸 E2E 통과를 전체 흐름 검증이라고 쓰지 않는다.

### 유지하는 제약

- 서울/부산 출발, 자차, KST 기준 다음날 복귀하는 1박 2일, 공식 관심사 1개 이상.
- 출발·귀가 이동은 24시간 허용. 관광·현지 자유활동은 07:00~21:00이며 휴식은 야간 현지 체류 구간이다.
- KTDB 2024의 같은 편도 일반 예상시간을 왕복에 각각 적용한다. 운전·식사·관광은 겹치지 않는다. 지역 안 도로 경로·이동시간·직선거리의 시간 환산은 하지 않는다.
- 점심·저녁 60분, 여행 범위에 들어오는 끼니만 배치한다. 이동 중 식사는 운전 외의 경과시간이다. 음식점은 지역 선택 후 조회하며, 서로 다른 식당·부족 안내·부분 실패 보존을 유지한다.
- TourAPI 공식 관광 분류와 기존 지역 매핑을 사용한다. 결측 때문에 모든 지역을 지원한다고 주장하지 않는다. 출발 그룹은 후보에서 제외한다.
- 새로운 유료 API, 새로운 키, DB, 로그인, LLM, 도로 길찾기, 예약, 숙소 추천, 평점·인기 추정은 추가하지 않는다.
- 음식점 추천 알고리즘 자체의 고도화, 여행 출력·공유, 출발지·기간 확대, 자동 수집 운영은 별도 후속이다. E4의 숙소는 **사용자가 입력하는 메모**이지 숙소 검색·추천이 아니다.

이 문서의 거리 문턱·여유 분·조회 상한은 공공기관의 보증값이 아닌 제품 휴리스틱이다. UI에는 실제 동선 최적화나 운영 보증으로 표현하지 않는다.

## 2. E1 — 비교할 가치가 있는 목적지 3안

### 사용자 결과

기존 결과 카드 최대 3개에 다음 역할을 하나씩 붙인다. 같은 목적지 그룹을 반복하지 않는다. 필수 질문이나 별도 선호도 입력 없이 현재 입력으로 생성한다.

| 역할 ID    | 카드 제목                 | 역할별 우선순위                                                                                                                                       |
| ---------- | ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `easy`     | 이동 부담을 줄인 여행     | 왕복 운전 분 오름차순 → 충족 관심사 수 내림차순 → 관광 수 내림차순 → 세부 분류 수 내림차순                                                            |
| `interest` | 관심사를 깊게 즐기는 여행 | 충족 관심사 수 내림차순 → 세부 분류 수 내림차순 → 관광 수 내림차순 → 왕복 운전 분 오름차순                                                            |
| `relaxed`  | 여유롭게 머무는 여행      | 근접성 비교 가능 후보 우선 → 현지 낮 자유시간 분 내림차순 → 당일 연속 관광지 평균 직선거리 오름차순 → 충족 관심사 수 내림차순 → 왕복 운전 분 오름차순 |

모든 비교값은 **실제 생성한 초안**의 값이다. 유효 거리 쌍이 없는 후보는 해당 거리 비교에서 마지막으로 두며 제외하지 않는다. 모든 최종 동점은 `groupId` 사전순이다. 원천 관광지 총개수, 유명도, 음식점 유무는 점수에 넣지 않는다.

근접성 비교 가능은 당일 연속 관광지 쌍이 1개 이상이고 그 쌍 모두의 좌표가 유효한 경우다. `distancePairCount`와 `validDistancePairCount`를 근거에 보존한다. 일부 쌍의 좌표가 빠져 평균 거리가 짧아 보이는 후보가 여유 역할에서 부당하게 앞서지 않게 한다. 남은 후보가 모두 비교 불가이면 자유시간·관심사·왕복시간·ID로 선택하고 `장소 간 근접성은 확인하지 못했어요`로 표시한다.

### 선택 절차

1. 기존 입력·지역·분류·시간 조건으로 실제 초안이 가능한 모든 그룹을 만든다. 기본 관광 3~6개·하루 최대 3개와 관광일 최소 자유시간 30분은 유지한다. E2 이후에는 E2 엔진으로 다시 계산한다.
2. `easy` 정렬 첫 후보를 선택한다.
3. 선택한 그룹을 제외하고 `interest` 정렬 첫 후보를 선택한다.
4. 앞의 그룹을 제외하고 `relaxed` 정렬 첫 후보를 선택한다.
5. 가능한 후보가 1~2곳이면 그 수만 보여 준다. 더 먼 곳·관심사가 부족한 곳을 임의 생성하지 않는다. 0곳은 기존 시간/분류 부족 안내다.

역할은 순차 선택의 목적이며 전국에서 각각 절대 최상위라는 뜻이 아니다. 예를 들어 세 번째 카드를 ‘가장 여유로운 지역’이라고 표현하지 않는다. 서로 다른 역할이라도 동일한 지표 값일 수 있으며 그 경우 “세 후보의 예상 이동시간은 같아요”처럼 사실만 표시하고 차이를 꾸미지 않는다. 관광 수를 억지로 줄여 자유시간 점수를 높이지 않는다.

카드에는 역할 + 지역명 + 왕복 일반 예상시간 + 실제 관광지 수 + 충족 관심사 + 현지 낮 자유시간을 간결히 표시한다. 선택 관심사 일부만 충족하면 `역사·문화 중 역사 포함`처럼 누락을 숨기지 않는다. 원천 코드·세부 점수는 펼쳐보기다.

### 계약·수용 기준

- `Candidate.recommendation`에 `role`, `algorithmVersion`, 비교에 사용한 유한 수치 및 결측 거리, 실제 설명 근거를 보존한다. `reasons`는 이 값으로 생성한다. 역할 때문에 `preview`와 실제 선택 결과를 다르게 생성하지 않는다.
- 동일 입력·데이터 버전은 검색 ID/조회 시각과 관계없이 같은 후보·역할·초안을 반환한다.
- 가까운 A, 분류가 다양한 B, 자유시간이 긴 C의 고정 데이터에서 A/B/C가 순서대로 선택되는 단위 검증을 제공한다. 역할별 단독 우승자가 중복되어도 다른 그룹을 차례로 선택한다.
- 서울 출발에 서울 모든 구 제외, 부산 출발에 부산 제외, 수원 일반구 중복 제거가 유지된다.
- 검색에서 관광 상세·음식점 외부 호출은 0회다. 1~2곳 결과와 모든 지표 동점도 검증한다.

## 3. E2 — 하루 관광 구성과 여유

### 시설 중복을 보수적으로 억제

기존 동일 콘텐츠 ID 제거와 `정규화 이름·주소 동일 + 좌표 100m 이내`의 강한 중복 억제는 유지한다. 추가 시설 묶음은 다음을 **모두** 만족하는 경우만 만든다.

- 비어 있지 않은 정규화 주소가 완전히 같음.
- 유효 좌표 사이가 300m 이내.
- 이름을 공백·괄호·문장부호로 나눈 토큰 중 3글자 이상인 동일 토큰이 있음. `관광지`, `박물관`, `미술관`, `문화재`, `기념관`, `전시관`, `공원`, `유적지`, `전망대`, `체험관`, `문화센터` 등 일반 시설명 토큰은 근거에서 제외한다. 목록은 단위 검증과 함께 관리한다.

예: 같은 주소·가까운 좌표의 `공산성 광복루`, `공산성 쌍수정`은 시설 의심 묶음이 된다. 다른 주소의 두 박물관이나 좌표만 가까운 장소는 묶지 않는다. 토큰 없는 이름은 추측해서 분해하지 않는다.

묶음은 ID순 대표를 기준으로 모든 새 구성원이 대표뿐 아니라 기존 구성원 모두와 위 조건을 충족해야 추가한다. A-B, B-C만 가까운 연결고리로 넓은 영역을 하나로 합치지 않는다. 원본을 삭제하거나 공공기관의 공식 시설 ID인 것처럼 표시하지 않는다.

엄격한 제외는 기존 동일 ID·강한 중복에만 적용한다. 위 토큰 기반 시설 의심은 **약한 근거**이므로 해당 묶음이 이미 여행에 사용되었으면 미사용 시설 후보를 우선하는 감점을 적용한다. 감점은 미충족 관심사·세부 분류·근접성보다 앞서며, 각 선택 풀에 대안이 없으면 선택을 허용하고 `같은 시설 안 장소가 포함될 수 있어요`를 안내한다. 의심만으로 지역을 탈락시키거나 시설 수를 확인된 사실로 표시하지 않는다. 대표 선택은 미충족 관심사 수 → 미사용 세부 분류 → 콘텐츠 ID 순이다.

원본의 묶인 장소는 교체·추가 후보에 보존하며 사용자의 명시적 추가는 안내 후 허용한다. 잘못 묶인 사례를 검토해 보정할 경우 `정렬된 콘텐츠 ID 쌍 + same-facility/independent + 확인 근거 + 확인일`의 소규모 보정 계약을 사용한다. 근거 없는 기본 보정은 만들지 않는다. 확인된 same-facility만 자동 여행 전체 한 장소를 엄격 적용하며, independent는 약한 감점을 해제한다. 보정은 프로필 원본 삭제가 아니고 규칙 버전에 포함한다.

### 오전·오후 공간 묶음

실제 시간 슬롯에서 12:00 이전 시작은 오전, 이후 시작은 오후로 구분한다. 각 날짜·오전/오후마다 새 묶음을 시작한다. 관광일 최대 3곳은 유지한다.

1. 첫 장소는 이미 사용한 시설 의심 묶음 회피 → 미충족 관심사 수 내림차순 → 당일 미사용 세부 분류 우선 → 콘텐츠 ID로 고른다.
2. 같은 반일의 다음 장소는 첫 장소에서 직선거리 5km 이내인 미사용 후보가 있으면 그 풀에서 고른다. 시설 의심 반복 회피 → 미충족 관심사 → 당일 미사용 세부 분류 → 직전 장소 거리 → ID 순이다.
3. 5km 안 후보가 없으면 유효 좌표가 있는 나머지에서 시설 의심 반복 회피 → 첫 장소와 가까운 순 → 미충족 관심사 → 세부 분류 → ID로 고르고 `장소가 떨어져 있어 위치 확인이 필요해요`를 근거에 남긴다. 좌표 후보도 없으면 시설 의심 반복 회피 → 관심사 → 세부 분류 → ID로 고른다.
4. 첫 장소 좌표가 없으면 근접 묶음 주장을 하지 않고 시설 의심 반복 회피 → 관심사 → 세부 분류 → ID를 적용한다. 좌표 결측으로 전체 계획을 실패시키지 않는다.

5km는 가까운 장소를 우선하는 선정 범위이지 도보 가능 거리·도로 접근성·실제 이동 가능 보증이 아니다. 다른 반일/날짜는 다른 공간 묶음을 시작할 수 있다. 여러 먼 권역을 잇는 실제 동선을 계산했다고 표현하지 않는다.

### 여유 블록

- 같은 낮 가용 구간에서 관광이 연속되면 사이에 **최소 15분 자유시간**을 확보한다. 식사·밤 휴식이 이미 사이에 있으면 별도 15분을 중복 추가하지 않는다. 남은 시간은 기존처럼 자유시간으로 둔다.
- 관광하는 날 자유시간 총합 최소 30분은 유지하며 위 15분들이 이 합에 포함된다. 30분을 다시 추가 차감하지 않는다.
- 이 블록은 `여유시간`이고 근거는 `이동·주차·대기 등에 사용할 수 있는 여유예요. 실제 이동시간을 계산한 값은 아니에요.`다. 장소 간 15분 이동이라고 표시하지 않는다.

## 4. E3 — 추천 근거와 방문 판단 정보

검색 결과에는 외부 상세를 새로 호출하지 않는다. 프로필 제목·분류·주소로 대표 장소 최대 3개와 E1/E2 근거를 먼저 보여 준다. 설명이 없으면 분류 기반 설명임을 유지하고 실제 장소 소개문을 지어내지 않는다.

지역을 선택하면 관광·식사 시간표를 즉시 표시하고, **그 계획에 실제 들어간 관광지 최대 6개**에만 관광 상세를 비차단으로 보강한다. 식당 목록은 기존 별도 흐름이다. 불러오기 실패나 느린 응답 때문에 계획 화면 전체를 대기·실패 상태로 만들지 않는다.

### 고정의 구분

기존 `장소 유지`는 콘텐츠 선택 보존이며 날짜·시각 고정이 아니다. 새 `시각 고정`과 UI·필드를 분리한다. 시각 고정은 해당 항목의 날짜까지 묶는다. 날짜 이동/순서 이동/삭제/교체가 시각 고정과 충돌하면 해제를 안내하고 기존 상태를 유지한다. 사용자가 고정 시각 자체를 수정하는 명령은 새 값 검증 후 원자 적용한다. 장소 유지된 관광지의 직접 교체·삭제는 기존대로 해제가 필요하다.

### 재계산과 보존

1. 편집 전 계획·명령·안정적 항목 ID를 받아 검증한다. 계산 중 네트워크 호출을 하지 않는다.
2. 기존 출발/귀가 운전 배치, 식사 시작 시각·현지/이동 구분, 야간 휴식을 유지한다. 이를 바꿔야만 가능한 편집은 실패다. 사용자가 고른 식당 때문에 여행 전체가 새로 생성되지 않는다.
3. 편집 대상 외 관광·개인 일정의 ID·선택·체류 분·날짜·상대 순서·시각 고정을 보존한다. 명시적 날짜/순서 이동 명령만 해당 순서를 바꾼다. 자동 새 관광 추가·삭제·교체는 하지 않는다.
4. 각 날짜의 고정 시각을 경계로 유효한 낮 구간에 나머지를 배치한다. 같은 구간의 관광·개인 활동 사이 15분 여유와 활동일 자유시간 30분을 확보한다. 식사/휴식 사이 추가 여유를 중복 넣지 않는다.
5. 여러 배치가 가능하면 편집 대상 외 기존 항목의 시작 시각을 그대로 유지한 개수 최대 → 기존 시각에서 이동한 절대 분 합 최소 → 최종 시작 시각 배열 사전순으로 결정한다. 날짜·항목 수가 작다는 범위에서 employee가 결정적 유한 탐색/계획 알고리즘을 선택한다. 불가능을 성공처럼 표시하는 근사 배치는 하지 않는다.
6. 성공만 한 번에 적용한다. 실패는 계획·저장 상태·식당·고정 상태 모두 유지하고 `해당 날짜 관광 3곳 한도`, `식사와 겹침`, `고정 시각 충돌`, `현지 체류 범위 밖`, `여유시간 부족`처럼 구체적 사유를 제공한다.

삭제 후 관광 최소 3개는 기존 편집 예외로 두고 개인 일정으로 관광 최소 수를 채우지 않는다. 개인 일정만 남은 낮도 자유시간 규칙을 적용한다. 개인 일정의 시작 시각 고정은 운전·식사·휴식을 침범할 수 없으며, 22시 관광/개인 활동을 허용하는 의미가 아니다. 야간 이동 입력 허용은 유지한다.

### 식사 및 상세의 정합성

편집 성공 후 기존 식당을 자동 교체하지 않는다. 관광 장소가 달라져 음식점 위치가 맞지 않을 수 있으면 해당 식사에 `방문 장소가 바뀌었어요. 식당 위치를 확인해 주세요`와 기존 대체 후보 선택을 제공한다. 개인 장소 좌표를 임의 추정하지 않는다.

새로운 관광 하위 지역 때문에 음식점 목록 추가 조회가 필요하면 사용자의 `식당 후보 다시 확인`에만 기존 최대 3지역·9회·동시성 2 상한으로 조회한다. 성공 목록은 대체 후보로 제공하며 이미 선택한 식당을 덮어쓰지 않는다. 관광 편집의 성공/실패와 음식점 조회 성공/실패는 독립이다.

### 저장 계약·이관

- E1~E3 추가 근거는 v2 저장본에 없는 선택적 메타데이터로 취급한다. 기존 v2를 불러올 때 `기존 추천`·정보 미조회로 표시하고 역할·시설 근거·휴무 확인을 새로 꾸미거나 자동 재검색하지 않는다. 구현 단계마다 저장 정규화 함수가 새 필드를 유실하지 않는지 확인한다.
- E4는 `schemaVersion: 3` 및 저장 컨테이너 v3로 확장한다. 관광/개인 일정 안정적 ID, 종류, 날짜·순서, 선택 보존, `fixedStartAt`, 숙소 메모, 규칙 버전, 데이터 시점과 기존 전체 스냅샷을 보존한다. 추가 메타데이터도 타입·길이·범위를 검사한다.
- 유효한 v2는 메모리에서 v3로 읽기 이관한다. 기존 블록의 날짜·순서·시각은 그대로 유지하고 `fixed`는 장소 유지로만 매핑한다. 개인 일정/숙소는 없음, 시각 고정은 없음이다. E2 규칙을 소급 적용해 이전 계획을 몰래 재배치하지 않는다.
- 기존 저장 키는 v3 쓰기가 완전히 성공하기 전 삭제하지 않는다. 전체 유효 항목을 확인한 뒤 쓰고 확인하며, 실패·잘못된 개별 항목 때문에 유효 계획까지 지우지 않는다. v3 컨테이너에 이관 완료 여부를 함께 저장하고 이후에는 v3를 우선한다. v3에 계획이 0개여도 이전 v2를 다시 수입하지 않는다. 남긴 v2는 복구용 원본이며 자동 이관 대상이 아니다. v3 손상/미지원 버전도 묵시적 v2 재수입 대신 오류·명시적 복구 안내로 처리해 사용자가 삭제한 계획이 부활하지 않게 한다.
- v2 계획을 편집할 때 새 규칙으로 유효 배치를 찾을 수 없으면 원본을 유지하고 새 규칙 적용 불가를 알린다. 사용자가 명시적으로 새로 검색할 수는 있지만 자동 전환하지 않는다.
- 최대 10계획, 명시적 저장/삭제, 저장 후 변경 표시와 저장소 차단·용량 실패 처리를 유지한다. API 키·원문 HTML·전국 프로필·개인 장소를 서버 로그에 저장하지 않는다.

### 수용 기준

- 관광 날짜/순서 이동·추가가 해당 명령대로 성공하고 무관한 선택·날짜·식당이 보존된다. 대상일 한도·식사·고정 충돌은 완전 rollback이다.
- 오후 14시 고정 관광은 다른 시간 수정에도 14시 유지, 21시를 넘는 고정은 실패, 시각 해제 후에만 날짜 이동 가능을 검증한다.
- 같은 ID 두 번 추가 불가, 시설 의심 추가는 안내 후 명시적으로 가능, 원천 후보 밖 ID 거절을 검증한다.
- 개인 일정이 공공 관광 수·관심사 충족에 들어가지 않고 숙소 메모가 야간 휴식 시간을 이중 차감하지 않는다. 필드 초과·악성 HTML은 안전하게 처리한다.
- v2 불러오기→편집→v3 저장→새로고침 복원에서 ID·고정·시각·식당·메모가 보존된다. 이관 후 삭제한 계획이 새로고침에서 v2로부터 부활하지 않는다. 미지원/깨진 저장본과 용량 오류가 기존 정상 저장본을 지우지 않는다.
- 저장본 복원·수정에서 자동 관광/음식 API 호출이 발생하지 않는다. 명시적 상세/목록 재확인에만 정해진 예산을 사용한다.

## 6. 디자인·검증·인계

기존 [H · 여행 수첩](../design/DESIGN_DIRECTION.md), [디자인 토큰](../design/DESIGN_TOKENS.md), 모바일 중심 화면 폭과 입력→결과→일정 구분을 유지한다. 별도 대시보드·카드 그리드로 재설계하지 않는다. 일정의 시간 열·세로 레일을 유지하고 편집은 항목 보조 동작/시트로 제공한다. 아이콘만으로 의미를 전달하지 않으며 모든 이동·추가·고정은 키보드로 가능해야 한다. 진행/실패 알림은 스크린리더에도 전달한다.

각 PR은 해당 E 번호, 명세 대비 구현·제외·검증 결과, 기존 음식 흐름 보존 여부를 기록한다. 핵심은 실제 공통 엔진을 통과하는 결정적 데이터 검증이며, 외부 API는 제한된 정규화 응답으로 실패/시간 초과/부분 성공을 재현한다. E3의 실제 API는 소량 확인하고 호출 불가를 기능 성공으로 표시하지 않는다. 실 API 검증 불가는 별도 명시하되 mock으로 검증한 사항과 구분한다.

필수 통합 흐름은 서울/부산 검색 → 세 역할 비교 → 선택 → 관광과 음식 목록 → 장소 편집 → 저장·복원이다. 단계에 아직 없는 후속 기능을 테스트에서 요구하지 않으며 기존 정상 기능을 fixture로 우회해서 통과시키지도 않는다. CI 검증과 빌드 실패가 있는 PR은 병합하지 않는다.

PM 리뷰 확인 사항: 기존 원천만으로 계산 가능한가, 추가 호출이 한정되는가, 사용자가 선택한 장소를 지우지 않는가, UI 문구가 데이터의 근거보다 강한 보증을 하지 않는가. 작업 계획의 진행 상태는 employee 문서에서 기록하고 이 기획서에 완료를 미리 표시하지 않는다.
