## 1. 제품 목적과 방향성

### 제품 목적

DURUDURU(두루두루)는 목적지를 아직 정하지 못한 국내 여행자가 **출발지와 실제 가용시간만으로 갈 수 있는 목적지부터 발견하고, 선택한 목적지의 실행 가능한 일정을 얻도록** 돕는 서비스다.

일반 여행 서비스의 출발점은 “경주에 갈 건데 무엇을 할까?”다. DURUDURU의 출발점은 “이번 주말 이 시간 안에 어디를 다녀올 수 있을까?”다. 따라서 인기순 장소 나열이나 목적지 선택 후의 코스 경쟁보다, 시간 제약을 이해한 목적지 추천을 제품의 중심 경험으로 둔다.

### 핵심 가설

목적지를 정하지 못한 사용자가 출발·복귀 가능 시간과 관심사를 입력했을 때, 시간상 가능한 후보와 그 근거를 먼저 받으면 목적지 선택을 시작하고, 제약을 지킨 일정까지 완성할 가능성이 높다.

이 가설은 다음 두 질문으로 검증한다.

1. 사용자는 추천된 목적지와 추천 이유를 납득해 하나를 선택하는가?
2. 선택 후 생성된 일정을 실제로 검토 가능한 계획으로 받아들이고 끝까지 생성하는가?

### 제품 원칙

- **실행 가능성을 매력도보다 우선한다.** 시간 안에 성립하지 않는 여행은 추천하지 않는다.
- **목적지 선택 전 문제를 해결한다.** 목적지별 콘텐츠의 양보다 가용시간 기반 후보 선별이 핵심이다.
- **근거를 함께 보여 준다.** 추천·제외·일정 배치의 시간 및 관심사 근거를 숨기지 않는다.
- **불확실성을 사실처럼 표현하지 않는다.** 평균 이동시간, fallback 값, 데이터 결측은 결과에서 구분한다.
- **핵심 엔진은 규칙과 데이터로 만든다.** 공공데이터와 규칙/점수 기반 엔진을 사용하며 LLM은 핵심 추천·일정 생성 범위에 넣지 않는다.
- **검증된 지역부터 확장한다.** 전국 커버리지보다 데이터 신뢰도와 일정 정확도를 우선한다.

## 2. 우선 사용자와 해결할 문제

### 우선 사용자

MVP의 우선 사용자는 다음 조건을 충족하는 국내 여행자다.

- 주말 당일치기 또는 1박 2일 여행을 고민한다.
- 출발지와 출발·복귀 가능 일시가 명확하다.
- 역사·문화·자연 등 여행 관심사가 있다.
- 초기 방향상 자차 여행자에 우선 초점을 둔다. 자차 정식 지원 및 출발지 단위는 아직 `제안` 상태다.

### 사용자의 문제

| 문제                    | 현재의 어려움                                     | DURUDURU가 제공할 결과                               |
| ----------------------- | ------------------------------------------------- | ---------------------------------------------------- |
| 목적지 선정의 막막함    | 시간이 있어도 어디부터 찾아야 할지 모른다.        | 시간 안에 갈 수 있는 목적지를 먼저 비교한다.         |
| 계획의 실행 가능성 판단 | 왕복 이동, 휴무, 운영시간을 각각 확인해야 한다.   | 시간 제약을 통과한 후보와 일정만 제시한다.           |
| 추천 결과에 대한 불신   | 인기·광고성 목록은 내 조건에 맞는지 알기 어렵다.  | 추천 이유, 이동시간, 현지 이용 가능 시간을 표시한다. |
| 데이터의 불완전성       | 정보가 없거나 오래된 정보를 확정 사실로 오해한다. | 출처·갱신·추정 및 결측 상태를 구분한다.              |

### 대표 사용자 시나리오

서울에서 토요일 08:00에 출발해 일요일 20:00까지 돌아와야 하는 사용자가 역사 관심사를 입력한다. 서비스는 왕복 예상 이동시간과 최소 현지 체류시간을 고려해 가능한 목적지를 선별한다(복귀 버퍼는 두지 않는다). 사용자는 경주·공주/부여·강릉처럼 후보별 시간 적합성과 관심사 적합성을 비교하고 한 지역을 선택한다. 이후 운영 가능 장소, 체류·이동시간, 식사, 선택적으로 여행 기간과 맞는 축제를 포함한 시간표와 복귀 근거를 확인한다.

### 결과 없음도 유효한 결과다

입력 조건으로 최소 기준을 충족하는 목적지가 없으면 무리한 일정이나 허위 후보를 만들지 않는다. 더 이른 출발, 더 늦은 복귀, 가까운 출발지 등 사용자가 조정할 수 있는 조건을 안내한다.

## 3. PoC 기록과 MVP의 구분

### 종료된 PoC 범위

PoC는 Next.js 화면 중심의 목업 구현이었다. 서울·대전·부산 출발지, 자차/대중교통 UI, 역사·자연·문화·미식 관심사를 입력받아 경주·공주·강릉의 목업 후보를 추천하고 간단한 일정 타임라인을 보여 준다. 추천은 고정 평균 이동시간, 관심사 태그, 왕복 이동시간과 7시간 기준을 사용하는 단순 규칙이며, 일정은 목업 운영시간·휴무·체류시간과 장소 간 고정 30분을 사용한다. 기간이 겹치는 목업 축제와 지역 대표음식도 표시한다.

PoC는 핵심 화면 흐름과 규칙 기반 접근을 확인하기 위한 검증물이었고 첫 커밋으로 종료했다. 따라서 PoC의 화면·스타일·목업 로직은 보존 대상이 아니라 MVP 구현으로 교체될 대상이다. 다만 PoC가 쓴 숫자와 목업 데이터는 검증되지 않은 임시값이므로 **정식 정책으로 승격하지 않는다.** 왕복 + 7시간 기준, 장소 간 고정 30분, 목업 운영시간·체류시간, 대중교통 UI는 그대로 옮겨 쓸 근거가 없다.

### PoC의 한계

- 출발지별 실제 이동시간, 관광지 간 실제 경로·이동시간을 계산하지 않는다.
- 식사·숙박·날짜별 예외 운영을 엄격히 배치하거나 검증하지 않는다.
- 모든 일정 항목이 복귀 출발시각 이전에 끝나는지를 완전하게 보장하지 않는다.
- 운영시간·휴무·체류시간의 결측과 실제 데이터 갱신을 처리하지 않는다.
- 대중교통 UI는 존재하지만 초기 정식 MVP 지원으로 확정된 것이 아니다.

따라서 PoC 화면의 시간과 이동시간은 실제 여행에 바로 사용할 수 있는 보장이 아니었다. 이 한계를 해소하는 것이 MVP 요구사항이다.

## 4. MVP 범위와 비범위

### MVP에서 구현해야 할 기능

| 우선순위 | 기능                                            | 사용자 가치                                                                                                    |
| -------- | ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| P0       | 여행 조건 입력                                  | 출발지, 출발·복귀 일시, 이동수단, 관심사를 한 번에 명확히 전달한다.                                            |
| P0       | 가용시간 기반 목적지 추천                       | 왕복 이동과 최소 현지 체류시간을 고려해 가능한 목적지 3~5개를 비교한다.                                        |
| P0       | 관심사 기반 점수화와 설명                       | 관심사·시간 적합성에 따라 후보를 정렬하고 이유를 보여 준다.                                                    |
| P0       | 제약 기반 일정 생성                             | 운영시간, 휴무, 체류시간, 이동, 식사와 복귀 조건을 반영한 시간표를 만든다.                                     |
| P0       | 근거·신뢰도 표시                                | 이동시간의 성격, 데이터 출처·갱신일, 결측 및 fallback 사용을 표시한다.                                         |
| P1       | 여행 기간과 맞는 축제 반영                      | 기간·지역·관심사에 맞을 때만 후보 또는 일정에 반영한다.                                                        |
| P0       | 식사 블록과 대표음식 음식점 배치                | 점심·저녁 시간대에 최소 1시간 식사를 확보하고 지역 대표음식을 파는 음식점을 배치한다. 평점·순위는 쓰지 않는다. |
| P1       | 동선 최적화 음식점 선정·복수 후보·미식 큐레이션 | 평점 경쟁이 아닌 여행 경험을 위한 식사 선택지를 넓힌다.                                                        |
| P1       | 일정 재생성 또는 장소 교체                      | 자동 일정에 대한 최소한의 조정 수단을 제공한다.                                                                |
| P2       | 대중교통, 동행 조건, 날씨, 예산                 | 핵심 경험 검증 후 조건을 확장한다.                                                                             |

### MVP 비범위

- 로그인, 개인화, 여행 저장·공유
- 실시간 교통, 정밀 내비게이션, 예약·결제
- 맛집 평점·랭킹
- GPS 방문 인증, 스탬프, 컬렉션, 친구, 랭킹, 미션
- 전국 모든 지역 및 모든 여행 조건의 즉시 지원
- LLM 기반 핵심 추천·일정 생성

장기 게임화와 방문 기록은 제품 배경상 가능한 방향이지만, 명시적 승인 전에는 MVP 범위에 포함하지 않는다.

## 5. 사용자 흐름과 화면별 요구사항

| 단계 | 화면/상태             | 사용자 행동                                          | 화면 요구사항                                                                                                                                        |
| ---- | --------------------- | ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 여행 조건 입력        | 출발지, 출발·복귀 일시, 이동수단, 관심사를 입력한다. | 필수값과 시간 역전 오류를 즉시 알리고, 추천에 사용되는 조건을 사용자가 확인할 수 있어야 한다.                                                        |
| 2    | 목적지 추천 결과      | 후보를 비교하고 한 곳을 선택한다.                    | 후보마다 지역 식별 정보, 추천 이유, 왕복 예상 이동시간, 현지 이용 가능 시간, 관심사 적합성을 보여 준다. 시간 제약을 통과한 결과임을 명확히 표시한다. |
| 3    | 목적지 상세/일정 생성 | 선택한 목적지의 일정을 생성한다.                     | 생성 중인 조건과 데이터 기준을 유지하고, 데이터 부족 시 확정된 일정처럼 보이지 않게 한다.                                                            |
| 4    | 일정 결과             | 시간표와 복귀 가능 근거를 검토한다.                  | 출발·도착·관광·식사·선택적 축제·복귀를 시간 순서로 제시한다. 항목별 운영 가능 여부, 체류시간, 다음 이동시간을 확인할 수 있어야 한다.                 |
| 5    | 예외/데이터 안내      | 조건을 조정하거나 결과의 신뢰도를 판단한다.          | 결과 없음, 결측 데이터, fallback, 평균·추정 이동시간, 출처·갱신 정보를 구분해 표시하고 가능한 조정 행동을 안내한다.                                  |

## 6. 기능별 수용 기준

| 기능           | 수용 기준                                                                                                                                                                                                                              |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 조건 입력      | 출발지, 출발·복귀 일시, 이동수단, 관심사가 추천에 필요한 형태로 검증된다. 복귀가 출발보다 이른 입력은 진행할 수 없다.                                                                                                                  |
| 목적지 추천    | 왕복 예상 이동시간을 제외한 시간이 최소 현지 체류시간(`4시간 × 일수` — 당일치기 4시간 / 1박 2일 8시간 / 2박 3일 12시간, 2026-08-31 확정)을 충족하는 목적지만 후보로 제시한다. 여행 유형은 출발·복귀가 걸치는 KST 달력일 수로 판별한다. |
| 후보 수와 정렬 | 가능 후보가 3~5개일 때 비교 가능한 목록으로 제시한다. 후보가 그보다 적을 때의 표시 정책은 별도 결정 전까지 확정 요구사항으로 간주하지 않는다.                                                                                          |
| 추천 설명      | 모든 후보에는 시간 적합성, 관심사 적합성, 축제 적합성 중 실제 점수에 영향을 준 적어도 하나의 근거가 표시된다.                                                                                                                          |
| 일정 생성      | 각 방문 항목은 해당 날짜와 시각의 운영 가능 여부·휴무 여부를 확인한 데이터 또는 명시된 fallback을 바탕으로 배치된다.                                                                                                                   |
| 복귀 보장      | 마지막 방문 종료와 예상 복귀 이동의 합이 사용자의 복귀 가능 시각을 넘지 않는다. 복귀 버퍼는 두지 않는다(2026-08-31 확정).                                                                                                              |
| 식사           | 점심 11:30~~13:30, 저녁 17:30~~19:30 시간대를 지나는 일정에는 최소 1시간의 식사 블록을 확보하고, 여유가 있으면 늘린다. 각 블록에는 지역 대표음식을 파는 음식점을 배치하며 맛집 순위로 표현하지 않는다.                                 |
| 이동시간       | 모든 이동시간은 실시간 정보가 아닌 평균 또는 추정치임을 표시한다.                                                                                                                                                                      |
| 데이터 결측    | 운영시간·휴무·체류시간이 누락되면 적용된 제외 또는 fallback 정책, 출처 수준을 결과 상세에서 구분한다. 정책이 `확정`되기 전에는 이를 임의로 제품 요구사항으로 확정하지 않는다.                                                          |
| 축제           | 여행 기간과 지역이 겹치고 여행 목적 또는 관심사에 맞을 때만 추천 점수나 일정에 반영한다. 축제 존재만으로 일정에 강제 삽입하지 않는다.                                                                                                  |
| 결과 없음      | 최소 제약을 충족하지 못할 경우 후보나 일정을 허위로 생성하지 않고 조정 가능한 조건을 안내한다.                                                                                                                                         |

## 7. 데이터와 신뢰도 원칙

### 데이터 운영 방향

관광지·축제·운영정보는 공공 API를 매 요청에 직접 의존하지 않고, **공공 API 수집 → 정규화 → 내부 데이터 계층 → 서비스 제공** 흐름을 지향한다. 변경 빈도가 낮은 데이터는 주기적으로 갱신하고, 외부 장애 시 마지막 정상 데이터를 제공할 수 있어야 한다. 초기 후보 데이터는 TourAPI를 중심으로 실제 필드 충족률을 검증한다.

### 결과 신뢰도 규칙

- 운영시간·휴무·체류시간·이동시간의 출처와 갱신 상태를 관리한다.
- 평균 이동시간과 카테고리 기본 체류시간 등 추정값은 확정값과 시각적으로 구분한다.
- 날짜별 예외 운영, 운영정보 누락, 오래된 데이터는 일정의 신뢰도를 낮추는 조건으로 다룬다.
- 데이터가 충분하지 않으면 무리한 일정 생성보다 보수적 제외 또는 명시적 fallback을 우선한다. 구체 정책은 `DECISIONS.md`의 상태를 따른다. 현재는 `제안`이며 승인 전에는 요구사항이 아니다.
- 외부 API 장애와 데이터 결측의 영향을 사용자가 이해할 수 있도록 결과의 데이터 상태를 표시한다.

## 8. 단계별 계획

### 0단계 — 제품·데이터 합의 (진행 중)

- PoC는 종료했다. 이 단계에서 PoC 코드를 보존하거나 확장하지 않는다.
- 초기 지역, 정식 이동수단, 출발지 입력 단위, 일정 수정 범위를 제품 결정으로 정리한다. 디자인 방향은 H로 확정됐다. 2026-08-31에 최소 현지 체류시간(형태 + 값), 데이터 결측 처리(형태), 복귀 버퍼 미도입, 점수 가중치·동점 규칙, 식사 시간대·음식점 포함이 확정됐다. 카테고리 기본 체류시간·장소 간 이동시간 산출 방식·계산 기준 시간대는 아직 미정이다.
- TourAPI 등 실제 데이터의 운영정보·휴무·좌표·축제 필드 품질을 조사한다.

이 단계의 미결정은 `DECISIONS.md`의 상태를 따른다. 이 기획서는 권장안을 확정으로 바꾸지 않는다.

### 1단계 — 제한 지역 핵심 MVP

- 데이터 품질이 확인된 제한 지역에서 가용시간 기반 목적지 추천과 복귀 조건을 지키는 일정 생성을 제공한다.
- 자차·주요 도시 출발은 현재 `제안` 방향이며, 확정 후에만 정식 지원 조건으로 적용한다.
- 추천 이유, 시간 근거, 데이터 신뢰도 표시로 핵심 가설을 검증한다.

### 2단계 — 여행 완성도 개선

- 축제, 대표음식/주변 식사, 전체 일정 재생성 또는 개별 장소 교체를 우선순위와 결정 상태에 맞춰 추가 검토한다.
- 초기 지역에서 얻은 데이터 품질과 사용자 행동을 바탕으로 지원 지역 확대 여부를 판단한다.

### 3단계 — 조건과 제품 루프 확장

- 대중교통, 동행 조건, 날씨, 예산은 데이터 신뢰도와 핵심 가치 훼손 여부를 검증한 뒤 순차 도입한다.
- 저장·개인화·방문 기록·게임화는 별도 가설과 명시적 승인 없이는 진행하지 않는다.

## 9. 성공 지표와 검증 방법

초기에는 사용 규모보다 핵심 경험의 유효성을 본다. 지표의 기간, 목표값, 정확한 이벤트 명세는 아직 확정되지 않았으므로 구현·운영 전 별도 합의가 필요하다.

| 지표                    | 확인하려는 것                                  | 기본 산식/기록 단위                                               |
| ----------------------- | ---------------------------------------------- | ----------------------------------------------------------------- |
| 후보 선택률             | 목적지부터 추천하는 경험이 선택을 시작시키는지 | 후보 결과를 본 세션 중 목적지를 선택한 세션 비율                  |
| 일정 생성 완료율        | 선택한 목적지가 일정 완성으로 이어지는지       | 목적지 선택 세션 중 일정 결과를 생성한 세션 비율                  |
| 복귀 조건 충족률        | 엔진이 핵심 시간 제약을 지키는지               | 생성된 일정 중 복귀 가능 조건을 충족한 일정 비율                  |
| 무효 일정 비율          | 운영시간·휴무 충돌이 얼마나 발생하는지         | 생성된 일정 중 운영 불가 또는 휴무 장소를 포함한 일정 비율        |
| 재생성·장소 교체 비율   | 자동 일정이 어느 정도 조정되는지               | 해당 기능이 도입된 뒤 일정 결과 대비 재생성·교체 행동 비율과 사유 |
| 만족 응답               | 추천 결과의 납득 가능성을 확인하는지           | 결과 확인 후 간단한 만족 응답의 분포                              |
| fallback/결측 적용 비율 | 데이터 신뢰도 위험이 어느 정도인지             | 생성 결과 중 fallback 또는 결측 정책이 적용된 결과 비율           |

가장 중요한 성공 판단은 **목적지를 정하지 않은 사용자가 추천의 근거를 이해하고, 선택 후 일정을 끝까지 생성하는가**다. 복귀 조건 충족률과 무효 일정 비율은 이 경험이 신뢰할 수 있는지 확인하는 안전 지표다.
