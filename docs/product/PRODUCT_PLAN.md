# DURUDURU 제품 계획

> 상태: 개발 시작 전 제품 합의용 초안
> 기준 문서: `PRD.md`, `DECISIONS.md`
> 이 문서는 구현 명세가 아니라 MVP의 제품 범위와 검증 기준을 정리한다.

## 1. 문제와 사용자 정의

### 해결하려는 문제

국내여행을 갈 시간은 있지만 목적지를 정하지 못해 계획을 시작하지 못하는 사용자가 많다. 기존 여행 서비스는 대체로 목적지를 고른 후 코스를 찾게 한다. DURUDURU는 출발지와 실제로 사용할 수 있는 시간을 기준으로 먼저 갈 수 있는 목적지를 제안하고, 그 선택을 실행 가능한 일정으로 연결한다.

### MVP의 우선 사용자

- 주말 당일치기 또는 1박 2일 국내여행을 계획하는 사람
- 출발지와 출발·복귀 가능 일시가 분명한 사람
- 자차로 이동하는 사람
- 역사·문화·자연 중 선호 테마가 있는 사람

### 핵심 가치

1. **목적지부터 제안:** “이 시간에 어디를 갈 수 있나?”를 먼저 답한다.
2. **실행 가능한 일정:** 왕복 이동, 운영시간, 휴무, 체류시간, 식사와 복귀 여유를 고려한다.
3. **납득 가능한 결과:** 추천·제외·시간 배치의 이유와 데이터의 불확실성을 보여 준다.

## 2. 핵심 사용자 시나리오

### 대표 시나리오: 서울 출발 역사 여행

1. 사용자는 서울에서 토요일 08:00 출발, 일요일 20:00 복귀, 자차, 역사 관심사를 입력한다.
2. 서비스는 왕복 예상 이동시간과 최소 현지 이용 가능 시간을 계산해 가능한 목적지 후보를 제시한다.
3. 사용자는 경주·공주/부여·강릉처럼 후보별 추천 이유, 왕복 이동시간, 현지 이용 가능 시간을 비교한다.
4. 사용자가 한 지역을 선택하면 서비스는 방문 가능한 역사 장소, 식사, 여행 기간에 적합한 경우의 축제를 시간표로 구성한다.
5. 사용자는 각 일정의 운영시간, 예상 체류·이동시간, 복귀를 위해 출발해야 하는 시각과 데이터 근거를 확인한다.

### 결과가 없어야 하는 시나리오

입력한 시간 안에 최소 기준을 충족하는 목적지가 없다면, 무리한 일정을 만들지 않는다. 대신 더 가까운 지역, 더 이른 출발 또는 더 늦은 복귀처럼 사용자가 조정할 수 있는 조건을 안내한다.

## 3. MVP 범위, 비범위와 우선순위

| 우선순위 | 범위 | 사용자에게 제공하는 결과 |
| --- | --- | --- |
| P0 | 가용시간 기반 목적지 후보 추천 | 가능한 목적지 3~5개와 추천 이유·왕복 예상 이동시간·현지 이용 가능 시간 |
| P0 | 왕복 가능 여부와 복귀 버퍼 | 무리한 목적지를 제외하고 안전한 복귀 시각을 반영 |
| P0 | 관심사 기반 점수화 | 역사·문화·자연 선호에 맞는 목적지와 장소 우선 제안 |
| P0 | 제약을 반영한 일정 생성 | 운영시간·휴무·체류시간·식사·이동시간을 고려한 시간표 |
| P0 | 근거와 불확실성 표시 | 추천·일정 근거, 평균/추정 이동시간, 데이터 출처·갱신 정보 |
| P1 | 여행 기간과 겹치는 축제 반영 | 테마와 맞는 경우에만 일정 또는 추천 이유에 반영 |
| P1 | 대표음식과 주변 음식점 제안 | 맛집 순위가 아닌 지역 음식 경험을 위한 식사 선택지 |
| P1 | 일정 재생성 또는 장소 교체 | 사용자가 자동 일정의 선택지를 조정할 수 있는 최소 수단 |
| P2 | 대중교통·동행 조건·날씨·예산 | 핵심 경험 검증 이후 확대할 입력 조건 |

### MVP 비범위

- 로그인, 개인화, 여행 저장·공유
- 실시간 교통, 정밀 내비게이션, 예약·결제
- 맛집 평점·랭킹
- GPS 방문 인증, 스탬프, 컬렉션, 친구, 랭킹, 미션
- 전국 모든 지역과 모든 여행 조건의 즉시 지원
- LLM 기반 핵심 추천·일정 생성

## 4. 핵심 화면과 사용자 흐름

### A. 여행 조건 입력

사용자는 출발지, 출발·복귀 일시, 자차 여부, 관심사를 입력한다. 입력 완료 전에도 필수값과 시간 역전 같은 명확한 오류를 안내한다.

### B. 목적지 추천 결과

목적지 카드에는 지역명, 대표 이미지 또는 식별 정보, 추천 이유, 왕복 예상 이동시간, 현지 이용 가능 시간, 관심사 적합성을 표시한다. 추천 결과는 단순 인기순이 아니라 시간 제약을 통과한 후보임을 명확히 알린다.

### C. 선택 목적지의 일정

일정 타임라인에는 출발·도착·관광·식사·선택적 축제·복귀를 시간 순서로 보여 준다. 각 항목에는 운영시간/휴무, 체류시간, 다음 장소까지의 예상 이동시간을 확인할 수 있어야 한다. 복귀 이동과 버퍼가 일정의 마지막 제약으로 명시돼야 한다.

### D. 예외 및 데이터 안내

추천 결과가 없거나 필요한 데이터가 충분하지 않은 경우, 확정된 사실처럼 일정을 제시하지 않는다. 사용자에게 부족한 조건 또는 추정으로 사용된 정보를 보여 주고, 조건 조정을 안내한다.

## 5. 기능별 수용 기준

| 기능 | 수용 기준 |
| --- | --- |
| 목적지 추천 | 입력 시간에서 왕복 예상 이동시간과 복귀 버퍼를 제외한 뒤, 최소 현지 체류시간을 충족하는 목적지만 후보로 제시한다. |
| 추천 설명 | 모든 후보에 추천에 영향을 준 최소 한 가지 근거(시간 적합성, 관심사 적합성, 축제 등)를 표시한다. |
| 일정 생성 | 일정의 각 방문 항목은 해당 날짜·시간의 운영 가능 여부와 휴무 여부를 확인한 데이터 또는 명시된 fallback을 바탕으로 배치한다. |
| 복귀 보장 | 마지막 방문 항목 종료 후 예상 복귀 이동과 버퍼를 더한 시간이 사용자의 복귀 가능 시각을 넘지 않는다. |
| 식사 반영 | 장시간 일정에는 식사 시간을 확보하며, 식당 제안은 동선 또는 지역 대표음식과의 관련성을 설명한다. |
| 이동시간 표시 | 모든 이동시간은 평균 또는 추정치임을 알리고, 실시간 교통 정보로 표현하지 않는다. |
| 결측 데이터 | 운영시간·휴무·체류시간이 누락된 경우 적용한 정책과 출처 수준을 화면 또는 결과 상세에서 구분한다. |
| 축제 반영 | 여행 기간과 지역이 겹치며, 여행 목적 또는 관심사에 적합할 때만 추천 점수 또는 일정에 반영한다. |
| 결과 없음 | 최소 제약을 충족하는 목적지가 없을 때 허위의 후보나 일정 대신 조정 가능한 조건을 안내한다. |

## 6. 단계별 출시 계획

### 0단계 — 제품·데이터 검증 준비

- 초기 지원 지역, 이동수단, 최소 현지 체류시간, 결측 데이터 정책을 사용자와 합의한다.
- 현재 PoC의 목업 경험을 기준선으로 유지하고, 실제 데이터 전환의 품질 기준을 세운다.
- 출시 조건: 아래 미결정 항목 중 P0 추천과 일정의 신뢰성에 직접 영향을 주는 정책이 합의됨.

### 1단계 — 제한 지역의 핵심 MVP

- 데이터 품질을 검증한 제한된 지역에서 자차·관광·역사/문화/자연 중심 흐름을 제공한다.
- 목적지 추천과 제약을 지키는 일정 생성을 검증한다.
- 출시 조건: 유효하지 않은 일정이 반복 생성되지 않고, 사용자가 추천 이유와 시간 근거를 이해할 수 있음.

### 2단계 — 여행 완성도 개선

- 축제, 대표음식/주변 음식점, 최소한의 일정 재생성 또는 장소 교체를 추가한다.
- 초기 지역의 데이터 품질과 사용자 피드백을 바탕으로 지원 지역을 넓힌다.
- 출시 조건: 추가 요소가 핵심 시간 제약을 훼손하지 않고 일정 만족도를 높임.

### 3단계 — 조건과 지역 확장

- 대중교통, 동행 특성, 날씨, 예산 같은 조건은 사용자 가치와 데이터 신뢰도를 검증한 뒤 순차 도입한다.
- 여행 저장·개인화·게임화는 별도의 제품 가설과 명시적 승인 후 검토한다.

## 7. 성공 지표

초기에는 규모보다 핵심 경험의 유효성을 검증한다.

- 입력 완료 후 목적지 후보를 선택하는 비율
- 목적지 선택 후 일정 생성을 완료하는 비율
- 생성 일정이 복귀 가능 조건을 충족하는 비율
- 운영시간·휴무 충돌로 무효한 일정이 생성되는 비율
- 일정 재생성 또는 장소 교체 비율과 사유
- 추천 결과에 대한 간단한 만족 응답
- fallback 또는 데이터 결측 정책이 적용된 결과의 비율

가장 중요한 판단 기준은 **목적지를 정하지 않은 사용자가 추천 결과를 납득하고, 일정을 끝까지 생성하는지**다.

## 8. 사용자와 확정해야 할 의사결정 및 권장안

| 상태 | 의사결정 | 권장안 | 확정이 필요한 이유 |
| --- | --- | --- | --- |
| 제안 | 초기 지역 | 경주, 공주/부여, 강릉 등 데이터 검증 지역부터 지원 | 전국 동시 지원보다 일정 신뢰도 검증을 우선 |
| 제안 | 초기 이동수단 | 자차만 정식 지원 | 이동시간 추정과 제약 모델을 먼저 안정화 |
| 제안 | 출발지 입력 단위 | 주요 도시 단위부터 시작 | 주소·좌표 입력과 지오코딩의 복잡도를 뒤로 미룸 |
| 보류 | 최소 현지 체류시간 | 여행 유형별 최소 기준을 명시적으로 정함 | 목적지 후보의 가능 여부를 결정하는 핵심 정책 |
| 보류 | 데이터 결측 처리 | 운영/휴무 결측은 보수적으로 제외하고, 체류시간은 출처가 표시된 fallback 허용을 우선 검토 | 허위의 실행 가능성보다 신뢰도를 우선 |
| 보류 | 일정 수정 범위 | MVP에는 전체 재생성부터 우선 제공하고, 개별 장소 교체는 P1으로 검토 | 화면과 일정 엔진의 초기 범위를 통제 |
| 보류 | MVP 출시 형태 | 제한된 지역의 공개 테스트 또는 초대형 테스트 중 선택 | 성공 지표 수집 방식과 운영 부담에 영향 |

표의 `제안`과 `보류`는 아직 확정된 요구사항이 아니다. 특히 최소 현지 체류시간과 결측 데이터 처리는 P0 일정의 신뢰성에 직접 영향을 주므로 개발 착수 전에 합의가 필요하다.

## 9. 리스크와 완화책

| 리스크 | 영향 | 완화책 |
| --- | --- | --- |
| 관광지 운영시간·휴무 정보의 누락 또는 형식 불일치 | 잘못된 일정 생성 | 출처·갱신일·결측 상태를 구분하고, 보수적 제외 또는 합의된 fallback 정책 적용 |
| 관광지 간 이동시간이 평균 추정치임 | 실제 이동과 일정의 차이 | 평균/추정임을 명시하고 복귀 버퍼를 두며, 정확도 검증 지역부터 지원 |
| 지역별 대표음식 데이터 품질 차이 | 식사 추천의 신뢰도 저하 | 대표음식은 P1으로 두고 데이터가 검증된 지역부터 제공 |
| 전국 단위의 조기 확장 | 정규화·검증 범위 과다 | 제한 지역에서 품질과 지표를 먼저 검증한 뒤 확대 |
| 추천 이유가 납득되지 않음 | 핵심 차별점의 신뢰 상실 | 후보별 시간 적합성·관심사·축제 등 구체적 근거를 표시 |
| 자동 일정이 사용자의 선호와 다름 | 이탈 또는 낮은 만족도 | MVP 후반에 재생성, 이후 개별 교체를 검토하고 변경 행동을 측정 |
