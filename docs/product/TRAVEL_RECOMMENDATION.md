# 여행 장소 추천 방법

## 목적

DURUDURU는 사용자가 목적지를 먼저 정하지 않아도, 출발지와 여행 가능 시간 안에 다녀올 수 있는 국내 여행지를 추천하고 선택한 여행지의 참고 계획을 만든다. 초기 MVP의 완성 기준은 자차로 1일차 08:00에 출발해 2일차 20:00까지 복귀하는 1박 2일 여행이다.

추천과 일정 생성은 LLM이나 목업 상수가 아니라 공공 관광 데이터와 규칙 기반 계산으로 수행한다. 결과는 예약·내비게이션·실시간 교통을 보장하는 일정표가 아니라, 여행을 계획하는 데 쓰는 참고 자료다.

## 검색 시작과 데이터 조회

`갈 수 있는 곳 찾기`를 누르는 것이 하나의 검색 실행이다.

1. 서버는 입력한 출발지, 출발·복귀 일시, 자차, 관심사를 검증한다.
2. 서버는 TourAPI에서 지원 후보 지역의 관광지와 음식점을 조회하고, 필요한 상세 정보로 이름, 분류, 좌표, 주소, 운영·휴무 정보, 소개를 보강한다.
3. 서버는 같은 검색 실행에서 필요한 모든 경로 거리·일반 예상시간을 [거리 계산 방법](DISTANCE_CALCULATION.md)에 따라 계산한다.
4. 조회·계산한 데이터는 검색 스냅샷으로 묶어 추천 목록과 목적지별 일정 생성에 재사용한다. 목적지를 고른 뒤에는 새 외부 API를 호출하지 않으며, 다음 검색에서만 새 데이터를 조회한다.

브라우저는 외부 API를 직접 호출하거나 서비스 키를 받지 않는다. API 실패, 시간 초과, 형식 오류는 정적 데이터나 PoC 값으로 대체하지 않고 재시도 가능한 오류로 표시한다.

## 목적지 후보 추천

### 입력과 후보 데이터

- 입력: 출발지, 출발·복귀 일시, 이동수단(초기 MVP는 자차), 관심사
- 후보: TourAPI 데이터가 충분한 지원 지역과 그 지역의 대표 좌표
- 필요 데이터: 출발지↔지역의 양방향 도로 경로, 관광 권역·장소, 음식점, 운영 정보, 체류시간 근거

### 가능 여부

후보마다 출발지에서 지역까지의 왕복 일반 예상시간을 계산한다. `복귀 시각 - 출발 시각 - 왕복 이동시간` 안에 여행을 구성할 수 있는 후보만 남긴다.

후보가 일정 생성에 필요한 최소 데이터를 갖추지 못하면 추천하지 않는다. 필요한 이동시간, 관광 권역, 식사 후보가 부족할 때 카드만 나열해 여행 계획이 가능한 것처럼 표시하지 않는다.

### 정렬

가능한 후보는 다음 순서로 평가한다.

1. 시간 적합성: 왕복 이동 뒤 실제로 쓸 수 있는 시간이 많은가
2. 관심사 적합성: 사용자가 고른 관심사와 관광지 분류·태그가 얼마나 맞는가
3. 여행 구성 가능성: 서로 다른 관광 권역과 식사를 날짜별로 배치할 수 있는가
4. 이동 부담: 지역 내부의 경로 거리·일반 예상시간이 과도하지 않은가

동점은 더 많은 현지 시간을 남기는 후보, 더 짧은 왕복 경로, 안정적인 지역 식별자 순으로 정한다. 평점·리뷰·랭킹은 사용하지 않는다.

## 1박 2일 참고 계획 생성

### 시간 범위

- 1일차는 출발 시각부터 숙소 경계 전까지, 2일차는 숙소 경계부터 복귀 시각까지로 나눈다.
- 숙소 자체는 추천·검색·이동 계산 대상이 아니다. 하루 종료와 다음 날 시작은 목적지 기준점에서 이어지는 경계로 표시한다.
- 출발지→목적지, 관광 권역 사이, 마지막 장소→출발지의 이동은 모두 실제 도로 경로 계산값을 쓴다.

### 장소와 권역

- 같은 유적의 문·정자·전망대처럼 사실상 같은 방문 경험인 세부 장소는 하나의 관광 권역으로 묶는다.
- 데이터가 충분한 경우 각 활동일에 서로 다른 관광 권역을 최소 두 곳 배치한다.
- 관심사 일치, 체류 대비 가치, 이동 부담을 기준으로 장소를 선택한다.
- 체류시간은 API에 있는 정보나 문서화된 분류별 기준으로만 사용한다. 근거가 없는 임의 시간은 넣지 않는다.

### 식사

- 점심은 11:30~~13:30, 저녁은 17:30~~19:30에 최소 1시간을 확보한다.
- 해당 시간에 운영 중이고 지역 대표음식 근거가 있는 음식점을 한 곳 배치한다.
- 미식 관심사가 없어도 식사는 계획에 포함한다. 맛집 평점·리뷰·순위는 선정 기준이 아니다.

### 음식 데이터와 음식점 선정

- 검색 시작 시 TourAPI의 음식점 데이터와 상세 정보를 관광지 데이터와 함께 서버에서 조회한다. 음식점은 이름, 주소·좌표, 운영 정보, 메뉴·분류, 조회 시각을 정규화한다.
- 대표음식 근거는 지자체의 공식 지정·향토음식 공공데이터를 우선하고, 그다음 공공 음식점 데이터의 메뉴 근거를 사용한다. 각 근거의 출처와 조회 시각을 검색 스냅샷에 보존한다.
- 음식점은 대표음식 근거를 우선 필터로 적용한 뒤, 해당 식사 시간의 운영 가능 여부와 경로 이동 부담, 안정 식별자 순서로 하나를 고른다. 평점·리뷰·랭킹은 사용하지 않는다.
- 운영시간을 해석할 수 없거나 대표음식·좌표 근거가 없으면 그 음식점을 식사 후보로 쓰지 않는다. 임시 문자열이나 이전 검색의 정적 음식점 데이터로 대체하지 않는다.

### 결과와 예외

결과는 날짜별 시간대, 관광 권역/장소, 점심·저녁, 이동시간, 짧은 추천 이유를 보여 준다. 조회 시각과 “방문 전 운영·휴무·예약 정보를 다시 확인하세요” 안내를 함께 표시한다.

최소 관광 권역, 식사, 이동시간 조건을 만족할 수 없으면 `지금은 계획을 만들 수 없어요`로 명확히 표시하고 다시 검색할 수 있게 한다. 외부 API 장애와 정상 응답이지만 조건을 채우지 못한 경우는 구분한다.
