# 여행 장소 추천 방법

## 목적

DURUDURU는 목적지를 정하지 못한 사용자가 서울특별시 또는 부산광역시 출발 기준 가용시간 안에 갈 수 있는 국내 여행지를 고르고, 선택한 지역의 1박 2일 참고 계획을 확인하도록 돕는다. 초기 MVP는 1박 2일만 지원하며, 기준 시나리오는 자차로 1일차 08:00에 출발해 2일차 20:00까지 복귀하는 여행이다.

추천과 일정 생성은 최신 공공 관광 데이터와 규칙 기반 계산으로 수행한다. LLM, 평점·리뷰·랭킹, 예약·내비게이션·실시간 교통은 사용하지 않는다.

## 후보 검색과 목적지 선택

`갈 수 있는 곳 찾기`는 목적지 후보를 찾는 첫 단계다.

1. 서버가 지원 출발지(서울특별시 또는 부산광역시), 출발·복귀 일시, 자차, 관심사를 검증한다. 입력 폼은 두 출발지 중 하나만 선택하게 한다.
2. 서버가 선택 출발 지역권에서 전국 252개 여행 지역권까지의 KTDB 자동차 일반 예상 이동시간을 조회한다. 계산 방법은 [지역 간 일반 예상 이동시간 설정](INTERREGIONAL_TRAVEL_TIME.md)을 따른다.
3. 왕복 후 여러 관광지를 배치할 수 있는 시간 적합 후보만 남긴다. 서울·부산 등 특별시·광역시·특별자치시는 시도 단위로 묶고, 도 지역은 시·군 단위로 유지한다. 읍·면·리와 광역시 내부 구는 후보 단위가 아니다.
4. 서버가 하루 1회 수집한 TourAPI 공식 분류 지역 프로필에서 선택 관심사 근거를 확인한다.
5. 선택 카테고리의 공식 분류 관광지가 서로 다른 콘텐츠 ID 기준 3개 이상인 후보 권역을 평가해 최종 3곳을 추천한다. 이 검색 단계에서는 음식점 API를 호출하지 않는다.
6. 조회·계산한 데이터는 검색 스냅샷으로 묶는다. 사용자가 최종 후보를 고르면 선택 지역 한 곳의 음식점 목록 기본 정보만 새 외부 API로 조회한 뒤 계획을 만든다.

관광지 프로필은 하루 1회 수집 작업으로 준비하고, 음식점 목록은 사용자가 선택한 한 지역에만 조회한다. 브라우저는 외부 API를 직접 호출하거나 서비스 키를 받지 않는다. API 실패, 시간 초과, 형식 오류는 정적 데이터나 PoC 값으로 대체하지 않고 재시도 가능한 오류로 표시한다. 상세 호출 순서는 [MVP 데이터 조회 흐름](API_FETCH_FLOW.md), 음식점 범위는 [MVP 음식점 데이터 정책](FOOD_DATA_POLICY.md)을 따른다.

## 목적지 후보 추천

### 입력과 후보 데이터

- 입력: 서울특별시 또는 부산광역시 출발지, 출발·복귀 일시, 이동수단(초기 MVP는 자차), 관심사
- 후보: KTDB 전국 252개 지역권과 TourAPI 법정동 코드 매핑. 표시·추천 단위는 특별시·광역시·특별자치시의 시도 또는 도 지역의 시·군이다.
- 필요 데이터: 서울 출발 지역↔여행 지역 자동차 일반 예상시간, TourAPI 공식 분류 지역 프로필. 점심·저녁 식사 후보는 목적지 선택 뒤 해당 지역에서만 조회한다.

### 가능 여부와 정렬

후보마다 선택 출발 지역권과 전국 여행 지역권의 왕복 일반 예상시간을 계산한다. `복귀 시각 - 출발 시각 - 왕복 이동시간` 안에 1박 2일 계획을 구성할 수 있는 후보만 남긴다.

가능한 후보는 시간 적합성, TourAPI 공식 관심사 적합성, 여러 관광지를 배치할 수 있는 구성 가능성, 더 짧은 왕복 예상시간 순으로 평가한다. 특별시·광역시·특별자치시 권역은 포함 존의 공식 분류 관광지를 콘텐츠 ID 기준으로 합치고, 이동시간·선택 후 음식점 조회에는 그중 가장 짧은 일반 예상시간의 대표 존을 쓴다. 분류 코드가 비었거나 선택 카테고리의 서로 다른 관광지 콘텐츠 ID가 3개 미만인 지역은 해당 추천에서 제외한다. 음식점 보유 여부는 이 단계의 추천 조건이 아니다. 관광지 내부 이동시간은 계산·선정·제약·표시에 쓰지 않는다. 동점은 더 많은 현지 시간, 안정적인 지역 식별자 순으로 정한다.

필요한 관광지 근거가 부족하면 추천하지 않는다. 추천 카드에는 관광지·시간 근거를 표시하며, 음식점은 목적지 선택 뒤 조회한다.

## 1박 2일 참고 계획 생성

### 시간 경계

- 1일차는 출발 시각부터 21:00 전까지, 2일차는 07:00부터 복귀 시각까지로 나눈다.
- 매일 21:00부터 다음날 07:00까지는 휴식으로 고정한다. 이 구간에는 관광·식사·이동을 배치하지 않는다.
- 1일차 서울 출발 지역→여행 지역과 2일차 여행 지역→서울 출발 지역의 시간만 KTDB 지역 간 일반 예상시간으로 반영한다.
- 관광지와 음식점은 각각 1시간을 차지한다. 여행지 내부 장소↔장소, 장소↔음식점 이동시간은 계산하거나 시간표에 표시하지 않는다.

### 관광지

- 사용자가 고른 TourAPI 공식 관심 카테고리에 맞는 관광지를 추천한다. 자연은 `A01`, 역사는 `A0201`, 휴양은 `A0202`, 문화는 `A0206` 또는 콘텐츠유형 `14`, 레저는 `A03` 또는 콘텐츠유형 `28` 근거만 쓴다. 휴양·레저를 UI에서 하나로 묶더라도 원천 코드는 분리 보존한다.
- 같은 장소의 세부 지점이 중복으로 보일 경우 하나의 관광 방문으로 묶는다.
- 식사와 휴식 경계 밖의 남는 시간에 관광지를 배치한다. 체류시간은 모두 1시간으로 고정한다.

### 식사와 음식점

- 점심은 11:30~~13:30, 저녁은 17:30~~19:30 안에 각각 최소 1시간을 배치한다.
- 식사는 관심사와 무관하게 반드시 배치한다. 네 식사 칸은 서로 다른 음식점을 우선 배정하며, 목록에 확보된 서로 다른 음식점 수보다 많은 칸은 비워 두고 `추천할 식당을 더 찾지 못했어요`를 표시한다.
- 음식점은 사용자가 목적지를 선택한 뒤 그 지역 한 곳의 TourAPI 목록 기본 정보를 조회해 고른다. 지역N문화의 향토음식 문화 키워드는 약한 보조 근거로만 쓰고, 관련 음식점 필드는 직접 추천·매칭에 쓰지 않는다. 모범음식점 공식 지정·음식 종류는 인증 캐시와 TourAPI 목록의 전화번호 또는 정규화 상호·주소가 일치할 때만 반영한다. 그 뒤 TourAPI 목록 기본 정보와 안정적인 콘텐츠 ID 순으로 우선순위화한다. 이 근거는 목적지 후보 제외 조건이 아니다. 목록 조회 중에는 진행 상태를 보이고, 운영시간·메뉴·휴무는 조회하거나 식사 적합성의 조건으로 쓰지 않는다.
- 여행지 내부 거리·이동시간은 음식점 선정·일정 제약·사용자 표시에는 쓰지 않는다.
- 평점·리뷰·랭킹은 사용하지 않는다.
- 기본 정보가 없으면 그 음식점을 추천하지 않는다. 사용자는 음식점을 클릭해 서버가 조회한 상세 운영시간·메뉴를 확인하며, 방문 전 재확인이 필요하다.

### 결과와 예외

결과는 1일차·2일차별 관광·점심·저녁 시간표, 출발·복귀 일반 예상시간, 짧은 추천 이유, 조회 시각을 보여 준다. “방문 전 운영·휴무·예약 정보를 다시 확인하세요” 안내를 함께 표시한다.

관광지 또는 출발지↔여행지 시간이 부족해 최소 시간표를 만들 수 없으면 `지금은 계획을 만들 수 없어요`로 명확히 표시하고 다시 검색할 수 있게 한다. 선택 지역의 음식점 목록 수집에 실패하면 목적지 추천은 유지하고 식사 정보 수집 실패와 재시도를 표시한다. 외부 API 장애와 정상 응답이지만 조건을 채우지 못한 경우는 구분한다.
