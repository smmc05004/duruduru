# DURUDURU 기능 명세서

> 상태: MVP 구현 기준 기능 명세. MVP 개발은 착수했고 PoC는 종료했다(`DECISIONS.md`의 `확정` — 개발 단계). 이 문서는 구현 작업을 분해하기 위한 기준이며, `PRD.md`와 `DECISIONS.md`의 확정·제안·보류 상태를 변경하지 않는다.
>
> 우선순위: 문서 간 해석 충돌 시 `PRD.md`와 `DECISIONS.md`를 우선한다. 제품 결정을 새로 확정해야 하는 경우에는 구현 전에 `DECISIONS.md`에 기록한다.

## 1. 목적·적용 범위·기준선

### 1.1 목적

목적지를 정하지 못한 국내 여행자가 출발지와 출발·복귀 가능 일시, 관심사를 입력하면, 시간 안에 실제로 다녀올 수 있는 목적지를 먼저 비교하고 선택한 목적지의 제약 충족 일정을 확인하게 한다. 핵심 추천과 일정 생성은 공공데이터 및 규칙/점수 기반으로 처리하며, LLM은 사용하지 않는다.

### 1.2 종료된 PoC와 MVP 요구사항

| 구분 | 종료된 PoC | MVP 요구사항 |
| --- | --- | --- |
| 데이터 | 경주·공주·강릉 목업 | 검증된 제한 지역의 정규화된 공공데이터 |
| 추천 | 고정 이동시간, 관심사 태그, `왕복 + 7시간` 목업 규칙 | 출발지·목적지·이동수단별 추정 이동과 최소 현지 체류 제약 (복귀 버퍼는 2026-08-31 결정으로 도입하지 않는다) |
| 일정 | 장소 간 30분 고정, 순차 배치 | 운영시간·휴무·체류·이동·식사·복귀를 모두 검증한 배치 |
| 신뢰도 | 목업 고지 | 출처·갱신·추정·fallback·결측을 결과별로 표시 |
| 지원 조건 | 서울·대전·부산, 자차/대중교통 UI | 초기 지역·자차·도시 입력은 각각 `제안` 상태이며 확정 후 적용 |

PoC는 화면/흐름 검증을 마치고 첫 커밋으로 종료했다. 따라서 PoC의 화면·스타일·목업 로직은 보존 대상이 아니라 이 명세의 MVP 요구사항으로 교체될 대상이며, MVP 요구사항은 기존 사용자 흐름 자리에서 구현한다. 다만 **PoC의 숫자·목업 데이터·대중교통 UI는 정식 정책으로 승격하지 않는다.** 각 요구사항의 구현 가능 시점은 `DECISIONS.md`의 `확정`·`제안`·`보류` 상태로 판단한다.

### 1.3 비범위

로그인, 개인화, 저장·공유, 실시간 교통, 정밀 내비게이션, 예약·결제, 맛집 평점·랭킹, 방문 인증·스탬프·친구·랭킹·미션, 전국 동시 지원, LLM 기반 핵심 엔진은 범위 밖이다. 숙박은 2026-08-31 결정으로 **숙박지를 고려하지 않는다** — 숙박 시설의 데이터·후보 산출·일정 배치·표시를 하지 않고, 1박 이상 일정에는 "저녁에는 숙소로 돌아간다" 정도만 반영한다(`DECISIONS.md` 7.4절). 따라서 "1박 2일 정식 구현 전 별도 결정"이라는 차단은 해제됐다. 다만 숙소 위치를 쓰지 않으므로 **"숙소로 돌아간다"의 이동시간과 다음날 시작 지점은 `보류`이며 F-04 배치 단계(E6·E7)에서 별도 결정으로 기록한다.**

## 2. 기능 목록과 우선순위

| ID | 우선순위 | 기능 | 사용자 가치 | 범위 / 비범위 |
| --- | --- | --- | --- | --- |
| F-01 | P0 | 여행 조건 입력·검증 | 자신의 실제 제약을 정확히 전달한다. | 출발지·출발/복귀 일시·이동수단·관심사 입력. 주소 지오코딩과 P2 조건은 제외. |
| F-02 | P0 | 목적지 가능 여부·추천 | 갈 수 있는 목적지를 목적지 미정 상태에서 비교한다. | 시간 제약 통과 후보와 3~5개 목표 목록. 후보 수 부족 표시는 정책 결정 의존. |
| F-03 | P0 | 점수·추천 근거 | 추천 결과를 납득하고 선택한다. | 시간/관심사/선택적 축제 적합성 근거. 인기순·블랙박스 점수는 제외. |
| F-04 | P0 | 제약 기반 일정 생성 | 선택 지역의 실행 가능한 시간표를 얻는다. | 운영·휴무·체류·이동·식사 시간·복귀 검증. 숙박·예약은 제외. |
| F-05 | P0 | 근거·데이터 신뢰도 표시 | 추정과 불완전한 데이터를 구분해 판단한다. | 출처·갱신·평균/추정·fallback/결측 표시. 실시간 정확성 보장은 제외. |
| F-06 | P1 | 축제 반영 | 여행 기간에 맞는 부가 경험을 발견한다. | 기간·지역·관심사 적합 시 제안/배치. 축제 강제 삽입 금지. |
| F-07 | P0(대표음식 기반 음식점 배치) / P1(그 외) | 대표음식·동선 인근 식사 제안 | 일정 속 식사 선택을 돕는다. | P0: 식사 블록에 해당 지역 대표음식을 파는 음식점 한 곳을 배치. P1: 동선 최적화 기반 선정, 복수 대체 후보 제시, 관심사(미식) 연동 큐레이션. 맛집 순위·평점은 우선순위와 무관하게 제외. |
| F-08 | P1 | 일정 재생성·장소 교체 | 자동 결과를 최소 범위에서 조정한다. | 포함 범위가 `보류`이므로 결정 전 구현하지 않는다. |
| F-09 | P2 | 대중교통·동행·날씨·예산 | 더 많은 조건을 반영한다. | 핵심 가설 검증 후 별도 단계. |

문서 정합성(2026-08-31 갱신): 이전 판은 "F-04는 식사 시간 블록 확보까지만 P0으로 다루며, 어떤 음식점을 제안할지는 F-07로 분리한다"였다. 2026-08-31 사용자 결정으로 **음식점도 일정에 포함**하기로 확정했고, 관심사에서 미식을 고르지 않아도 끼니를 거르지 않는다. 따라서 F-04의 P0 범위는 식사 시간 블록 확보 + **그 블록에 대표음식 기반 음식점 한 곳 배치**까지이며, F-07의 나머지(동선 최적화 선정, 복수 대체 후보, 미식 관심사 큐레이션)는 P1에 남는다. **맛집 평점·랭킹은 1.3절과 `PRD.md` 비목표 그대로 범위 밖이다** — 선정 기준은 "해당 지역의 대표 음식을 파는 음식점"이며 순위·평점·리뷰 수를 정렬 기준으로 쓰지 않는다.

## 3. P0 상세 명세

### F-01. 여행 조건 입력·검증

| 항목 | 명세 |
| --- | --- |
| 입력 | 출발지 식별자, 출발 일시, 복귀 가능 일시, 이동수단, **관심사 1개 이상(필수)**. 관심사 필수화는 2026-08-31 확정이며 근거는 `DECISIONS.md` 7.3절이다. 정식 허용값은 지원 지역·이동수단 결정 후 데이터 계층이 제공한다. |
| 검증 | 필수값 누락(**관심사 0개 선택도 필수값 누락이다**), 파싱 불가 일시, 출발 이상이 아닌 복귀, 지원하지 않는 출발지/이동수단은 제출을 막고 항목별 오류를 표시한다. 과거 일시 허용 여부와 최소 여행 기간은 별도 정책 없이는 고정하지 않는다. |
| 처리 | 사용자가 제출한 원문 조건과 정규화된 조건을 결과 생성 동안 유지한다. 시간 계산은 하나의 명시적 시간대 기준으로 수행한다. **여행 유형은 출발·복귀가 걸치는 서로 다른 KST 달력일 수로 판별한다** — 일수 = 달력일 수, 박수 = 일수 − 1. 달력일이 바뀌면 1박 2일이고 그 이상도 같은 방식으로 센다. 무박(밤새 이동)은 별도 유형으로 다루지 않는다(2026-08-31 확정 — `DECISIONS.md` 7.4절). |
| 출력 | 제출 조건 요약, 수정 가능한 입력 폼, 항목별 검증 오류. |
| 오류/결측 | 지원 조건 데이터 자체를 불러오지 못하면 추천을 시작하지 않고 재시도 안내를 표시한다. 임의 출발지·이동수단으로 대체하지 않는다. |
| 수용 기준 | 복귀가 출발보다 빠른 입력은 추천 엔진에 전달되지 않는다. **관심사를 하나도 선택하지 않은 입력도 추천 엔진에 전달되지 않는다.** 유효한 제출의 모든 조건은 추천/일정 결과 요약에서 동일하게 확인된다. 판별된 여행 유형과 그에 적용된 최소 현지 체류시간은 결과에서 확인된다. |

### F-02. 목적지 가능 여부·추천

| 항목 | 명세 |
| --- | --- |
| 입력 | 검증된 여행 조건, 지원 목적지 목록, 출발지→목적지 이동시간, 목적지 메타데이터, 최소 현지 체류시간 정책, 점수 정책(가중치·동점 규칙). |
| 처리 규칙·제약 | 후보별 `현지 이용 가능 시간 = 복귀 - 출발 - 편도 이동×2`를 계산한다. **복귀 버퍼는 계산식에 넣지 않는다**(2026-08-31 확정 — `DECISIONS.md` 2.3절). 현지 이용 가능 시간이 해당 여행 유형의 최소 현지 체류시간 이상인 후보만 통과시킨다. 여행 유형은 F-01의 KST 달력일 기준으로 판별하고, 최소 현지 체류시간은 `4시간 × 일수`(일수 = 박수 + 1)로 구한다 — 당일치기 4시간, 1박 2일 8시간, 2박 3일 12시간(2026-08-31 확정 — `DECISIONS.md` 6.3절). 이동시간은 실시간값이 아닌 평균 또는 추정값이며 종류를 보존한다. 결과는 참고 계획이므로 이동시간이 추정임을 표시하되 안전 여유를 값으로 더하지 않는다. |
| 점수 | 통과 후보만 정렬한다. 시간 적합성, 관심사 일치, F-06이 구현된 뒤 조건을 충족한 축제 적합성만 점수 구성요소로 사용할 수 있다. 가중치와 동점 규칙은 2026-08-31에 확정됐다(`DECISIONS.md` 6.1절). 구성요소를 0~1로 수치화하는 식도 같은 날 확정됐다(`DECISIONS.md` 7.1·7.2절) — **시간 적합성 = 현지 이용 가능 시간 / (복귀 − 출발)**, **관심사 일치 = (목적지 태그 ∩ 선택 관심사) 개수 / 선택 관심사 개수**. 두 값은 후보 집합에 의존하지 않는 절대 기준이며, 후보 중 최대값으로 정규화하지 않는다. 계산할 수 없는 구성요소는 항을 제외하고 남은 항을 합이 1이 되도록 재정규화한다(축제 미구현 구간과 동일한 규칙). 값은 소스 상수가 아니라 **버전이 있는 점수 정책으로 주입**하고, 결과에는 정책 버전·사용된 가중치·적용된 동점 단계를 남긴다. |
| 출력/표시 | 목표 3~5개 후보의 지역명, 시간 적합성, 왕복 예상 이동시간, 현지 이용 가능 시간, 관심사 적합성, 추천 근거, 데이터 신뢰도. 후보 선택 동작을 제공한다. |
| 오류·결과 없음 | 모든 후보가 제약을 탈락하면 결과 없음을 정상 결과로 표시하고 더 이른 출발·더 늦은 복귀·지원 범위 내 출발지 조정 같은 행동을 안내한다. 후보가 1~2개일 때 표시/확장 정책은 보류 항목이며 임의 보충 후보를 넣지 않는다. |
| 수용 기준 | 제시된 모든 후보는 계산식상 최소 현지 체류시간을 충족한다. 통과하지 못한 후보는 추천 목록에 나타나지 않는다. 각 후보에는 실제 점수/통과에 기여한 근거가 하나 이상 있다. |

### F-03. 점수·추천 근거

| 항목 | 명세 |
| --- | --- |
| 입력 | F-02의 제약 계산 결과, 관심사 태그 일치 결과, 선택적으로 축제 적합성 결과, 데이터 출처 상태. |
| 처리 규칙 | 근거 문구는 실제 계산된 항목만 사용한다. 관심사 미일치 후보에 관심사 적합을 주장하지 않으며, 결측/fallback을 확정 정보처럼 표현하지 않는다. 탈락 이유는 사용자가 비교를 요청하거나 결과 없음인 경우 설명 가능한 형태로 생성한다. |
| 출력/표시 | 후보별 시간 근거, 관심사 근거, 선택적 축제 근거, 이동시간의 평균/추정 표기. 점수 숫자를 표시하면 항목 또는 계산 원칙을 함께 표시한다. 시간 근거는 "가용시간 중 이동에 쓰이지 않은 비율"로, 관심사 근거는 "선택한 관심사 중 몇 개가 일치했는가"로 설명할 수 있어야 한다(`DECISIONS.md` 7.1·7.2절의 산식이 그대로 문장이 된다). |
| 오류·결측 | 근거 데이터가 없으면 해당 근거를 제거하고 신뢰도 상태를 표시한다. 누락을 임의의 긍정 점수로 바꾸지 않는다. |
| 수용 기준 | 화면의 근거와 엔진의 입력/점수 로그가 일치한다. 추천 순서를 바꾸는 모든 규칙은 재현 가능하다. |

### F-04. 제약 기반 일정 생성

| 항목 | 명세 |
| --- | --- |
| 입력 | 선택 목적지, 검증된 여행 조건, 장소/축제/음식점 후보, 장소별 운영시간·휴무·날짜 예외·체류시간, 장소 간 이동시간, 복귀 이동시간, 식사 정책, 점수 정책, 결측 정책. |
| 처리 규칙·제약 | 출발→도착부터 복귀 출발→복귀까지 절대 시각 순서로 배치한다. 관광 항목은 방문 날짜의 운영시간 안에 시작·종료하고 휴무/예외 운영과 충돌하지 않아야 한다. 각 항목 종료와 다음 항목 시작 사이에 이동시간을 넣는다. 식사 블록은 **점심 11:30~13:30, 저녁 17:30~19:30 시간대 안에서 최소 1시간**을 확보하고, 일정에 여유가 있으면 그 이상으로 늘릴 수 있다(2026-08-31 확정 — `DECISIONS.md` 6.2절). 각 식사 블록에는 대표음식 기반 음식점 한 곳을 배치하며, 음식점도 운영시간·휴무 검증을 관광 항목과 동일하게 받는다. **마지막 항목 종료 + 목적지→출발지 이동은 복귀 가능 일시 이하이어야 한다**(복귀 버퍼 항은 없다). 제약을 만족하지 못하는 장소는 배치하지 않는다. |
| 선택·점수 | 먼저 제약 충족 가능 여부를 판단한 뒤 관심사 적합성, 체류 대비 가치, 이동 부담의 규칙 기반 점수로 후보를 우선한다. 가중치와 동점 규칙은 2026-08-31에 확정됐다(`DECISIONS.md` 6.1절)이며 F-02와 같은 방식으로 정책 주입·결과 기록한다. 탐색 순서가 결과를 좌우하면 그 규칙과 탈락 사유를 기록한다. 축제는 F-06 조건 충족 시에만 후보로 넣는다. 음식점은 대표음식 연결과 운영 가능 여부로만 고르고 평점·랭킹을 정렬 기준으로 쓰지 않는다. |
| 출력/표시 | 날짜별 시간표에 출발·이동·방문·식사(음식점명·대표음식 근거 포함)·선택적 축제·복귀를 시간순으로 보인다. 각 항목에는 시작/종료, 체류시간, 다음 이동, 운영 가능 여부, 근거와 신뢰도 상태를 보인다. 복귀 가능 계산을 별도 요약한다. |
| 오류·결과 없음·결측 | 선택 목적지에서 완전한 제약 충족 일정이 없으면 “일정 생성 불가”와 제약 원인/조건 조정을 제시하며 불완전 일정을 성공 결과로 표시하지 않는다. 운영시간·휴무 결측은 후보에서 제외한다(2026-08-31 확정). 체류시간 결측의 카테고리 기본값 fallback은 형태만 확정됐고 값과 출처 등급 집합이 미정이므로, 그 값이 정해지기 전에는 fallback을 적용한 확정 일정을 생성하지 않는다. 적용된 fallback은 항목별로 표기한다. |
| 수용 기준 | 생성 일정의 모든 방문·식사 항목은 배치 시간에 열려 있고 휴무가 아니며, 모든 연속 이동과 복귀 제약을 만족한다. 일정이 점심·저녁 시간대를 지나면 해당 식사 블록이 누락되지 않고, 각 블록은 최소 1시간이며 대표음식 근거가 있는 음식점이 붙는다. 마지막 항목 종료와 복귀 이동의 합이 복귀 가능 일시를 넘는 일정은 출력되지 않는다. |

### F-05. 근거·데이터 신뢰도 표시

| 항목 | 명세 |
| --- | --- |
| 입력 | 각 추천/일정 계산에 쓰인 데이터의 출처, 수집·갱신 시각, 값 종류(공식/평균·추정/fallback/결측), 정상 데이터 여부. |
| 처리 규칙 | 결과 단위와 항목 단위에 적용 데이터 상태를 연결한다. 외부 수집 실패 시 마지막 정상 데이터 사용 여부와 갱신 시각을 보존한다. 신뢰도 등급의 이름/색은 구현에서 정하되 값의 근거를 숨기지 않는다. |
| 출력/표시 | 최소한 이동시간 추정 표기, 장소 운영/휴무/체류 데이터 출처·갱신·fallback 여부, 데이터 부족 경고를 제공한다. |
| 오류·결측 | 데이터 계층 장애는 결과 생성 오류로 구분한다. 마지막 정상 데이터를 썼다면 그 사실과 시점을 표시한다. 결측을 빈 화면이나 확정값으로 표현하지 않는다. |
| 수용 기준 | 화면의 모든 추정·fallback 표시는 해당 데이터 계약의 상태와 일치한다. 사용자는 일정이 실시간 교통 보장이 아님을 확인할 수 있다. |

## 5. 도메인 데이터 계약

구체 API·DB·테이블 설계는 이 명세의 범위가 아니다. 데이터는 공공 API를 주기 수집·정규화한 내부 데이터 계층에서 제공하고, 매 사용자 요청의 외부 API 직접 호출을 전제로 하지 않는다.

| 도메인 | 필수 필드 | 출처·갱신·신뢰도 계약 | fallback/결측 |
| --- | --- | --- | --- |
| 출발지·목적지 | 안정 식별자, 표시명, 행정권역, 지원 상태, 좌표 또는 이동 산출에 필요한 기준점 | 출처와 갱신 시각, 지원 범위 버전 | 기준점 없으면 추천 대상 제외 |
| 목적지 태그 | 목적지 ID, 관심사 태그, 태그 근거/출처 | 정규화 시점과 출처 보존 | 태그 없음은 관심사 가점 없음; 임의 태그 금지 |
| 출발지↔목적지 이동 | 출발/도착 ID, 이동수단, 편도 예상시간, 거리(있다면), 산출 방식, 기준일 | 도로공사 평균/과거 데이터 등 출처, 갱신일, 평균·추정 표기 | 값 없으면 가능 여부 계산 불가로 후보 제외 |
| 장소 | 장소 ID, 목적지 ID, 이름, 카테고리, 좌표, 설명 | 공공 관광 데이터 출처·갱신일 | 필수 식별/위치 부족 시 일정 후보 제외 |
| 운영 정보 | 장소 ID, 적용 날짜/요일, 운영 구간, 휴무, 예외 운영, 출처·갱신일 | 공식 정보 우선, 날짜별 예외 여부 명시 | 운영시간·휴무 결측은 제외(2026-08-31 확정) |
| 체류시간 | 장소 ID 또는 카테고리, 권장 시간, 값 출처 수준 | 실제 통계→공식 권장→카테고리 기본값 순의 출처 수준 표시 | 카테고리 기본값 사용은 확정, 값과 출처 등급 집합은 미정 |
| 장소 간 이동 | 출발 장소/도착 장소 ID, 이동수단, 예상시간, 산출 방식, 기준일 | 좌표 거리+보정 또는 추후 경로 서비스, 추정 표기 | 값 없으면 연속 배치 불가 |
| 축제 | ID, 지역, 시작/종료, 성격/태그, 운영 시간(있다면), 출처·갱신일 | TourAPI 등 공공데이터, 기간 검증 | 핵심 일정 제약 필드가 부족하면 추천 근거/제안으로만 처리 |
| 지역 대표음식 | 목적지 ID, 대표음식명(원문 표기 보존), **별칭**, 대표음식 근거/출처(제공기관·데이터셋·원문 URL), **소스 유형과 신뢰도**, 확인일·정규화 시점 | 지자체 대표·향토음식 공개데이터 우선. 소스 유형 4종·신뢰도 4단계를 보존한다(2026-08-31 확정 — `DECISIONS.md` 6.4절, 정의는 `docs/product/FOOD_DATA_STRATEGY.md` 2절). 메뉴 텍스트에서 도출한 근거를 공식 지정과 동일하게 취급하지 않는다. 하나의 음식에 여러 근거를 연결할 수 있어야 한다 | 대표음식이 없는 목적지는 음식점 배치 근거가 없으므로 식사 블록만 확보하고 음식점을 배치하지 않는다. 별칭의 부분 문자열 일치만으로 메뉴 일치를 확정하지 않는다 |
| 음식점 | 장소 ID, 목적지 ID, 이름, 좌표, 연결된 대표음식 참조와 그 연결 근거, 운영 구간·휴무·날짜 예외, 예상 식사 소요시간, 출처·갱신일 | 공공데이터 API(TourAPI 음식점 등)에서 주기 수집·정규화하며 주기는 소스별 갱신주기에 맞춘다(2026-08-31 확정). 대표음식 연결은 근거를 보존하고 임의 연결을 금지한다 | 좌표·대표음식 연결이 없으면 배치 후보에서 제외. 운영시간·휴무 결측은 관광 장소와 같은 제외 규칙(2026-08-31 확정)을 적용하며 **운영시간 파싱 실패도 결측으로 다룬다.** 배치 가능한 음식점이 없으면 식사 블록만 확보하고 그 사실을 표시한다 |

## 6. 추천·일정 엔진 요구사항

- 엔진은 결정론적 규칙/점수 기반이어야 한다. 같은 입력·데이터 버전·정책 버전은 같은 후보 순서와 일정을 낸다.
- 제약 충족 여부를 점수보다 먼저 판정한다. 불가능한 목적지·장소를 높은 관심사 점수로 통과시키지 않는다.
- 추천 계산은 후보별 여행 총시간, 왕복 이동, 현지 이용 가능 시간, 최소 체류 충족 여부, 점수 구성요소를 산출한다. 복귀 버퍼 항은 없다(2026-08-31 확정).
- 일정 계산은 각 항목의 시작·종료·이동·운영 검증 결과·탈락 사유·복귀 여유를 산출한다.
- 사용자 표시와 운영 검증을 위해 입력 조건, 데이터 버전/상태, 정책/점수 버전, 결과를 연결 가능하게 기록한다. 개인 식별 정보의 수집은 이 요구사항에 포함하지 않는다.
- 결과 설명은 위 산출값에서 생성한다. 설명만 그럴듯하게 만드는 별도 생성 모델을 사용하지 않는다.

## 7. 구현 단위·순서·완료 조건

### 7.1 음식점·대표음식 데이터 조사 항목 (E2)

2026-08-31 결정으로 음식점 배치가 P0에 들어왔으므로 E2 데이터 품질 조사에 음식점·대표음식 항목을 추가했다. **같은 날 세 차례 조사로 아래 여덟 항목 중 일곱이 답을 얻었다.** 실측 값·표본·한계는 `docs/product/FOOD_DATA_STRATEGY.md` 3절에 있고, 후속 순서는 `docs/product/FOOD_DATA_NEXT_STEPS.md`에 있다. 아래 표는 무엇이 답해졌고 무엇이 남았는지로 갱신했다.

| 확인 항목 | 상태 | 확인된 것 / 남은 것 |
| --- | --- | --- |
| 초기 지역별 음식점 건수 | **답했다** | 경주 211 · 공주 76 · 강릉 482. 세 지역 모두 후보 0이 아니다 |
| 좌표 충족률 | **답했다** | 100% (전수 769건 누락 0) |
| 운영시간 충족률 | **답했다 / 새 차단 요인** | 충족률 100%. 그러나 **자유 서식**이라 브레이크타임·라스트오더·자정 넘김·오타가 실제 값에 있다. 파싱 규칙이 없으면 점심 준비시간에 식사를 배치하는 오류가 난다. 파싱 실패는 결측으로 다룬다 |
| 휴무·날짜 예외 충족률 | **부분** | 휴무 93%(표본 60건). 날짜 예외 필드의 유무는 확인하지 않았다 |
| 메뉴·대표메뉴 정보 충족률 | **답했다** | 209/211 · 76/76 · 300/304. 대표메뉴·취급메뉴 두 필드가 제공된다 |
| 지역 대표음식 데이터의 지역 커버리지와 출처 | **답했다** | 소스 3종 확인(향토음식 데이터·모범음식점 표준데이터·음식점 메뉴 파생). 시군구 커버리지 133/226(약 59%), 초기 3지역은 강릉 15 · 경주 2 · 공주 2. **탈락시킨 소스와 그 이유**는 `docs/product/FOOD_DATA_STRATEGY.md` 4절에 있고 다시 조사하지 않는다 |
| 대표음식 ↔ 음식점 연결 방식의 판정 가능성 | **답했다** | **카테고리로는 불가**(7단계 대분류, 빈 값 최대 49%, 신규 체계는 지정 유형). **메뉴 텍스트로만 가능**하며 별칭 처리가 필수다(같은 음식의 표기 변형이 실측됐다). 문자열 부분 일치만으로 확정하지 않는다 |
| 갱신 주기와 마지막 갱신 시각 | **답했다** | 소스별로 크게 다르다 — 향토음식 데이터는 비주기(최종 2023-12-21), 모범음식점은 레코드에 갱신시점 존재, TourAPI는 상시이나 일일 요청 한도가 있다. 이 결과로 "하루 한 번 수집" 전제를 소스별 주기로 정정했다(`DECISIONS.md` 1절) |

**남은 조사 항목** — 강릉 잔여 178건, 전국 베이스라인 구성, 소표본 임계 표본 수, 향토음식 CSV의 컬럼·행수, 운영시간 서식 변형의 전수 분포. 우선순위와 이유는 `docs/product/FOOD_DATA_NEXT_STEPS.md` 4절에 있다.

**남은 구현 선행 조건** — (1) 운영시간 자유 서식 파싱과 그 실패 처리, (2) 3지역 대표음식 목록 확정(절차는 `docs/product/FOOD_DATA_NEXT_STEPS.md` 3절). 이 둘이 P0 음식점 배치의 실제 차단 요인이다.

미달 항목은 값이 아니라 **후보 제외 또는 식사 블록만 확보**라는 이미 확정된 규칙으로 처리한다. **음식점 관련 숫자(대표음식 목록의 실제 음식명, 예상 식사 소요시간)는 여전히 문서·코드에 넣지 않는다.** 현재 `scripts/probe-tourapi.mjs`는 관광지·문화시설과 축제만 조회하므로 음식점 조회 추가는 남은 작업이다.

### 8.2 이벤트와 성공 지표 관측

이벤트의 저장 방식·분석 도구는 정하지 않는다. 이벤트에는 세션 단위 식별자, 익명화된 조건 범주, 데이터/정책 버전, 결과 상태를 포함하되 개인 식별·정확한 위치의 불필요한 수집을 피한다.

| 이벤트 | 발생 시점 | 필수 속성 | 지표 |
| --- | --- | --- | --- |
| `trip_conditions_submitted` | 유효 조건 제출 | 출발지 범주, 기간, 이동수단, 관심사 수, 정책 버전 | 입력→결과 전환 |
| `recommendations_viewed` | 후보/결과 없음 표시 | 후보 수, 결과 상태, 데이터 상태, 엔진 버전 | 후보 선택률 분모 |
| `destination_selected` | 후보 선택 | 목적지 ID, 순위, 근거 종류 | 후보 선택률 분자 |
| `itinerary_requested` | 일정 계산 시작 | 목적지 ID, 조건/데이터 버전 | 생성 완료율 분모 |
| `itinerary_generated` | 제약 충족 일정 표시 | 복귀 충족, 항목 수, fallback/결측 사용 | 생성 완료율·복귀 충족률 |
| `itinerary_unavailable` | 일정 불가 표시 | 원인 분류, 데이터 상태 | 제약/데이터 병목 |
| `data_fallback_applied` | fallback/마지막 정상 데이터 사용 | 도메인, 상태, 갱신 시각 | fallback 비율 |
| `recommendation_feedback_submitted` | 만족 응답 완료 | 결과 상태, 응답값 | 만족 응답 |

지표의 기간, 목표값, 정확한 분모 제외 규칙은 아직 미확정이다. 구현 전 운영 계획에서 정하되 PRD의 지표 정의(후보 선택률, 일정 생성 완료율, 복귀 충족률, 무효 일정 비율, fallback 비율)를 훼손하지 않는다.
