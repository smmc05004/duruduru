# DURUDURU 프로젝트 컨텍스트

> 대상: 이후 DURUDURU의 범위·우선순위·검증 계획을 수립할 PM 에이전트
>
> 이 문서는 제품 의사결정과 조사 맥락을 보존하기 위한 자료다. 현재 구현 상태의 기준은 코드이며, 제품 요구사항과 결정 상태는 `PRD.md`, `DECISIONS.md`를 함께 확인한다. 2절의 PoC 서술은 첫 커밋으로 종료된 PoC의 기록이며 현재 코드 상태를 나타내지 않는다.

## 1. 제품 배경과 정체성

- 서비스명은 **DURUDURU / 두루두루**다. 초기 명칭 후보였던 ‘방방곡곡’ 대신 두루두루로 결정했다.
- 국내 여행 계획 추천 서비스다.
- 핵심 차별점은 사용자가 목적지를 먼저 정하지 않는다는 점이다. 출발지, 정확한 출발/복귀 일시, 자차 여부, 여행 목적, 관심사(역사·문화·자연 등)를 입력하면 사용 가능한 시간 안에 갈 수 있는 목적지 후보부터 추천하고, 사용자가 선택한 지역의 일정을 생성한다.
- 대표 시나리오: 서울에서 토요일 08:00 출발, 일요일 20:00 복귀, 자차, 관광 목적, 역사 관심사라면 공주·부여·경주·강릉 등 시간 제약을 통과한 후보를 먼저 비교한 뒤 한 곳의 여행 일정을 만든다.

기존 여행 플래너의 질문은 “경주에 갈 건데 무엇을 할까?”에 가깝다. DURUDURU가 검증하려는 질문은 “이번 주말 이 시간에 어디를 다녀올 수 있을까?”다. 개별 일정·공유·게임화 기능 자체가 새롭다는 가설이 아니라, **시간 기반 목적지 추천이 실제로 사용자의 출발점 문제를 해결하는지**가 핵심 가설이다.

## 2. 종료된 PoC의 기록

PoC는 Next.js + TypeScript App Router 기반의 화면 중심 구현이었고 첫 커밋으로 종료했다. 아래는 그때의 범위 기록이다.

- 입력: 출발지(서울·대전·부산), 출발/복귀 일시, 자차/대중교통, 역사·자연·문화·미식 관심사
- 후보: 경주·공주·강릉 목업 데이터
- 추천: 전체 여행시간, 목적지별 자차/대중교통 고정 평균 이동시간, 관심사 태그 일치, ‘왕복 이동시간 + 7시간’ 기준으로 계산하는 단순 점수
- 일정: 관심사에 맞는 장소 우선 정렬, 목업 운영시간·휴무 요일·권장 체류시간 확인, 장소 사이 고정 30분, 복귀 이동 항목 표시
- 축제: 입력 기간과 목업 축제 기간이 겹치면 제안 항목을 삽입
- 음식: 지역별 대표음식 문자열을 표시
- TourAPI: 앱에 연결되지 않았다. `npm run check:tour-api`는 키가 주어졌을 때 경주·공주·강릉 데이터의 필드 충족률을 조사하는 수동 프로브다.
- DB, 로그인, 저장, 실제 교통/경로, 실제 음식점 데이터, 테스트 러너는 없다.

PoC는 대표 흐름을 보여 주었지만 실제 여행에 쓸 만큼 일정 제약을 보장하지 않았다. 출발지별 이동시간, 관광지 간 실제 이동시간, 식사, 숙박, 복귀 시각 이전의 모든 일정 배치, 날짜별 예외 운영이 그 대상이다. 이 한계를 해소하는 것이 MVP 요구사항이며, **PoC의 목업 값·7시간 기준·대중교통 UI는 정식 정책으로 승격하지 않는다.**

## 3. 핵심 제품·기술 결정

### 확정 또는 강한 방향

- 핵심 추천과 일정 생성에는 LLM을 사용하지 않는다. 공공데이터, 규칙/점수 기반 추천, 시간 제약 일정 알고리즘을 사용한다. LLM은 장래에 자연어 설명 같은 부가 기능으로만 검토할 수 있다.
- 일정은 출발/복귀의 절대 시각, 지역 간 평균 이동시간, 관광지 간 예상 이동시간, 운영시간·휴무, 예상 체류시간, 식사(점심·저녁 블록과 대표음식 음식점), 축제/행사 시간을 고려해야 한다. 복귀 버퍼는 2026-08-31 결정으로 두지 않는다.
- 실시간 교통은 MVP 요구사항이 아니다. 내비게이션 서비스가 아니므로 통계/평균 기반 예상 이동시간이면 충분하다. 평균/추정치임은 사용자에게 표시한다.
- 데이터는 요청마다 외부 API를 직접 호출하기보다 **공공 API → 주기적 수집 → 정규화 → 내부 데이터 레이어 → 서비스** 구조를 선호한다. 낮은 변경 빈도의 데이터는 하루 단위 캐시하고, 외부 장애 때 마지막 정상 데이터를 제공하는 구조가 바람직하다.
- 초기에는 Next.js Route Handler/Server Action/BFF와 필요 시 PostgreSQL로 시작한다. 처음부터 NestJS/Spring 같은 별도 서버를 전제하지 않는다. Redis와 큐는 규모·갱신 복잡도가 생길 때 검토한다.
- 초기 검증은 자차, 주요 도시 출발, 제한된 지역에서 우선 진행하는 방향이다. 다만 PoC의 대중교통 UI는 정식 MVP 범위를 확정한 것은 아니다.

### 아직 확정되지 않은 것

- 카테고리 기본 체류시간의 숫자와 출처 등급 집합 — 조사 산출물 필요
- 장소 간 이동시간 산출 방식과 보정 계수 — `제안`
- 계산 기준 시간대 — `제안`

2026-08-31에 확정된 것: 최소 현지 체류시간(여행 유형별 형태 + 당일치기 4시간 / 1박 2일 8시간), 운영시간·휴무 결측 제외와 체류시간 fallback의 형태, 복귀 버퍼 미도입, 점수 가중치·동점 규칙 두 층, 식사 시간대·최소 길이와 대표음식 기반 음식점 배치.
- 일정 재생성/개별 장소 교체의 MVP 포함 범위 — `보류`
- 초기 지원 지역, 출발지 입력 단위, MVP 공개 방식

디자인 방향은 H로 확정됐다(`docs/design/DESIGN_DIRECTION.md`). 결정 상태와 근거는 `DECISIONS.md`가 최신 기록이며, 승인 대기 항목의 선택지는 그 문서 2절에 있다. 새 범위 판단은 그 문서에 먼저 기록한다.

## 4. 공공데이터 조사 요약

### 관광지와 축제: 한국관광공사 TourAPI

TourAPI는 전국 관광지, 위치/좌표, 지역·위치·키워드 검색, 상세정보, 이미지, 운영시간/휴무 관련 정보, 숙박, 음식점, 행사/축제, 관광 카테고리의 중심 후보 소스다. PoC와 핵심 서비스는 공공데이터 중심으로 구현 가능하다는 것이 조사 결론이다.

축제는 여행 기간과 지역이 겹치는 행사만 찾고, 관광 목적이며 관심사와 성격이 맞을 때 추천 점수를 올리거나 일정 후보로 제안한다. 축제가 있다는 이유만으로 반드시 일정에 넣지 않는다.

다만 운영시간·휴무 커버리지와 형식은 실제 응답으로 확인해야 한다. 저장소의 `check:tour-api` 프로브는 경주·공주·강릉의 관광지·문화시설과 이후 축제를 조회하고, 주소·좌표·운영정보 필드 충족 여부를 출력한다. 실제 서비스 전환 전 이 결과와 데이터 정규화 비용을 판단한다.

### 이동시간

한국도로공사의 도시간 소요시간, 톨게이트 간 과거 평균 통행시간·거리 데이터는 장거리 목적지의 가능 여부 판단에 사용할 수 있다. 관광지 간의 정확한 도로 이동시간 공공데이터가 부족할 수 있으므로, 초기에는 좌표 거리와 거리 구간별 평균/보정 모델로 예상한다. 정확도 요구가 높아지면 Routing API 도입을 검토한다.

### 체류시간

전국 POI별 일관된 평균 체류시간 API는 부족하다. 다음 우선순위를 고려한다.

1. 실제 평균/통계 데이터
2. 공식 권장 관람시간
3. 카테고리별 기본값 fallback

`stayDurationSource`처럼 체류시간의 출처 수준을 구분해 결과에 표시하는 방안을 고려한다.

### 음식점과 지역 대표음식

맛집 평점·랭킹은 핵심에서 제외한다. 2026-08-31 결정으로 **음식점은 일정에 포함**하며 선정 기준은 지역 대표음식을 파는지 하나다(동선 최적화 선정은 P1). 여행 동선 근처의 음식점 또는 지역 대표음식을 경험할 수 있는 음식점을 제안한다. 예시는 강릉의 초당순두부·장칼국수·물회, 춘천의 닭갈비·막국수, 전주의 비빔밥·콩나물국밥이다.

전국 단일 규격의 대표음식 API는 확인하지 못했지만, 지자체별 대표/향토음식 공공데이터는 존재한다. 수동 데이터 관리가 기본 전략은 아니다. 여러 지자체 API를 하루 한 번 수집하고 정규화해 내부 DB/캐시에서 제공하며, 정말 없는 지역만 수동 보완한다. 일 단위 수집은 API 하나당 월 최대 약 31회라 호출량 부담은 작다고 판단했다.

### 주차장

전국주차장 표준데이터를 활용할 수 있지만 초기 우선순위는 낮다.

## 5. 경쟁 환경과 포지셔닝

| 서비스 | 알려진 성격 | DURUDURU에 주는 시사점 |
| --- | --- | --- |
| 대한민국 구석구석 AI콕콕 | 사용자가 지역을 먼저 정하고 기간/테마 기반 코스를 추천 | 가장 가까운 비교 대상. DURUDURU는 목적지 미정 상태에서 가용시간으로 후보부터 제시해야 한다. |
| 대한민국 구석구석 배지랜드 | 실제 방문 미션, 배지/도감, 점수·랭킹·공유 | 게임화 기능은 존재하지만 현재 MVP 범위가 아니다. |
| 스탬프투어 | GPS/QR 방문 인증, 스탬프, 포인트/등급, 랭킹, 친구 경쟁 | 장기 기록 루프의 참조 사례이며, 핵심 차별점이 되지 않는다. |
| 트리플 | 일정 생성, 동선 고려, 동행자 공동 일정 등 종합 여행 기능 | 목적지 선정 이후의 기능 경쟁보다, 목적지 선택 이전의 문제를 우선 검증해야 한다. |

결론: 개별 기능은 이미 널리 존재한다. 차별화의 우선순위는 시간 제약을 이해해 목적지부터 추천하는 경험이다.

## 6. 장기 제품 방향 — 현 구현 범위 아님

명시적 승인 전에는 구현 범위에 넣지 않는다.

- 실제 방문 → 스탬프/발도장 → 지역·테마 컬렉션 → 친구 공유/비교 → 랭킹·미션
- 예시 컬렉션: 조선 왕궁 정복 4/5, 백제 유적 정복 7/12, 전국 국립공원 9/23
- 방문 기록을 다음 추천과 연결: “백제 유적 컬렉션이 2곳 남았습니다. 이번 주말 1박 2일이면 부여에서 모두 완료할 수 있어요.”
- 장기 루프: 시간이 생김 → 목적지 추천 → 일정 생성 → 실제 방문 → 기록/컬렉션 → 다음 여행 추천
- 장래 입력 조건 후보: 아이와 함께, 부모님과 함께, 많이 걷기 싫음, 비 오는 날, 반려견 동반, 예산 제한

장기 도메인으로는 `User`, `Trip`, `Place`, `Visit`, `Stamp`, `Collection`, `Friendship`을 예상한다. 여행 저장·사용자·방문 기록이 실제 범위가 되면 DB와 백엔드가 필요하다.

## 7. 사용자 기술 배경과 설계 선호

사용자는 9년차 웹 개발자이며 프론트엔드가 주력이다. Next.js/React/TypeScript 중심, App Router와 Server Components를 적극 활용하고, TanStack Query·Axios·Zustand 및 vanilla-extract에 익숙하다. SSR·SEO·성능을 중시하며 Docker, Nginx, GitHub Actions, AWS EC2 경험이 있다.

따라서 익숙한 Next.js 중심 기술을 최대한 사용하고, 필요한 백엔드·DB 기술만 단계적으로 추가하는 방향을 선호한다. 기술 선택은 제품의 데이터 신뢰성·운영 복잡도·검증 속도를 우선해 제안한다.
