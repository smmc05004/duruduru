## 목적과 범위

목적지를 정하지 않은 사용자가 시간 안에 갈 수 있으면서 선택한 관심사를 즐길 근거가 있는 지역을 발견하게 한다. 단순히 가깝거나 세부 장소 수가 많은 지역이 유리한 현상을 개선한다.

- 입력 → 최대 3개 여행지 → 지역 선택 → 계획 흐름을 유지한다. 필수 질문·권역 선택·거리 성향 입력을 추가하지 않는다.
- 지원 지역 전체를 사전 관광 데이터로 비교한다. 검색 시 시간·방향으로 6개 지역만 골라 외부 조회하는 방식은 채택하지 않는다.
- 관광지 목록·공식 분류·중심 관광지 근거는 사전 수집한다. 음식점은 지역 선택 뒤, 방문 상세는 기존 선택 계획 보강·클릭 계약대로 조회한다.
- 기존 KTDB 일반 예상시간, 표준 출발 지역, 출발 권역 제외, 1박 2일, 현지 직선거리 이동 및 편집/저장 정책을 유지한다. 거리 하한이나 먼 지역 가점은 추가하지 않는다.
- 구현 범위는 D1 새 분류 대응, D2 중심 관광지 사전 수집, D3 장소 연결, D4 추천·방문 선정이다. 무료 공공 API와 기존 키를 사용한다. 별도 DB·유료 API·전국 상세 수집·스케줄 운영 인프라는 필수가 아니다.

## 확인한 사실과 한계

2026-09-10 실제 TourAPI 키워드 4회·지역별 구/신 분류 비교 6회가 모두 성공했다. 공산성(125949), 불국사(126166), 첨성대(126207), 미륵사지(127977)는 cat1/2/3가 비어 있고 lclsSystm1=HS 및 하위 코드·법정동·좌표가 존재했다. cat2=A0201 조회에서는 누락되고 lclsSystm1=HS 조회에서는 반환됐다.

구/신 체계 전체가 1:1이라는 뜻은 아니다. 모든 건수 차이를 누락 수라고 단정하지 않는다. 과거 원시 응답은 없어 당시 원천 상태까지 단정하지 않는다. 현재 수집/검색 코드는 새 필드를 처리하지 않는다.

중심 관광지 표본은 총 12회 정상 응답했고 202608의 공주·익산·경주·과천·광명·파주 자료를 확인했다. 전국 완전성·부하·모든 관심사의 분류 대응·자동 연결률·개선된 추천 순위는 아직 검증하지 않았다. 표본 성공을 전체 구현 완료로 취급하지 않는다.

## D1 — 공식 분류와 관광지 기본 자료

새 lclsSystm1/2/3를 우선한다. 분류 코드 목록의 공식 명칭·계층을 확인해 자연·역사·휴양·문화·레저로 연결한 버전별 표를 관리한다. 역사 HS는 실제 확인됐다. 나머지 코드 문자열은 추측하지 않고 D1에서 공식 목록으로 확정한다. 새로운 분류가 해석되지 않으면 임의로 기존 코드로 덮지 않고 검토 대상으로 분리한다. 새 분류가 없을 때만 기존 cat 또는 기존 콘텐츠유형 기반 규칙을 하위 호환으로 사용한다.

역사 박물관을 이름에 역사 단어가 있다는 이유만으로 역사로 재분류하지 않는다. 현재의 문화 판정을 유지한다. 공식 세부 분류 근거로 추가 교차 관심사를 도입할 필요가 있으면 변경 표와 영향을 이 문서에 먼저 반영한다. 작업자는 새 관심사나 의미가 다른 분류를 임의 추가하지 않는다.

분류별 전국 목록을 페이지 끝까지 받은 후 법정동으로 검증된 KTDB 매핑에 배정한다. 같은 contentId는 장소 하나로 관리하고 분류 근거는 보존한다. 새 필드·구 필드·유형·주소·좌표·원천 수정일·수집일·이미지 이용조건을 보존한다. 이미지가 있다고 사용권한을 추정하지 않는다. 새 분류를 저장만 하고 검색에서 옛 cat만 읽는 부분 수정은 완료가 아니다.

유효 분류 없는 장소와 미매핑 지역은 사유별 제외/검토 집계에 남긴다. 좌표 결측은 기존 미확정 이동 정책을 유지한다. 모든 지역·명소를 지원한다고 표현하지 않는다. 공산성·불국사·첨성대·미륵사지의 올바른 ID·지역·역사 판정을 회귀 표본으로 사용한다.

### D1-b — 관심사 ↔ 분류 코드 버전별 표

해석기 SSOT는 `lib/interest-classification.ts`의 `INTEREST_CLASSIFICATION_RULES`다. 수집·검색·후보/저장 변환이 이 표만 사용한다.

| 관심사       | 새 분류(우선, `lclsSystm*`)                                                                    | 콘텐츠유형(두 경로 공통) | 구 분류(새 분류 없을 때만) | 상태                          |
| ------------ | ---------------------------------------------------------------------------------------------- | ------------------------ | -------------------------- | ----------------------------- |
| 자연 nature  | `lclsSystm1 = NA`                                                                              | —                        | `cat1 = A01`               | 활성                          |
| 역사 history | `lclsSystm1 = HS`                                                                              | —                        | `cat2 = A0201`             | 활성                          |
| 문화 culture | `lclsSystm2 ∈ {VE06 공연시설, VE07 전시시설, VE09 교육시설}` 또는 `lclsSystm3 = VE120100 서점` | `contentTypeId = 14`     | `cat2 = A0206`             | 활성(의미 보존 범위)          |
| 레저 leisure | `lclsSystm1 = LS`                                                                              | `contentTypeId = 28`     | `cat1 = A03`               | 활성                          |
| 휴양 rest    | `lclsSystm2 ∈ {EX05 웰니스관광, NA04 자연공원, VE03 도시공원}`                                 | —                        | `cat2 = A0202`             | 활성(의미 근접 범위, PM 결정) |

우선순위 규칙:

1. 레코드에 `lclsSystm1/2/3`가 하나라도 있으면 **새 분류 + 콘텐츠유형**만으로 판정하고 구 `cat`은 보지 않는다.
2. `lclsSystm*`가 전혀 없을 때만 구 `cat` + 콘텐츠유형으로 하위 호환 판정한다.
3. `contentTypeId` 14(문화시설)·28(레포츠)는 안정 신호이나, **공식 L1이 관심사 밖 버킷(`AC 숙박`·`SH 쇼핑`·`FD 음식`·`EV 축제`·`C01 추천코스`)이면 이 신호를 무시한다**(공식 분류가 신호를 이긴다). T2 실측에서 `contentTypeId=28` 조회가 데려온 `AC` 레코드 약 1,980건이 이 규칙으로 레저에서 제외됐다. 공식 L1이 없는 하위 호환 레코드에서는 신호를 그대로 쓴다. 유입량은 수집 보고에 분리 집계한다.
4. 휴양의 `NA04`는 자연(`NA`)과도 겹친다. 자연공원·자연휴양림은 자연과 휴양 두 관심사의 근거가 될 수 있으며, 방문 수는 하나로 관리한다.
5. 레코드의 `lclsSystm*` 값이 위 D1-a 목록(정확히는 `data/tourapi-lcls-systm-codes.json` 전체 코드 집합)에 **없으면** 임의로 기존 코드로 덮지 않고 `unresolvedLcls`로 분리해 집계한다. 목록에는 있으나 5개 관심사에 매핑되지 않는 코드(예: `AC`, `SH`)는 정상 제외이며 미해석이 아니다.

### D1-c — PM 확인이 필요한 의미 변경

- **휴양(rest): 결정 반영, 구현 진행.** 구 `A0202 휴양관광지`는 자연휴양림·온천/스파·찜질방·테마공원·도시공원·리조트를 한데 묶었다. 새 체계에서 이 항목들은 `NA040600 자연휴양림`, `EX05 웰니스관광`, `VE02 테마공원`, `VE03 도시공원`, `VE05 복합관광시설`로 흩어져 대응 L1이 없다. **2026-09-10 PM 결정: 위 (b)안** — `EX05 웰니스관광` + `NA04 자연공원`(국립·도립·군립·지질공원, 생태관광지, `NA040600` 자연휴양림, 수목원·정원 포함) + `VE03 도시공원`으로 활성화한다. 놀이공원·리조트에 해당하는 `VE02 테마파크`·`VE05 복합관광시설`은 휴양에서 제외한다(휴양의 성격이 아님). 구 `cat2=A0202`는 새 분류가 없는 레코드에만 fallback으로 쓴다. 이 매핑으로 휴양은 전국 다수 지역에서 후보를 확보한다(T2 재수집으로 검증).
- **문화(culture): 범위 축소 매핑으로 활성화.** 새 `VE 문화관광`은 구 `A0206 문화시설`보다 넓어 랜드마크(`VE01`)·테마공원(`VE02`)·도시공원(`VE03`)·교통시설(`VE11`)까지 포함한다. 기획서 "현재의 문화 판정을 유지한다"에 맞춰 공연·전시·교육 시설과 서점(`VE06/VE07/VE09/VE120100`)만 문화로 본다. `contentTypeId = 14`가 이 의미를 이미 anchor 하므로 활성화했으나, VE 하위 코드 경계(예: 과학관 `VE070500`, 카지노 `VE120200` 제외 여부)는 PM이 검토 가능하다.
- 자연·역사·레저는 공식 L1 명칭이 1:1(자연관광/역사관광/레저스포츠)이라 의미 변경 없이 활성화했다.

| 7    | 정상 데이터 묶음 저장·배포                        | 관광 API 없음                                  |

기존 키는 TOUR_API_SERVICE_KEY, 새 키는 CENTRAL_ATTRACTION_API_SERVICE_KEY다. 인코딩된 키도 최종 요청에서 한 번만 인코딩한다. 키·키 포함 URL은 로그/JSON/브라우저에 남기지 않는다.

중심 관광지는 명시한 baseYm으로 받는다. 첫 구현의 검증된 기준월은 202608이며 ‘최신 월 자동 확인 완료’라고 쓰지 않는다. 월별 갱신 시 같은 기준월·지역 성공분은 재사용한다. 지역별로 과거 월을 자동 탐색해 혼합하지 않는다. areaCd는 lDongRegnCd, signguCd는 지역 코드와 하위 코드를 결합한 5자리이며 공식 응답으로 대조한다. 광역시 그룹 하나가 API 1회라는 가정은 금지한다.

상위 100위까지 요청하며 totalCount·실제 개수·중복 ID·페이지 종료를 검증한다. 현재 249개 매핑이 지역당 한 페이지면 약 249회지만 재시도·코드 조회는 별도이며 계정 잔여 한도를 확인한다. 호출 정책은 동시성 1, 요청 시작 간 최소 1초, 요청 제한 20초, 실행별 기본 예산 400회(중심 관광지), 기존 관광 프로필 예산 900회 이내다. 공식 초당 허용량을 확인해 더 낮은 값이 있으면 그 값으로 제한한다. 두 API의 예산은 각각 설정하며 일일 실사용·다른 실행의 소비량을 제외한 잔여 한도보다 작게 적용한다.

실패도 예산에 포함한다. 인증/권한 오류·일일 한도 초과는 즉시 중단한다. 초당 제한·일시적 연결/5xx는 대기 후 최대 2회 재시도하고 재시도도 예산에 센다. HTTP 200의 원천 오류·XML 오류를 성공으로 처리하지 않는다. 오류 로그는 HTTP 상태·원천 코드·지역·페이지만 남긴다.

같은 작업의 동시 실행을 막고 완료 체크포인트를 보존한다. 재개 시 기준월·분류 버전·매핑 버전이 같을 때만 성공분을 재사용한다. 관광 프로필은 갱신 실행 ID 안에서 페이지 재개하며 다른 실행의 일부 페이지와 합치지 않는다. 최신 목록은 스냅샷 격리가 보장되지 않으므로 건수 변동·누락 징후를 검출하면 해당 수집을 다시 검토한다.

정상 0건과 실패를 구분한다. 실패 지역이 남은 수집을 완전한 전국 갱신으로 게시하지 않는다. 기존 정상 묶음을 유지하며 임시 파일→검증→정상 묶음 교체 순서로 배포한다. 프로필·중심 원본·연결 인덱스의 버전이 맞지 않으면 섞지 않는다. 최초 중심 자료가 미준비이면 새 프로필의 기존 분류 기반 추천은 가능하되 중심 근거를 꾸미지 않는다.

JSON은 로컬 수집 후 검토·커밋·배포로 제공한다. 배포 서버 시작·빌드·검색에서 자동 수집하지 않으며 Vercel 로컬 파일 쓰기나 메모리를 영속 갱신 장치로 사용하지 않는다. 관광 프로필 하루 1회, 중심 자료 새 기준월 갱신은 운영 목표이며 예약 자동화 완료를 뜻하지 않는다.

## D3 — 보수적인 장소 연결

hubTatsCd와 TourAPI contentId는 다른 ID다. 실제 행정지역이 같은 후보 안에서 정규화 이름과 좌표를 함께 확인한다. 지역 그룹이 같다는 이유만으로 다른 구의 동명 장소를 연결하지 않는다.

- 자동 확정은 지역명 접두어·명시적 유네스코 표기·공백/문장부호만 정리한 이름이 동일하고 좌표가 500m 이내이며 유일한 후보일 때다. 500m는 이번 제품 휴리스틱이지 공식 동일 장소 보증이 아니다.
- 일반 괄호 내용을 무조건 삭제하지 않는다. 천마총(대릉원)과 대릉원 같은 본체/부분 차이를 보존한다. 부분 이름 포함이나 가까운 좌표만으로 확정하지 않는다.
- 후보가 여러 개면 정확한 원문 이름과 좌표 근거로 유일성을 확인할 수 있는 경우 외에는 ambiguous로 남긴다. 좌표 결측은 자동 확정하지 않는다.
- 별칭 수동 연결은 실제 확인한 명칭·주소·공식 자료와 확인일·두 원천 ID를 기록한다. 모델 추측으로 전국 별칭을 만들지 않는다.
- 공산성→공산성연지, 동학사→동학사계곡 연결은 금지 회귀 사례다. 미연결 명소는 지역 원천 근거로 보존할 수 있지만 일정 가점·직접 배치에 쓰지 않는다.
- 동일 contentId 또는 확인된 동일 시설에 여러 중심 항목이 연결되면 가장 높은 순위 하나만 인정한다. 시설 의심만 있는 항목은 기존 E2 약한 중복 정책을 적용한다.

연결 결과는 matched/unmatched/ambiguous/rejected와 사유·방법·거리·원천 버전으로 보존한다. 쇼핑·숙박·교통시설을 중심 목록에 있다는 이유로 관광 일정에 넣지 않는다. 장소의 관심사 판정은 D1의 TourAPI 분류를 기준으로 한다.

## D4 — 추천과 실제 방문 장소에 반영

시간·지역·최소 관광 후보 조건이 먼저다. 기존 공통 엔진으로 식사·휴식·직선거리 이동·귀가를 만족하는 초안만 평가한다. 선택 관심사 충족 수가 우선이며 원천 관광지 총개수로 점수를 부풀리지 않는다.

목적지 간 비교의 핵심은 **실제 초안의 관심사 충족, 서로 다른 시설의 방문 깊이, 요청 관심사 안의 세부 유형 다양성**이다. 원천 목록의 총개수나 지역 내 `hubRank`의 역로그 합으로 목적지의 전국 우열을 정하지 않는다. 기존 `1/log2(1+hubRank)` 기반 목적 점수는 새 검색 정렬에서 제거한다.

- 요청 관심사별로 실제 배치된 서로 다른 시설 수와 세부 유형 수를 계산한다. 시설 중복은 기존 E2 정책, 분류는 D1의 새 공식 분류 우선순위를 따른다. 분류 결측을 독립 유형으로 세지 않는다.
- 방문 수·다양성의 기여에는 포화 상한을 둔다. 요청하지 않은 관심사나 장소를 무작정 늘려 점수를 높이지 않는다. 여러 관심사에 속하는 시설은 해당 관심사별 충족에 기여할 수 있지만 전체 시설 수에서는 한 번만 센다.
- 목적 적합성은 일정 지표로 만든 고정 등급/점수 구간으로 비교한다. 후보 두 개의 점수 차이만으로 매번 동점을 판정하는 비추이적 비교자는 금지한다. 같은 구간에서는 미세한 원점수 차이보다 왕복 일반 예상시간을 우선한다.
- 상한·가중치·구간 경계는 공식 데이터가 주는 수치가 아닌 제품 휴리스틱이다. T7에서 기존 48개 사례로 제한 비교하고 이 절에 정확한 수식·경계·선택 근거를 기록한 뒤 구현 상수로 고정한다. 특정 도시를 올리거나 왕복시간 중앙값을 낮추기 위한 반복 튜닝은 하지 않는다.

중심 관광지 연결은 **보조 근거**다. 실제 배치된 관심사 시설 중 확정 연결된 시설의 존재/중복 제거 개수만 제한적으로 사용하며, 목적 적합성 구간이나 더 긴 이동의 우선권을 단독으로 만들지 않는다. 동일 적합성 구간·왕복시간까지 같은 후보의 보조 동점 기준으로만 사용한다. 하위 구 개수로 나누는 방식도 채택하지 않는다. 동일한 일정·시간·분류·연결 근거라면 행정구역 분할 개수나 각 구의 순위 숫자만 달라져도 목적지 순위가 바뀌지 않아야 한다.

관광 선정은 하드 시간 제약·확인된 시설 중복 회피 → 미충족 관심사 → 기존 의심 시설 감점 → 세부 유형 다양성·기존 근접성 → 해당 관심사 중심 근거 → 안정 ID 순으로 후보를 검토한다. 중심 근거가 다양한 실제 일정보다 앞서 사찰 등 같은 유형만 반복 선택하게 하지 않는다. `hubRank`는 동일 원천 지역 안에서 조건이 비슷한 장소의 보조 선택에만 활용하며, 다른 구의 숫자를 전국 공통 척도로 비교하지 않는다. 가점 장소가 불가하면 다음 후보를 검토하고 귀가/고정 활동을 침범하지 않는다. 사용자 편집·저장 복원에서 신규 순위로 기존 선택을 몰래 바꾸지 않는다.

역할 선택과 표시 순서는 interest → easy → relaxed를 유지한다. interest는 **충족 관심사 수 내림 → 목적 적합성 구간 내림 → 왕복시간 오름 → 상한 적용 중심 연결 시설 수 내림 → groupId 오름**으로 선택한다. 같은 구간 안에서 원점수·관광 수를 다시 왕복시간 앞에 넣지 않는다. 더 높은 적합성 구간이면 먼 지역도 선정될 수 있다. easy는 앞서 선택한 그룹을 제외하고 기존 이동 부담 정렬, relaxed도 선택 그룹을 제외하고 기존 여유 정렬을 유지한다.

중심 데이터가 없어도 실제 일정의 충족·시설·다양성 평가는 정상 계산한다. 중심 보조 근거만 없음으로 남기며 지역 매력 0으로 표현하지 않는다. 지역별 순위 합산, 하위 구 순위 1위 누적, 점수를 현지 자유시간으로 나누는 계산, 관광 수를 일부러 줄여 여유 역할을 얻는 조작은 하지 않는다. 추가 이동시간 입력·거리 하한/상한·먼 지역 가점은 도입하지 않는다.

카드는 실제 초안의 대표 장소와 추천 이유를 간결히 보여준다. 원천명·기준월·연결 상태·세부 점수는 근거 펼치기에 둔다. ‘전국 역사 1위’, ‘가장 인기’, ‘영업 보장’은 표시하지 않는다. 중심 근거가 없는 카드에 중심 관광지 문구를 붙이지 않는다.

### D4-a — 확정 상수 (T7-1, 2026-09-10)

기존 48개 비교 입력(출발지 4 × 관심사 6세트 × 시간 2)으로 상한·구간 경계 후보(`[capF,capT] ∈ {[4,3],[3,3],[4,2],[5,3]}`, 경계 `∈ {[4,6],[4.5,6],[4.5,6.5],[5,6.5]}`)를 제한 비교하고 아래 값을 골랐다. 특정 도시 상위 노출이나 왕복시간 중앙값을 목표로 튜닝하지 않았다. 구현 상수는 `lib/tourism-evidence.ts`의 `PURPOSE_FIT_METRIC`이며 `lib/__tests__/enhancement-t7-comparison.test.ts`가 문서 값과 동기화를 검증한다.

**목적 적합성 지표(요청 관심사 `i`마다):**

- `facilities_i` = 실제 초안에 배치된, `i`에 해당하는 서로 다른 시설 수(E2 시설 그룹으로 중복 제거).
- `types_i` = 그 시설들의 서로 다른 세부 유형 수. **하나의 시설 그룹(E2 시설 그룹)은 이 관심사의 세부 유형에 최대 하나만 기여한다** — 그룹 내 유효 분류가 있는 장소 중 안정적인 콘텐츠 ID 순서(오름차순)로 대표 하나를 고르고, 세부 유형 = 그 대표의 `lclsSystm3 → lclsSystm2 → cat3 → cat2` 중 처음 있는 값이다. 넷 다 없으면(그룹 내 유효 분류가 없으면) 유형으로 세지 않는다(관심사 조합 문자열 fallback 금지). 그룹은 시설 수에는 포함되지만 유형 수에는 기여하지 않는다. 그룹별 대표 유형을 다시 중복 제거해 `types_i`를 만든다 — 같은 시설에 세부 항목(예: 서로 다른 소분류 코드를 가진 하위 장소)을 추가하는 것만으로 `types_i`·`fit_i`·구간이 오르지 않게 하는 결함 수정(2026-09-11)이다.
- `fit_i = min(facilities_i, 4) + min(types_i, 3)` — **facilityCap 4, typeCap 3** 포화 상한.
- `avgFit = (Σ_i fit_i) / 요청 관심사 수`.
- `fitBand = [4.5, 6.5].filter((b) => avgFit >= b).length` → **0(보통) · 1(충실) · 2(매우 충실)** 3개 고정 구간.

**보조(중심 연결) 근거:** `matchedFacilityCount = min(확정 연결된 초안 배치 관심사 시설의 서로 다른 시설 그룹 수, 4)` — **matchedFacilityCap 4**. 하위 구 개수·구별 순위 숫자에 불변이다.

**관광 선정(`selectPlaces`) 순서:** 하드 시간 제약·시설 그룹 중복 회피 → 미충족 관심사 → 세부 유형 다양성(당일) → 이전 장소 근접성 → **해당 관심사 중심 근거(확정 연결 여부 불리언)** → 안정 ID. 중심 근거는 `hubRank` 숫자 크기를 쓰지 않고 "확정 연결 여부"만 본다 — 다른 구의 순위를 전국 공통 척도로 비교하지 않고 총순서(추이성)를 유지하기 위해서다. 이 재정렬로 사찰 등 같은 세부 유형을 반복 선택하던 T6 현상이 사라졌다.

**`interest` 정렬 키(전부 스칼라 `compareNumber`/`compareText`의 사전식 결합 = 총순서):** `충족 관심사 수 ↓ → fitBand ↓ → 왕복시간(분) ↑ → matchedFacilityCount ↓ → groupId ↑`. 원점수(`score`)·관광 수·세부 분류 다양성은 이 정렬에 넣지 않는다(참고 필드로만 보존).

**선택 근거 요약:** `[4.5, 6.5]`는 하루 6곳·유형 3+의 충실한 근거리 일정과 원거리 대도시 일정을 같은 구간(2)에 두어 왕복시간이 승부를 내게 한다. `[4, 6]`은 단일 관심사 최소 `fit`(≈4)이 이미 band1이라 구간 변별력이 사실상 사라진다. `[5, 6.5]`는 야간·저다양성 근거리 후보를 자주 band0로 떨어뜨려 원거리 선택이 늘었다. 48개 재실행 결과 `interest` 왕복시간 min/중앙/max = 18 / 48 / 80분, 편도 2h+ 셀 0개(T6는 62→358, 34/48). 이는 목표가 아니라 (a) 세부 유형 다양성을 중심 근거보다 앞세운 관광 선정 재정렬과 (b) 포화 상한이 함께 만든 결과다. 강릉→삼척(문화), 강릉→속초(역사+문화 야간)처럼 **근거리에 더 낮은 구간·미충족만 있을 때는 더 먼 후보**가 정상 선택된다.

## 수용 기준

T7 추가 완료 조건: 유사 적합성에서는 짧은 이동이 선택되고, 명확히 높은 일정 적합성에서는 먼 후보도 선택될 수 있어야 한다. 시설 중복·행정구역 분할·지역 내 순위 변경만으로 지역 비교 점수가 부풀지 않아야 한다. 중심 결측 지역도 기본 적합성을 평가한다. 48개 사례에서 실제 장소·시설 수·다양성·구간·왕복/현지시간·선정 이유를 비교하며, 낮은 왕복 중앙값이나 특정 도시 상위 노출을 통과 조건으로 삼지 않는다. 기존 T6 판정은 T7 완료를 뜻하지 않는다.

1. 네 대표 명소를 새 분류로 수집·역사 판정하고 기존 필드 결측 때문에 제외하지 않는다. 전체 5개 관심사 매핑은 공식 코드에 연결된다.
2. 원천 HTTP 성공만으로 수집 완료 처리하지 않는다. 총량·페이지·부분 실패·예산·중복·잘못된 월/지역·재개/정상본 보존을 검증한다.
3. 잘못된 본체/부분 연결을 막고 동일 시설 중심 근거를 중복 가점하지 않는다. 전국 및 표본 지역의 연결률·미연결 원인을 보고한다.
4. 같은 입력/버전은 같은 추천·초안을 생성한다. 점수의 근거 장소는 실제 일정에 있어야 한다.
5. 공주/익산/경주가 무조건 나오게 이름/지역 가점을 넣지 않는다. 서울·부산 등 출발/기간/관심사 비교 결과와 개선되지 않은 경우를 보고한다.
6. 검색의 관광 목록·중심 관광지·음식점·상세 외부 호출은 0회다. 선택 이후의 기존 음식점·상세 요청 상한과 저장본 보존이 유지된다.

신규 가중치의 전국 품질·연결률은 구현 후 검증 대상이다. 검증이 좋지 않으면 임의 튜닝을 반복하지 말고 원인과 제품 규칙 변경안을 보고한다.
