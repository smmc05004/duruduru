# 초기 3지역 대표음식·음식점 후보 제안

> 상태: **PM 검토 및 사용자 승인 대기** (2026-09-03)
>
> 이 문서는 대표음식 값을 확정하거나 E6 데이터에 주입하지 않는다. 실제 수집 응답으로 후보와 근거를 남겨 PM이 제안하고 사용자가 승인할 수 있게 하는 E2 조사 산출물이다. 결정의 단일 출처는 [DECISIONS.md](DECISIONS.md)이며, 확정 절차는 [FOOD_DATA_NEXT_STEPS.md](FOOD_DATA_NEXT_STEPS.md) 3절을 따른다.

## 1. 목적과 경계

E6의 P0 식사 배치에는 지역 대표음식과 이를 취급하는 음식점의 실제 근거가 필요하다. 이번 작업은 경주·공주·강릉의 TourAPI·모범음식점 원문을 새로 조회하고, 지역N문화는 아직 재검증하지 않은 2026-08-31 E2 실측 기록을 참조해 승인 검토용 후보를 만든다.

1. 한국문화원연합회 지역N문화 「향토음식과 지역이야기」 — 대표음식 시드 (`LOCAL_SPECIALTY`)
2. 한국관광공사 TourAPI KorService2 음식점 검색·상세 응답 — 메뉴·좌표·운영/휴무 원문 (`RESTAURANT_MENU`)
3. 지방행정 인허가 데이터개방 모범음식점 표준 CSV — 지정 업소의 주된음식종류 교차 확인

다음은 이번 문서의 범위 밖이다.

- 대표음식 확정, `RepresentativeFood`/`RestaurantRecord` 생성, 음식점 순위화
- 운영시간 자유 서식 파싱 및 특정 여행일·식사 시간대의 실제 영업 가능 판정
- 장소 간 이동, E6 일정 엔진, 평점·리뷰·상용 지도 스크래핑

따라서 아래의 “후보”는 **대표음식 또는 배치 가능 음식점이라는 제품상의 확정값이 아니다.** TourAPI 검색 결과가 있는 것은 해당 키워드로 검색된 공개 음식점 레코드가 있다는 뜻이며, 식사 시간대에 열려 있다는 뜻은 아니다.

## 5. 운영 원문 보유 표본의 판정 상태

이번 실제 응답에서 모든 표본에는 TourAPI 좌표와 운영시간·휴무 원문이 있었고, 모범음식점 교차 행은 `영업` 상태인 행만 별도로 적었다. 그러나 이것만으로는 “운영 가능한 음식점”이 아니다.

- TourAPI의 운영시간에는 요일, 준비시간, 마지막 주문, 조기마감, HTML 줄바꿈이 섞여 있다.
- 모범음식점의 `영업`은 해당 지정 데이터의 상태이며, TourAPI 음식점 ID와의 동일 업소 매칭을 뜻하지 않는다.
- 선택 여행일의 휴무·예외 운영과 점심(11:30~~13:30)·저녁(17:30~~19:30) 1시간 충족 여부를 아직 계산하지 않았다.

따라서 E6 입력 레코드로 승격할 수 있는 상태는 아직 **없음**이다. 다음 수집/정규화 작업에서 메뉴 별칭의 근거 있는 매칭, 업소 ID/좌표 동등성 검증, 운영시간 파싱 성공, 특정 날짜 휴무 검증을 모두 통과한 경우에만 `RestaurantRecord`의 배치 후보로 기록한다. 실패·결측은 [FUNCTIONAL_SPEC.md](FUNCTIONAL_SPEC.md) F-04/F-07의 확정 규칙대로 후보에서 제외하며, 데이터 부재를 “후보 0곳”으로 바꾸지 않는다.

## 6. PM·사용자 승인 요청

PM은 아래를 사용자에게 제안할 승인안으로 작성하기 전에 각 항목의 원문 표기, 별칭, 소스 유형, 신뢰도를 검토한다. PM은 최종 승인자가 아니다.

1. 경주: 지역N문화 시드(두부삼합·김치 사연지)를 대표음식 데이터로 남기되 음식점 배치 근거에서 제외할지, 또는 쌈밥을 `RESTAURANT_MENU` 후보로 사용자에게 함께 제안할지
2. 공주: 칼국수는 ①·③과 키워드 표본만 있는 상태로 제안하고, 공주 밤묵은 음식점 연결 불가 상태로 남길지
3. 강릉: 초당두부/감자옹심이/주문진 한치물회를 lift 검증 전 사용자 승인안 후보로 제안할지와, 막국수·장칼국수의 보류 유지 여부
4. `초당두부`/`초당순두부`, `주문진 한치물회`/`물회`의 별칭 연결을 원문 메뉴와 어떤 검증 규칙으로 판정할지

사용자가 승인하기 전에는 어느 항목도 제품의 “대표음식”으로 표시하거나 코드 상수에 넣지 않는다. 승인 뒤에도 이 문서의 원시 표본을 그대로 서비스하지 않고, 소스별 수집 시각·상태·원문 URL을 보존하는 내부 데이터 계약으로 정규화한다.

## 7. 남은 데이터 준비 작업

- 지역N문화 공개 CSV의 정식 다운로드 경로·컬럼·행수와 초기 3지역 레코드를 재현 가능하게 확인한다.
- TourAPI 음식점 전체 페이지를 수집하고, 전체 모집단 기준 메뉴 빈도와 별칭 매칭 근거를 계산한다. 첫 페이지 표본을 빈도나 lift로 해석하지 않는다.
- 운영시간 자유 서식 파서와 파싱 실패=결측 제외 규칙을 테스트로 구현한다.
- TourAPI와 모범음식점 업소의 동일성은 이름만이 아니라 좌표·주소 등 근거를 보존해 검증한다.
- 라우팅 공급자와 키가 결정된 뒤 장소 간 이동시간을 실제/추정 출처와 상태로 수집한다. 이 문서는 그 결정을 기다리지 않고 수행할 수 있는 음식 데이터 조사만 다룬다.
