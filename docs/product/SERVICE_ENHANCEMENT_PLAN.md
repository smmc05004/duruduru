# DURUDURU 서비스 고도화 계획

> 후속 방향: [서비스 2차 고도화 계획](SERVICE_ENHANCEMENT_PHASE_2_PLAN.md)에 장소 간 직선거리 기반 이동시간과 KTDB 출발 지역 검색·선택을 정리했다. 아래 내용은 1차 고도화 범위이며 후속 기능의 구현 완료를 뜻하지 않는다.

> 기준일: 2026-09-08. 사용자가 MVP 종료 및 아래 1~4번의 단계별 기획·구현·PR·병합을 승인했다. 이 문서는 고도화 방향과 범위의 기준이며, 상세 기능 정책은 [고도화 기획서](SERVICE_ENHANCEMENT_SPEC.md)를 따른다.

## 목표와 유지할 제약

목적지를 먼저 정하지 않아도 사용 가능한 시간으로 여행지를 고르고, 추천받은 계획을 수정해 실제 여행 준비에 활용할 수 있게 한다. 기능 개수보다 추천의 선택 가치, 일정의 현실성, 수정·활용 가능성을 높인다.

- 핵심 추천은 공공데이터와 결정론적 규칙을 사용한다. LLM·유료 API를 도입하지 않는다.
- 기존 KTDB 2024 지역 간 일반 예상시간과 TourAPI 관광지 분류·좌표·소개 정보를 활용한다. 내비게이션이나 실시간 교통 서비스로 바꾸지 않는다.
- 장소 간 좌표 거리는 근접성 판단에만 쓴다. 도로 경로나 장소 간 이동시간으로 환산하지 않는다.
- 서울·부산 출발, 자차, 다음날 귀가하는 1박 2일을 유지한다. 이동 시각은 제한하지 않고 관광만 07:00~21:00에 배치한다.
- 음식점은 목적지 선택 후 필요한 하위 지역만 조회한다. 대표음식·지역N문화·모범음식점 보조 근거를 유지한다.
- 기존 H · 여행 수첩 디자인과 정상 작동하는 교체·저장·상세 기능을 유지한다.
- 정보 결측을 영업 가능·인기·평점으로 바꾸지 않는다. 외부 장애 때문에 이미 만든 전체 여행 계획을 잃게 하지 않는다.

## 승인된 구현 범위: 1~4

### 1. 비교할 가치가 있는 목적지 3안

현재의 동일 정렬 상위 3곳을 이동 부담, 관심사 경험, 여유라는 서로 다른 선택 근거로 개선한다. 추가 필수 입력 없이 기존 조건으로 제안한다. 목적지는 중복하지 않고, 실제 차이가 없으면 억지로 특성을 붙이지 않는다. KTDB 시간·분류·좌표·실제 생성 일정으로 계산하므로 새 외부 원천은 필요하지 않다.

### 2. 관광지 개수보다 하루의 구성 개선

이름·주소·좌표가 함께 뒷받침하는 동일 시설 후보를 보수적으로 묶고, 가까운 장소를 오전·오후에 구성한다. 세부 관광 유형의 반복과 지역 내 왕복을 줄인다. 좌표만으로 독립 관광지를 삭제하지 않는다. 활동 사이 여유시간은 정책상 확보하는 자유시간이며 계산된 이동시간으로 표시하지 않는다. 불확실한 시설 연결은 순위 보조로 사용하고, 보정은 근거가 있는 소규모 목록으로 제한한다.

### 3. 추천 이유와 방문 판단 정보

실제 방문 장소의 짧은 소개, 관심사 연결 근거, 사용 조건을 확인한 이미지, 확인 가능한 휴무 원문, 주소 복사·외부 지도 연결을 제공한다. 전국 상세 조회 대신 선택된 계획의 소수 관광지에 제한 조회를 적용한다. 명확한 휴무 충돌은 교체·변경을 제안하되 자동 삭제하지 않고, 해석 불가·결측·API 실패는 확인 필요로 남긴다. 무료 API가 제공하지 않는 인기·영업 보장은 하지 않는다.

### 4. 자동 계획을 내 계획으로 완성

기존 교체·삭제·체류시간 수정·저장에 날짜/순서 이동, 후보 관광지 추가, 숙소·약속·개인 장소 추가, 방문 시각 고정을 더한다. 기존 사용자 선택을 최대한 보존하고 불가능한 변경은 이유와 함께 되돌린다. 개인 장소는 사용자가 입력한 정보임을 구분하고 좌표가 없으면 공간 선정에서 제외한다. 숙소 추천·예약·주소 자동 변환 API는 도입하지 않는다.

## 후속 제안: 이번 자동 실행 범위 제외

### 5. 음식 선택 품질

끼니별 다른 식당과 주변 관광지 근접성을 유지하면서, 확인된 음식 종류에 한해 메뉴 다양성과 지역 음식 근거를 제공한다. 자유 식사를 선택할 수 있게 한다. 상호만으로 메뉴를 추측하거나 전국 음식점을 정규화하지 않는다.

### 6. 여행 중 활용

하루별 여행 모드, 인쇄/PDF, 계획 파일 내보내기·가져오기, 주소·전화번호 복사를 우선 고려한다. 로그인·서버 저장·기기 간 동기화·공개 공유 링크는 별도 저장소와 정책이 필요하므로 분리한다.

### 7. 운영 기반

지역 프로필 정기 수집→필수 필드·중복·급감 검사→정상본 반영을 자동화하고, 실패 시 마지막 정상본과 관리자 알림을 유지하는 방향을 검토한다. 현재 저장소의 수집 스크립트와 실제 예약 실행은 구분한다. 외부 API 한도와 운영계정 승인, 지속 캐시의 저장 방식은 별도 운영 작업으로 구체화한다. 이번 1~4의 범위에 무단으로 DB·외부 서비스를 추가하지 않는다.

출발지는 기존 시간표에서 매핑·유효값이 확인되는 지역부터 후속 확대할 수 있다. 당일치기·다박·날씨·축제·대중교통은 별도 우선순위 결정 전까지 보류한다.

## 실행과 완료 기준

1. PM이 1~4의 기능 명세와 수용 기준을 작성한다.
2. 주 에이전트가 정책 충돌, 구현 가능성, 외부 의존성, 결측·편집 보존·회귀 위험을 검토한다. 수정이 필요하면 PM에게 돌려보낸다.
3. 기획 검토 뒤 실행 조정·PR 병합 역할은 사용자 요청 모델 `gpt-5.6-terra` 에이전트로 위임한다. 세션 모델 자체가 전환되었다고 표현하지 않는다.
4. Employee가 단계별 작업 계획을 먼저 작성하고 승인된 명세대로 구현한다. 각 단계는 최신 main에서 별도 영문 작업 브랜치로 시작한다.
5. MVP가 종료되었으므로 기존 역할 문서의 Jest·Playwright·독립 리뷰·검증 절차를 적용한다. 검증을 통과시키기 위해 실제 시나리오를 제거하거나 검색부터 결과까지를 전부 가짜 응답으로 대체하지 않는다.
6. 한글 커밋·PR을 작성하고 CI 완료와 병합 가능 상태를 확인한 뒤 병합한다. 실패·충돌은 해결하고 재검증한다. main 직접 push·force push·보호 우회는 하지 않는다.
7. 병합된 단계의 구현 상태·PR·검증 근거와 다음 작업을 작업 계획에 남긴 뒤 다음 단계로 진행한다. 네 번째 단계 병합까지 감독을 지속한다.

현재 단계는 PM 기획 작성·총괄 리뷰 완료이며, 본 문서의 존재가 구현 완료를 뜻하지 않는다. 사용자 승인 없이 5~7이나 지원 기간·출발지를 확대하지 않는다.

### 기획 리뷰 결과 (2026-09-08)

- E1~E4의 입력·계산·예외·완료 조건과 기존 시간/음식/디자인 정책의 연결을 검토하고 순차 구현을 승인했다.
- 약한 시설 추정의 과도한 제외를 감점으로 바꾸고, 모든 공간 선택 분기에서 같은 기준을 적용하도록 정리했다.
- 관광 상세는 항목 순차·내부 2병렬로 전체 동시성 2를 지키고, 최대 12원천 호출·28초·실패 비차단으로 제한했다. 클릭과 자동 보강은 진행 요청을 공유한다.
- v3 저장본 우선 및 이관 완료 표식을 정의해 이전 v2 백업 때문에 삭제한 계획이 부활하지 않도록 했다.
- 읽은 근거는 현재 추천/일정/저장/상세 코드와 제품·역할 문서다. 이 검토는 기획의 구현 가능성 검토이지 새 기능의 테스트 통과나 실제 API 응답 확인이 아니다.
- 구현·검증·독립 리뷰에서 발견한 명세 문제는 기록하고 최소 수정한다. 외부 비용이나 제품 범위 확장이 필요하면 사용자에게 결정받는다.

## 확인 근거

- `lib/mvp-phase-two-search.ts`: 현재 목적지 정렬과 상위 3개 반환.
- `lib/mvp-phase-two-planner.ts`: 동일 콘텐츠·유사 장소 처리, 일정과 편집 엔진.
- `lib/attraction-detail.ts`: 소개·운영정보 정규화와 사진 사용 조건 검사.
- `lib/mvp-phase-two-types.ts`: 서울·부산, 일정·편집·저장 계약.
- `e2e/home.spec.ts`: 현재 검색 응답을 대체하는 세 시나리오만으로 전체 여행 흐름을 검증했다고 볼 수 없음.
- [TourAPI 공식 제공 안내](https://www.data.go.kr/data/15101578/openapi.do): 무료 관광·소개·이미지 정보, 사진별 이용 조건, 개발계정 트래픽 및 운영계정 심의/증설 안내. 실제 프로젝트 키의 승인 상태·남은 호출량과 정보 충족률은 별도 확인 대상이다.
- [GitHub 예약 실행 문제 해결](https://docs.github.com/en/actions/how-tos/troubleshoot-workflows): 정기 실행 지연 가능. 예약 시각에 정확히 갱신된다고 보장하지 않는다.
