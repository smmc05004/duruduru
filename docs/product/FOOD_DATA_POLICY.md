# MVP 음식점 데이터 정책

## 범위

식사는 관심사와 무관하게 여행 범위 안에서 60분을 확보할 수 있는 점심·저녁을 배치한다. 야간 출발 전이나 귀가 후의 식사는 넣지 않으며 네 끼를 강제하지 않는다. 현지 식사에는 음식점을 추천하고 이동과 겹치는 식사는 운전 분과 별도로 계산한 `이동 중 자유 식사`로 둔다. 특정 경유지·식당을 임의 추천하지 않는다. 미식은 관심사·지역 프로필·목적지 추천 필터가 아니다. 지역N문화 향토음식과 모범음식점 지정·음식 종류는 선택 후 식당 선정의 보조 근거다. 시간·호출·교체 수용 기준은 [2단계 기획서](MVP_PHASE_2.md) P2-01/P2-04/P2-05를 따른다.

이 근거는 여행 지역을 후보에서 제외하는 조건이 아니며, 선택 후 음식점 후보를 고르는 근거다. 전국 음식점 정규화 데이터셋은 만들지 않는다. 평점·리뷰·랭킹은 사용하지 않는다.

## 원천별 역할과 최신성

| 원천                                 | 역할                                | 최신성·제약                                                                                                              | 앱에서의 사용                                                                                                              |
| ------------------------------------ | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| 지역N문화 `향토음식과 지역이야기`    | 지역의 향토음식·문화 키워드         | 현재 확보 원본은 2023년 12월 스냅샷이며 비주기 자료다. 관련 음식점 필드는 콘텐츠 지역과 실제 음식점 주소가 다를 수 있다. | 지역 대표음식의 **약한 보조 근거**로만 쓴다. 관련 음식점 이름·주소를 TourAPI 음식점의 직접 추천·매칭 원천으로 쓰지 않는다. |
| 행정안전부 모범음식점정보 조회서비스 | 모범음식점 지정 여부·주된 음식 종류 | 지자체 관리 정보를 통합한 REST API다. 지정·영업 상태는 변할 수 있다.                                                     | 정기 수집해 지역별 인증 캐시를 만들고, TourAPI 목록과 안전하게 일치한 음식점에만 가점을 준다.                              |
| TourAPI 음식점 목록                  | 실제 일정에 배치할 음식점 기본 정보 | 사용자가 목적지를 선택한 시점의 목록 정보다.                                                                             | 선택 권역 안 실제 관광 하위 지역을 제한 조회하고 식당명·주소·콘텐츠 ID를 일정 스냅샷에 보존한다.                           |

모범음식점 API 호출에는 서버 전용 `EXCELLENT_RESTAURANT_API_SERVICE_KEY`를 사용한다. 키는 브라우저·검색 스냅샷·로그에 포함하지 않는다.

## 목적지 선택 후 음식점 수집

목적지 후보 검색에서는 음식점 API를 호출하지 않는다. 선택 목적지의 실제 관광지가 있는 매핑 하위 지역을 방문 수·첫 방문·지역 ID 순으로 최대 3개 조회한다. 지역당 100개씩 최대 3페이지, 동시성 최대 2, 전체 최대 9호출이다. 대표 KTDB 존 한 구로 고정하지 않는다. 상한으로 제한된 조회 범위를 전체 지역 음식점이라고 표현하지 않는다. 목록 전체의 상세·운영시간·메뉴는 조회하지 않는다.

선택 스냅샷에는 TourAPI 음식점 콘텐츠 ID, 이름, 주소·좌표, 분류, 대표 이미지, 수집일 등 목록 기본 정보와 지역N문화 음식 키워드·모범음식점 근거를 보존한다. 지역N문화 키워드와 모범음식점 인증 캐시는 정기 수집 결과를 사용한다.

TourAPI 목록과 모범음식점 인증 캐시는 전화번호가 정확히 일치할 때 우선 결합하고, 전화번호가 없을 때만 정규화한 상호와 도로명·지번 주소가 모두 일치할 때 결합한다. 모호하거나 불일치한 레코드에는 모범음식점 가점을 주지 않는다. 지역N문화 관련 음식점 필드는 이 결합에 사용하지 않는다.

일정은 해당 현지 식사 앞뒤 관광지와의 좌표 근접성, 대표음식 문화 키워드, 안전하게 연결한 모범음식점 근거, 콘텐츠 ID 순으로 식당을 고른다. 직선거리 기반 추정 이동시간을 포함해 배치 가능한 후보를 순서대로 검토한다. 좌표 결측은 근접성 가점을 생략하고 이동 구간을 미확정 예약으로 처리하며 보조 원천 결측은 가점만 생략한다. 메뉴·운영시간·휴무 결측은 후보 제외 사유가 아니다. 현지 식사 전체에서 다른 콘텐츠 ID를 배정하며 부족하면 60분 식사 블록과 `추천할 식당을 더 찾지 못했어요` 안내를 유지한다. 이동 중 자유 식사는 음식점 결측이 아니다.

대체 후보는 다른 식사에 사용된 ID를 제외한다. 음식점 배정·교체 시 [서비스 2차 고도화 정책](SERVICE_ENHANCEMENT_PHASE_2_PLAN.md)으로 앞뒤 장소 간 이동을 다시 계산한다. 다른 식당·관광 선택을 초기화하지 않으며, 시각 고정·식사·귀가 제약 안에서 시간표만 재배치한다. 초기 배정 불가는 다음 후보를 검토하고 모두 불가하면 식사·미확정 예약과 사유를 유지한다. 사용자 교체 실패는 기존 계획 전체를 유지한다. 상호가 같아도 콘텐츠 ID로 선택·상세를 연결한다. 사용자 관광 편집 후 기존 선택 식당을 몰래 바꾸지 않는다.

일부 하위 지역 수집이 실패하면 성공한 목록을 유지하고 부분 실패·재시도를 보여 준다. 전체 실패해도 목적지·관광·식사 시간 블록을 유지하고 식사 정보만 재시도한다. 임의 식당으로 대체하지 않으며 이전 지역의 늦은 응답이 현재 계획을 덮어쓰지 않는다.

## 상세 확인

사용자가 음식점을 클릭할 때만 서버 Route Handler가 해당 콘텐츠 ID로 TourAPI `detailIntro2`를 호출한다. 이 요청에서 메뉴·운영시간·휴무 등 상세 정보를 보여 주고, 실제 방문 전 확인이 필요하다고 안내한다.

상세 호출의 성공·실패는 이미 만든 일정의 후보 순서·식사 블록·시간표를 바꾸지 않는다. 실패는 해당 음식점 상세의 재시도 상태로만 보인다.

## 제외 범위

- 음식점 메뉴 또는 운영시간을 검색 단계에서 조회·해석·필터링하는 처리
- 음식점 품질 순위, 평점·리뷰·광고 순위
- 상용 지도·리뷰 플랫폼 스크래핑 및 정적 음식점 fallback

## 준비 의존성

로컬 MVP 준비 시에는 지역N문화 원본을 정규화해 음식 문화 키워드만 적재하고, 모범음식점 API를 페이지 단위·제한 동시성으로 수집해 인증 캐시를 만든다. 이 두 작업은 TourAPI 공식 카테고리 지역 프로필 생성이나 여행 지역 후보 필터를 막는 의존성은 아니다. 인증 캐시 수집 실패 시에도 목적지 후보·TourAPI 음식점 목록은 사용할 수 있으며, 모범음식점 가점만 적용하지 않는다.
